# 聚合-本周工作内容

## 核心定位

**Agent 驱动，非固定映射表。** 每周的工作内容不同，Agent 必须阅读每条原始项的**实际内容**，理解语义后动态判断如何合并。不能仅凭关键词或固定映射表。

## 输入

从 `提取-本周飞书内容` 输出的结构化列表：

```json
[
  {"text": "建联25位达人，寄样10位...", "checked": true, "day": "周二"},
  {"text": "2000投流费用预算申请...", "checked": false, "day": "周一"},
  ...
]
```

约 17 条原始工作项。

## 指导原则（非硬编码规则）

Agent 在阅读内容后参考以下原则进行判断：

| 原则 | 说明 |
|------|------|
| **同领域同层合并** | 同一平台、同一执行阶段的操作优先合并 |
| **预算独立** | 涉及跨部门审批的预算项单独成条 |
| **策略独立** | 长期方向探索/策略规划独立成条 |
| **跨平台分开** | 抖音和小红书永远不合并 |
| **会议汇聚** | 所有会议合并为一条 |
| **单项独立** | 包装采购、团建等非达人任务各自独立 |

> 详细的正例/反例、判定标准和历史映射表见 [[references/consolidation-heuristics.md]]。

## 硬约束

> **聚合后不超过 10 条。** 无论原始工作项有多少，最终输出 ≤ 10 条。

如果 Agent 初次聚合超过 10 条，需要重新审视合并粒度，适当放宽同类项合并。

## 混合进度处理

当合并的多个子项进度不一致时：

| 场景 | 处理 |
|------|------|
| 所有子项 checked=true | → `进展100%` |
| 所有子项 checked=false | → `进展____%` |
| 进度不一致 | → Agent 给整体估计值（如：规划完成+预算待审批 → `进展50%`；大部分完成一项卡住 → `进展70%`） |

不取 max 也不取 min，给反映整体推进状态的估计值。

## 输出

```json
[
  {"domain": "抖音bd", "text": "建联25位达人寄样10位...; 查找达人32位...", "progress": "100%"},
  {"domain": "抖音bd", "text": "2000投流费用预算申请...", "progress": "____%"},
  {"domain": "小红书pr", "text": "达人建联不上新增备选方案...; 登记报价筛选206位...", "progress": "100%"},
  {"domain": "小红书pr", "text": "种草专项推进...; 预算确认...", "progress": "50%"},
  ...
]
```

- `domain`：`"抖音bd"` | `"小红书pr"` | `"入职融入"` | `"会议"` | `""`（无领域，如团建/包装）
- `text`：合并后的文本，子项间分号连接，保留飞书原文不编造
- `progress`：`"100%"` | `"____%"` | `"50%"` 等

## 检查点（三阶段人机确认）

> 每个检查点 Agent 必须暂停并等待人工回复"继续"后才能进入下一阶段。
> 人工回复"不对"或指出具体错误 → 回到对应阶段重新执行。

### CP1：标注预览（步骤 1 之后）

```
输出标注预览表：
| # | 原始项摘要 | 平台 | 层级 | checked |
|---|-----------|------|------|---------|
| 1 | 建联25位达人... | 抖音 | 执行 | ✅ |
| 2 | 2000投流预算... | 抖音 | 预算 | ❌ |
| ...

确认标注无误后回复"继续"，进入合并阶段。
```

### CP2：聚合草案（步骤 2-5 之后，输出之前）

```
输出聚合草案：
| # | domain | 合并内容摘要 | progress | 合并来源(#) |
|---|--------|-------------|----------|------------|
| 1 | 抖音bd | 建联25+催稿+查找32+素材 | 100% | #1,3,15,11 |
| ...

确认聚合无误后回复"继续"，进入最终输出。
如指出归类错误 → 回到 Agent 判断流程重新聚合对应项。
```

### CP3：最终输出确认

```
输出完整 JSON，等待人工确认"落盘"。
```

## Agent 判断流程

### 执行方法

Agent 从上游接收 JSON 输入后，按以下 7 步执行，每步输出中间结果到 CP 检查点：

```
步骤 1: 标注（→ CP1）
  逐条标注 平台（抖音/小红书/入职融入/通用）和 层级（执行/策略/预算/运营/会议/入职）
  输出标注预览表

步骤 2: 同层合并 — "同一执行阶段"判定标准：
  ✅ 可合并：
    · 操作对象相同（都在做达人建联、都在做素材处理）
    · 时间紧密相连（同一天或相邻天）
    · 产出性质一致（都是外联执行 or 都是内部材料）
  ❌ 不合并：
    · 一条是"建联达人"一条是"写周报" — 产出性质不同
    · 一条是"上周寄样跟进"一条是"下周规划" — 时间跨度过大
    · 一条仅完成一条完全未开始 — 进度差距过大（≥2 档）

步骤 3: 独立项判定
  预算项 → 关键词含"预算/费用/审批/申请/内控/财务" → 独立成条
  策略项 → 关键词含"方案/名单/规划/策略/方向/权限" → 独立成条

步骤 4: 会议汇聚
  所有含"会议/拉齐/周会/讨论"的项 → 合并为一条，末尾附关键结论

步骤 5: 计数门禁（→ CP2）
  聚合后 > 10 条 → 回到步骤 2 放宽粒度：
    第 1 次放宽：同平台内所有执行层合并为 1 条
    第 2 次放宽：同平台所有项合并为 1 条（预算+策略+执行全合）
  连续 2 次仍 >10 → 输出当前最优 10 条 + 标注 "forced_truncation": true

步骤 6: 混合进度处理
  合并子项进度不一致 → Agent 给整体估计值（不取 max/min）

步骤 7: 输出（→ CP3）
  最终 JSON 数组
```

## 边界条件

| 条件 | 处理 |
|------|------|
| 输入为空数组 `[]` | 报错：上游提取步骤未返回任何工作项，检查飞书文档是否已更新 |
| 输入不是数组或格式不匹配 | 报错：输入格式错误，期望 `[{text, checked, day}, ...]`，实际收到 `{type}` |
| 某条原始项 `text` 为空字符串 | 跳过该条，警告 `"skipped_empty_text": true` 并继续 |
| 某条原始项缺少 `checked` 字段 | 默认 `checked=false`，警告 `"missing_checked_field": true` |
| 某条原始项缺少 `day` 字段 | 默认 `day="未标注"`，不中断 |
| 输入仅 1 条原始项 | 不合并，直接包装为 1 条聚合项输出 |
| 输入仅 2 条原始项（同平台同层级） | 正常合并为 1 条 |
| 聚合后 > 10 条 | 放宽合并粒度，重新执行步骤 2-3；连续 2 次仍 >10 → 输出当前最优 10 条 + 标注 `"forced_truncation": true` |
| 所有原始项 checked=false | 所有聚合项 progress 均为 `____%`，正常输出 |
| 聚合后无会议项 | 不虚构会议条，正常跳过 |
| 聚合后无某平台项（如无小红书pr） | 不虚构该平台条，正常跳过 |
