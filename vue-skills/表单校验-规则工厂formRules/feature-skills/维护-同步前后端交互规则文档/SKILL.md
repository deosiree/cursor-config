# 维护-同步前后端交互规则文档

父级：[`../../SKILL.md`](../../SKILL.md)。本 feature 维护源码事实与产品文档，不修改业务运行时代码，也不代替样本同步。

## 何时使用

- 当前任务新增、修改或删除 `microfb/src/utils/formRules.ts`。
- 当前任务新增、修改或删除 `apex_dev/src/utils/formRules.ts`。
- 用户明确要求重构或核对跨仓表单校验规则总目录。

## 何时不要使用

- 仅改翻译文案、组件样式或页面消费端，两个规则工厂均未变。
- 用户只要求同步 skill 模板；改走独立的 [维护-从业务仓同步样本](../维护-从业务仓同步样本/SKILL.md)。
- 仅设计后端 API，且没有前端表单规则需要对齐。

## 真相来源

- 当前工厂和消费端源码是前端规则的事实依据；旧文档只作为迁移输入，不作为当前规则依据。
- 后端字段、接受集合和接口约束以当前服务源码及 Swagger/API 契约为依据。
- 仅当本会话实际能访问 HexHub 时才引用实时 DDL；不可用时沿用用户确认的实体区分，未确认的物理列约束标记为待核实。
- 菜单节点归入 `[数据] menu（菜单节点）`，API 节点归入 `[数据] menu-api（API 节点）`，不可混写。
- 当前业务仓根路径以用户指定的 `microfb`、`apex_dev` 为准；不要拿 `nebula-all` 等副本替代。

## 执行步骤

1. 记录两个仓库的工作区状态；只依据当前源码，不覆盖用户已有文档或代码修改。
2. 读取两边 `src/utils/formRules.ts`，列出规则工厂、组合规则、导出常量及只供内部调用的 helper。
3. 对每个规则工厂搜索所有生产消费点：`rules` 绑定、组件 `:rules`、`@blur`/trim、字段级自定义 validator、提交前校验、网关映射。测试引用单独标记，不算业务消费。
4. 搜索页面或 composable 在工厂外追加的必填、唯一性、关联字段、动态值、文件、提交校验；标出实际页面/组件，不把它们归给工厂。
5. 查阅相关后端实现、Swagger 和 `docs/product/menu-route-path-validation.md`。分别记录前端工厂、消费端补充、后端契约，不把三者的接受集合推断为相同。
6. 若前后端规则或现有产品契约接受集合冲突：暂停该属性的统一裁决，列明两边实现证据、文件位置和具体差异，等待人类决定；不得私下择一、删除旧约束或并写两套 live 规则。
7. 更新唯一正文 `docs/product/frontend-form-validation-rules.md`，按 `[模块]` → `[数据]` → `[属性]` 组织。每项用无序列表分别写 `要求`、`场景`、`实现`、`伪代码`；实现须列出工厂、消费组件/页面、业务补充和相关后端契约。无生产消费的工厂明确标记“未消费”。
8. 路由路径属性链接专项契约，不复制完整契约细节；只有后端接受集合或接口契约受影响时才更新专项文档。
9. 确保 Apex 旧文档路径只保留到新正文的短链接，并在 `docs/product/README.md` 登记 SSOT。检查源码链接、模块名和数据实体层级。
10. 独立执行样本同步 feature；不得以更新 `template/` 代替更新产品文档。

## 输出检查

- [ ] 已扫描两边规则工厂，以及全部生产消费端和工厂外业务校验。
- [ ] 工厂规则、页面/网关补充规则、后端/API 契约分别标明。
- [ ] 未消费规则工厂有明确清单；仅测试调用未误记为业务消费。
- [ ] `menu` 与 `menu-api` 独立分章；菜单路径链接专项契约。
- [ ] 每项都含要求、场景、实现和伪代码，正文不使用表格或长段落。
- [ ] 接受集合冲突已暂停并附证据，未自行选边。
- [ ] 新正文是唯一 SSOT，旧路径只作重定向，索引和源码链接有效。
- [ ] 样本同步独立完成；未修改 locale 或无关运行时代码。

## 使用示例

```text
apex_dev/src/utils/formRules.ts 已修改菜单路径规则。
先完成页面落地，然后运行本 feature：检查 apex_dev 与 microfb 的工厂和全部消费点，核对菜单后端实现/API；更新 docs/product/frontend-form-validation-rules.md。若接受集合冲突，列证据并停下该项。随后独立运行业务仓样本同步。
```
