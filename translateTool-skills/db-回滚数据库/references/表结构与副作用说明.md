# 表结构与副作用说明

## 涉及表

| 表 | 角色 |
|----|------|
| `term_agent_audit` | Agent 术语学习待审核队列；`review_status`: pending / approved / rejected |
| `t_translate` | 术语库 + 工作台翻译共用；`translate_state`: 1=待翻译审核, 3=已审核术语库 |
| `t_entry_info` | 工作台词条；`{lang}_trans_id` 指向当前语种翻译 |

## 批量同意副作用（TermAuditService.review）

源码：`translationtool/terminology-agent/app/services/term_audit/service.py`

同意且存在 `suggested_translation` 时顺序：

1. **`_sync_workbench_entry`** — 回写 `t_entry_info` 挂载的 `t_translate`，通常 `translate_state=1`
2. **`update_audit`** — `review_status='approved'`
3. **`_merge_to_store`** — 若术语库无精确匹配（`find_exact` 仅查 state=3），**INSERT** 新 `t_translate`（state=3）

因此一次同意可能产生 **两条** `t_translate`：

- state=3：术语库（可能未被 entry_info 引用，`ref_count=0`）
- state=1：工作台当前挂载（`entry_info.en_trans_id` 等指向）

## 语种 → 外键列

与 `terminology-agent/app/shared/term_word/etl/constants.py` 一致：

| type / target_lang | 列名 |
|--------------------|------|
| 英文 | `en_trans_id` |
| 俄文 | `ru_trans_id` |
| 法文 | `fra_trans_id` |
| 西文 | `spa_trans_id` |
| 中文 | `zh_trans_id` |

## 回滚四步

| 步骤 | 操作 | 目的 |
|------|------|------|
| 1 | `t_translate` 软删 state=3 | 撤销术语库入库 |
| 2 | `t_entry_info.{lang}_trans_id = NULL` | 解除工作台挂载 |
| 3 | `t_translate` 软删 state=1 | 删除工作台译文记录 |
| 4 | `term_agent_audit.review_status = 'pending'` | 恢复待审核列表 |

## 与 auto_approved 的差异

| 路径 | 写 audit | 写术语库 state=3 | 写工作台 state=1 |
|------|----------|-----------------|-----------------|
| 人工 batch approved | 是 | 可能（无重复时） | 是 |
| pre_translate auto_approved | 否 | 否 | 是 |

auto_approved 回滚见 `扩展场景-预翻译与工作台.md`。

## task_name vs department

- `term_agent_audit.task_name` — 翻译任务名（如 `admin-proj`）
- `term_agent_audit.department` — 部门（如 `通用平台部`），对应 `t_translate.visual_range`

用户说「admin-proj 项目」通常指 **task_name**，不是 department。

## 何时用整库 restore vs audit 逐条回滚

| 场景 | 方式 |
|------|------|
| 本地测试，操作多、不想逐条排查 | **backup + restore**（见 `备份与整库恢复说明.md`） |
| 只撤销几条术语同意，其他数据不能动 | **audit 四步回滚** |
| 测试前忘了备份 | audit 逐条或手动 mysqldump 后 restore |

整库 restore 会覆盖 **全部表**，不限于 audit / translate / entry_info。
