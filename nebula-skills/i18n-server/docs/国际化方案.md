# 1. 背景与目标

## 1.1 背景

现有云平台相关系统仅支持中文硬编码，无法满足不同地区用户的语言习惯。

## 1.2 目标与范围

系统需要支持多语言，根据用户语言环境自动展示对应语言内容，保证：

*   用户界面文案正确翻译
    
*   API 返回信息与用户语言一致
    
*   数据排序、搜索、过滤在多语言环境下保持一致性
    
*   多租户环境下语言策略清晰
    

目标：

1.  支持多语言 UI
    
2.  支持多语言 API 返回
    
3.  支持租户级默认语言
    
4.  支持用户级语言设置
    
5.  保证搜索 / 排序 / 分页一致性
    
6.  前后端语言同步，保证显示到用户界面的语言保持统一
    

范围：

*   全站文本的动态替换（中/英/其他目标语言）
    
*   **金额**的自动格式化（符号、千分位、小数位随语言变化）
    
*   **日期/时间**的自动格式化（顺序、分隔符、12/24小时制随语言变化）
    
*   目标语言单复数适配
    
*   组态工具图形画面文本翻译
    
*   后端返回到前端需要展示的数据、信息等
    

具体策略：

1.  提供用户级的语言切换入口，并持久化用户选择
    
2.  将多语言 Key 的管理纳入开发规范（禁止硬编码中文）
    
3.  自动抽取代码中需要翻译的中文，并且转换成目前平台翻译工具可导入的excel，统一处理翻译
    
4.  性能：按模块抽取词条、按需引入

# 2. 场景分析

#### 2.1 语言来源

系统语言可能来自以下来源：

| 来源 | 说明 |
| --- | --- |
| 浏览器语言 | HTTP `Accept-Language` |
| 用户设置 | 用户个人语言 |
| 租户默认语言 | 租户级配置 |
| 系统默认语言 | 系统 fallback |

#### 2.2 首次登陆/多租户的语言选择

*   新用户首次访问`Accept-Language`、租户默认语言、系统默认语言的优先级冲突如何处理
    
*   用户语言设置与租户默认语言不一致时：是“个人优先”还是“租户强制”
    
*   同一个浏览器多个租户/多个账号：localStorage 的 key 维度如何区分（否则互相污染）
    

#### 2.3 前端

*   界面上看到的内容，由前端按用户 locale 渲染
    
    *   UI 文案：菜单、按钮、表单、提示、空状态、引导
        
    *   用户输入的入库数据
        
    *   展示型字段名：表格列名、详情页 label、图表图例/tooltip、枚举
        
    *   用标准库/Intl API 格式化：时间/数字/货币/单位（格式化原始值）
        
    *   通知系统：告警/工单/运营消息
        
    *   导入导出：报表相关内容
        
*   前端框架翻译（element-plus框架支持）
    
*   组态工具图形画面，涉及翻译的内容
    
    *   画面编辑：用户输入文本、绑定变量、图元、图表等
        
    *   浏览态渲染：实时变量更新时，哪些文本需要翻译、哪些不翻译（变量值/单位/状态等）
        
    *   画面导入导出/复制：i18n 资源如何随画面一起迁移，避免丢翻译
        
*   搜索/排序/过滤
    
    *   资源列表按名称排序在不同语言下顺序不同
        
    *   搜索（前缀/大小写/重音）命中差异
        
    *   排序 + 分页导致翻页不稳定：（比如第一页Apple Banana、第二页apple banana。导致分页数据跳动。排序必须加 **稳定 secondary key）**
        
    *   前端排序 vs 后端数据库排序不一致：**排序必须统一在后端实现**
        
    *   过滤条件语言问题：采用枚举
        

#### 2.4 后端

*   语言选择
    
    *   前端传递：Accept-Language: en
        
    *   系统语言，不随浏览器变化（审计日志）
        
*   文本范围
    
    *   API 返回消息、异步任务消息、系统提示模板
        
    *   错误信息（Error Message）
        
    *   系统枚举值翻译
        
    *   告警
        
    *   审计日志（Audit Log）
        
    *   系统配置内容
        
    *   权限系统（RBAC）
        
    *   系统资源名称
        
    *   导出文件（CSV / Excel）
        
    *   API 文档内容
        
    *   时间：根据租户时区算 / 数字 ~~/ 货币格式~~
        
*   搜索 / 排序（Collation）
    
*   URL / slug 文本：不应该依赖翻译，否则会导致链接变化
    

#### 2.5 特殊场景分析

1、**用户输入类的内容：**

*   对于租户名、设备类型、告警描述等用户可编辑字段，建议统一采用**JSON字段扩展法**进行多语言支持。
    
*   前端界面提供“翻译”操作入口，允许用户为当前字段填写各语种版本，未填写则默认显示原始输入内容。当用户在当前界面语言（如中文）下输入内容时，系统自动将该值作为默认语言（zh-CN）。用户可随后通过“编辑”入口补充其他语言版本（如 en-US）。若某语种未配置，展示时自动降级（Fallback）回显默认语言内容。数据结构示例：{ "deviceName": { "zh-CN": "设备 1", "en-US": "Device 1" } }
    
*   该方式避免频繁修改数据库结构，也规避了词条抽取带来的维护成本。

2、**搜索框查询：**

*   多语言文本匹配：后端需根据请求头或参数中的 `locale`（当前语言），动态映射并查询数据库中对应的语言字段（如 `name_zh` 、 `name_en`），后端根据当前当前语言匹配查询字段对应的语言值。
    
*   枚举/字典值处理：对于“状态”、“类型”等基于后端 Code（代码值）存储的枚举字段，前端传递的可能是翻译后的文本（如“已完成”）。后端需先通过多语言字典映射表将输入文本反查为对应的 Code（如 `FINISHED`），再对 Code 字段进行精确匹配查询；若前端直接传递 Code，则直接匹配。

#### 总结：

**第一层：前端**

1.  不翻译输入：用户输什么，传什么。
    
2.  传递上下文：请求头或参数中必须携带 `Accept-Language` 或 `locale`。
    
3.  枚举处理：
    
    *   若是下拉筛选，直接传 `Code`。
        
    *   若是文本搜索，提示用户“请输入关键词”。
        

**第二层：后端API**

*   如果是关键字查询，后端需要拿这个关键字去匹配需要查询的字段对应的语言值进行过滤。
    
*   枚举值则code直接匹配。
    

**存在问题：**

JSON字段法虽灵活，但可能带来查询性能下降与数据膨胀问题，对高频查询字段是否仍采用传统词条定义方案？

3、**审计日志/告警：**

**结构存储，动态渲染，建议采用“存储 Code + 参数（JSON）+ 描述”，运行时动态翻译。**不要将翻译后的完整文本直接入库。告警、审计入库数据统一按租户语言入库，不随前端语言变化。否则前端切换语言查询会有问题。

数据库中只存储**事件代码（Event Code）**和**上下文参数（Context Params）**。展示时，后端根据当前用户的语言环境，实时组合获取翻译后传给前端。

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/ABmOoWbvDEjMNOaw/img/4356a616-db6c-4f25-9c09-36ce0bcb32b4.png)

**存在的问题：**

*   若采用code模板方案，节点名、操作人等变量参数是否翻译？
    
*   边端上报告警时，云端与边端需共用一套code体系，目前尚无统一模型，协调成本高。
    

4、**导入导出**

**1）导出**

**当前界面语言为准**

*   不存翻译，只存 Code/ID：导出的文件中，对于枚举值（如状态、类型），严禁直接存储翻译后的文本（如“已完成”），而应存储通用 Code（如 `COMPLETED`）或多语言 Key。
    
*   动态渲染文本：对于普通文本字段（如产品名称、描述），根据当前操作用户的 Locale，实时从数据库对应的语言字段（`name_zh`, `name_en`）或翻译服务中获取内容填入 Excel/CSV。
    
*   表头本地化：Excel 的列头（Header）也必须根据当前用户语言进行翻译。
    

**2）导入**

*   上传的模板中，关键枚举字段必须填 **Code**（如 `COMPLETED`），而不是文本。
    
*   在导入模板中，明确区分语言列。
    

| ID | Name\_zh | Name\_en | Name\_ru | Status\_Code |
| --- | --- | --- | --- | --- |
| 101 | 设备 | Device | xxx | COMPLETED |

# 3. 需求分析

#### 3.1 前端翻译涉及内容

####  界面显示语言策略

*   用户首次进入系统时，如果本地存储（localStorage）中的语言值lang存在，则取本地lang，否则语言由浏览器 `navigator.language` 自动获取，并本地化存储。
    
*   若用户在登录页面手动切换语言（如从中文切为英文），该选择将被持久化至浏览器本地，后续所有界面均以此为准，不受租户或后端设置影响。
    
*   登陆后的语言也支持切换，页面实时更新对应语言，语言值本地化存储。
    
*   语言设置完全独立于租户配置，不存在租户上下文。

#### 时区语言策略

*   租户创建时需要管理员设置默认时区
    
    *   前端的所有时间基于租户时区转换、传递给后端为UTC时间
        
    *   后端统计服务等入库时间格式为UTC、
        
*   租户创建时需要管理员设置默认语言，该设置**不影响前端界面显示语言**。
    
    *   租户语言仅用于后端处理与该租户相关的~~日志~~、告警、审计等入库信息的文本翻译，确保生成内容的语言一致性。（审计：系统审计、租户审计）
        
    
*   前端界面语言始终以浏览器设置为准，与租户语言无绑定关系
    

#### 时区配置与使用逻辑

*   **租户时区的必要性**
    
    *   所有服务端时间存储和计算均采用 **UTC 时间**，但租户必须配置其所在时区（如东八区）。
        
    *   主要用于设备统计数据的“天”维度划分：例如中国租户设为 UTC+8，则统计服务将以 UTC+8 的 00:00 作为一天的起点，而非 UTC 的 00:00。
        
    *   若不依赖租户时区，跨时区设备的数据统计会出现“日期错位”，影响业务准确性。
        
*   **前端时间展示与转换规则**
    
    *   用户在界面上操作的时间（如下拉框选择“8:00”）均指**租户时区对应的时间**，而非浏览器本地时间或 UTC。
        
    *   前端在调用后端接口前，需将用户选择的租户时区时间转换为对应的 UTC 时间传入；后端返回的 UTC 时间也由前端根据租户时区还原为可读时间展示。
        
    *   服务端不参与时间格式化，仅处理 UTC 时间，避免多层转换导致混乱。
        
    
    ##### 接口参数（推荐）
    
    ```json
    {
     "startTime": "2026-03-23T00:00:00Z", // 明确是 UTC
     "timezoneContext": "Asia/Shanghai" // (可选) 告诉后端这个时间是基于哪个时区转换来的，方便后端做日志审计或二次校验
    }
    ```
    
*   **语言与时区解耦**
    
    *   语言与时区为两个独立配置项，不可通过语言自动推断时区。例如用户使用中文界面，但租户可能位于 UTC-5 美国区域。
        
    *   界面可同时显示当前语言（如“中文”）和租户时区偏移（如“UTC+8”），两者分别管理，互不影响。
        

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/ABmOoWbvDEjMNOaw/img/336bb28b-b414-4f01-ac50-e72c511fc894.png)

#### 前后端时间交互模式

*   **统一采用前端转换策略**
    
    *   所有时间字段在前后端交互中均以 UTC 格式传输，**时间的加减转换由前端负责**。
        
    *   前端在请求时将租户时区下的时间转为 UTC，在响应后将 UTC 时间转回租户时区进行展示。
        
    *   后端无需解析时区上下文，简化逻辑并降低耦合。
        
*   **特殊场景：统计服务的时区处理**
    
    *   统计服务需基于租户时区确定每日数据切片的起止点（如 UTC+8 租户的“今日”从 UTC 时间 16:00 开始）。
        
    *   该逻辑由后端根据租户配置动态计算，是唯一需要在服务端处理时区偏移的场景
        

#### 语言翻译范围

*   前端负责界面显示内容的翻译，使用资源文件进行多语言管理，前后端各自打包语言包，不通过远程拉取。
    
*   后端返回的 message 不应为纯文本，而应通过 code 或 key 的方式交由本地化服务进行**翻译后传递给前端**。
    
*   **运行期间入库的数据不需要翻译**，审计日志、告警记录等数据以结构化形式存储，仅将可枚举的静态部分进行多语言映射。
    
*   动态拼接的告警内容难以全量翻译，因此提出将告警描述进行**细分告警描述的组成，然后将各部分 使用 key 进行翻译**，如拆分为动作类型、对象类型、参数等固定字段，分别配置多语言词条。
    

#### 3.2 后端翻译涉及内容

*   代码中写死的值
    
*   系统内置的“资源元数据”
    
    *   枚举项显示名
        
    *   内置告警规则名、内置报表模板名
        
*   配置中心里的“模板/策略/文案配置”
    
    *   帮助文档、公告、活动文案、营销文案
        
*   数据库相关
    
    *   系统内置枚举数据
        
    *   可配置数据（后台配置）
        
    *   用户自定义内容：设备名称、描述、工单内容、备注、日志说明等（通常不翻译）
        
*   后端错误码体系： **Error Code + I18n**
    
*   日志 / 审计 / 操作记录
    
*   通知系统（邮件 / 短信 / 推送）
    
*   API / SDK 文档
    
    *   API 文档
        
    *   SDK 文档
        
    *   CLI 提示
        
*   时间 / 数字 / 货币格式：可提供原始值给前端翻译
    
*   权限 / 资源名称：系统内部的能力名称、功能模块名称、云资源类型名称等需要展示给用户的标识文本
    

#### 3.3 组态工具图形画面翻译

*   **双重语境**：既包含“编辑态”（配置界面时的提示、属性名、图元信息等），也包含“浏览态”（最终用户看到的监控画面）。
    
*   **动态绑定**：大量文本不是写死的，而是绑定到实时数据库变量、告警代码或外部数据源。
    
*   **用户自定义**：画布上放置的文本框、图元、图表等，这些内容需要被提取并支持多语言。
    
*   **高性能要求**：浏览态翻译不能阻塞渲染循环，需避免频繁的 DOM 操作或重绘。
    
*   **右键菜单：**
    
*   **图元内的文字：**若为编辑内容，应纳入翻译体系；建议图片尽量无文字，必要时通过叠加文本层实现可翻译性。
    
*   **组态画面考虑词条的抽取和翻译**，可在组态工具画面json里添加多语言字段，或打标后由脚本统一抽取至语言包。
    
*   支持单个画面文件内嵌多语言字段，避免维护多套画面文件带来的同步问题。
    
*   渲染时动态替换 Jason 文件中的文本节点，基于当前语言调用翻译方法完成展示，不修改原始文件内容。保持版本一致。

# 4. 需求整理

#### 4.1 功能需求

**（功能项 1）基于中文原文的动态文本渲染引擎**

*   **需求描述**：
    
    *   系统必须支持以**中文字符串**作为 `vue-i18n` 的 Key 进行翻译查找。
        
    *   在 `zh-CN` 环境下，Key 直接映射为自身（Value = Key），无需额外配置。
        
    *   在其他语言环境（如 `en-US`）下，系统需根据中文 Key 查找对应的翻译 Value。
        
    *   支持带参数的插值语法（如 `$t('你好，{name}', { name: 'Tom' })`），且参数名与语言无关。
        
    *   支持处理歧义场景，允许通过“中文后缀”（如 `'打开||文件'`）区分相同文案的不同语境，且在中文界面显示时可自动隐藏或统一显示为通用词。
        

**（功能项 2）区域化自适应格式化组件（金额/日期/数字）**

*   **需求描述**：
    
    *   提供统一的 `$n()` (Number/Currency) 和 `$d()` (DateTime) 全局 API。
        
    *   内置多套预设格式模板（如 `short`, `long`, `currency`, `dateOnly`），并在 `datetimeFormats` 和 `numberFormats` 中为每种支持的语言（zh-CN, en-US, de-DE 等）定义符合当地习惯的配置（如千分位符号、货币符号位置、日期顺序、12/24小时制）。
        
    *   当用户切换语言时，所有使用这些 API 的组件必须**即时响应**并重新渲染为对应地区的格式，无需刷新页面。
        

**（功能项 3）自动化资源扫描与同步工具链**

*   **需求描述**：
    
    *   提供 CLI 命令（如 node extract-i18n.js），自动递归扫描 `src` 目录下所有 `.vue` 和 `.ts/.js` 文件。
        
    *   提取所有 
        
        ```javascript
        t('...') 
        $t('...')
        this.$t('xxx')
        i18n.global.t('xxx')
        trans('xxx')
        ```
        
    *   组态工具画面文件：画面json文件内需要展示给用户的文本，指定一个固定key，脚本自动抽取。画面展示的地方调用国际化API。
        
    *   自动对比现有的 `locales/*.json` 文件：
        
    *   **新增检测**：将代码中存在但 JSON 中缺失的 Key 自动追加到所有语言包（中文包补全 Value，外文包标记为空）。
        
    *   **废弃检测**：识别 JSON 中存在但代码中已不再引用的 Key，生成“待清理清单”供人工确认（平台翻译工具支持冗余词条展示）。
        
    *   支持 JSON 文件的自动格式化排序，减少 Git 冲突。
        
    *   按需加载+ 异步切换\*首次加载只导入默认语言包，根据后续切换异步加载。
        
    *   如果语言包巨大（例如单个语言包 > 2MB），需要更细粒度的控制，比如：不要把所有文案抽取到一个 `zh-CN.json` 里。按路由或功能模块拆分。
        

**（功能项 4）翻译缺失降级与容错机制**

*   **需求描述**：
    
    *   配置 `vue-i18n` 的 `missingWarn` 和 `fallbackWarn` 策略。
        
    *   **降级策略**：当目标语言包缺失某个中文 Key 时，系统应直接**返回中文 Key 本身**作为显示内容，确保界面不出现空白或错误代码，保证基本可用性。
        
    *   **开发提示**：在非生产环境（Dev/Test），当发生缺失时，需在浏览器控制台输出清晰的 Warning 日志，指明缺失的 Key 和所在文件，辅助开发人员快速定位。
        

**（功能项 5）语言切换与持久化状态管理**

*   **需求描述**：
    
    *   提供全局语言切换接口，支持响应式更新整个应用的文本和格式。
        
    *   实现用户偏好持久化：用户切换语言后，自动将选择保存至 `localStorage` 或 `Cookie`。
        
    *   应用初始化时，优先读取用户本地存储的语言设置；若无记录，则根据浏览器系统语言（`navigator.language`）自动匹配最接近的支持语言；若均不匹配，默认 fallback 到 `zh-CN`。
        

#### 4.2 性能需求

*   **首屏加载延迟增量 ≤ 100ms**：引入国际化框架及加载默认语言包后，首屏渲染时间（FCP）增加不得超过 100ms。
    
*   **语言切换响应时间 ≤ 200ms**：用户点击切换语言后，界面所有文本和格式完成更新并呈现的时间不超过 200ms（不含网络请求时间，指本地渲染耗时）。
    
*   **内存占用增长 ≤ 5MB**：加载全部支持的语言包后，运行时内存占用增长控制在 5MB 以内。
    
*   **扫描工具执行时间** ：在标准项目规模（约 500 个 Vue 文件）下，自动化扫描与 JSON 同步脚本的执行时间不应过长
    

#### 4.3 质量属性需求（DFX）

*   **可维护性（Maintainability）**：
    
    *   **代码可读性**：强制要求源代码中的翻译 Key 必须是语义清晰的中文，禁止出现 `key_001` 或 `btn.save` 等非自然语言 Key，确保“代码即文档”。
        
    *   **文案解耦**：所有 UI 文案必须 100% 从代码逻辑中剥离，严禁硬编码。
        
*   **可靠性（Reliability）**：
    
    *   **降级可用**：在翻译文件损坏、网络加载失败或部分 Key 缺失的极端情况下，系统必须能稳定回退到中文显示，绝不允许出现白屏、JS 报错崩溃或显示 `undefined`。
        
    *   **数据一致性**：确保金额和日期的格式化逻辑严格遵循 `Intl` 标准，避免因手动拼接导致的格式错误（如欧洲用户看到错误的千分位）。
        
*   **可调试性（Debuggability）**：
    
    *   **缺失可视化**：在开发模式下，对于缺失翻译的 Key，可选择性地用特殊样式（如红色虚线框或背景高亮）在界面上标记出来，便于测试人员快速发现漏翻。
        
*   **可扩展性（Scalability）**：
    
    *   **语种热插拔**：架构需支持未来无缝接入新语言（如俄语、西语），仅需新增对应的 JSON 文件和格式配置，无需修改核心业务代码。
        
*   **安全性（Security）**：
    
    *   **XSS 防护**：在使用插值语法（`{param}`）时，必须对用户传入的参数进行 HTML 实体转义，防止翻译内容或参数中包含恶意脚本。（`vue-i18n` 默认配置为安全插值模式）
        

# 5. 国际化选型分析

*   国际化方案是建立一套 Key-Value 映射表，中文为key，核心在于**消除‘定义 Key’的中间环节**，让源代码即文档，直接以中文文案作为底层 `vue-i18n` 的检索键值。从“统一格式展示”转变为“基于 Locale（语言环境）的自适应格式策略”。
    
*   利用 `vue-i18n` 的灵活配置能力，将 `zh-CN` 的语言包 Key 直接设为中文原文，其他语言包则以中文原文为 Key 进行翻译映射。
    
*   国际化是**数据与展示的分离**以及**区域化适配**：不仅仅是文本翻译，更是**动态格式化引擎**的构建（针对货币、时间、数字、复数规则等）
    
*   **利弊分析**：
    
    *   **优势**：极大提升开发速度，代码可读性极高（代码里看到的即是最终中文展示），无需维护冗长的 Key 命名映射表。无需依赖外部插件来展示中文，而且外部插件并不支持文件内搜索。
        
    *   **挑战**：将“文案修改”与“Key 变更”强绑定。若中文文案微调（如“保存”改为“保存数据”），所有外语翻译将失效（因为 Key 变了），需同步修改外文翻译，不便频繁修改文案。
        

**方案分析：**

| **差异点** | **现状** | **国际化方案** | **影响分析** |
| --- | --- | --- | --- |
| **文本展示** | 硬编码中文： `<span>保存成功</span>` | Key 映射： `<span>{{ $t('保存成功') }}</span>` | 需要翻译的中文包上$t函数；开发习惯需改变 |
| **金额格式** | 手动拼接： `'¥' + num.toFixed(2)` | 配置驱动： `$n(num, 'currency')` | 移除所有手动拼接逻辑；需在 i18n 配置中定义 `numberFormats` |
| **日期格式** | 固定模板： `formatDate(date, 'YYYY-MM-DD')` | 区域自适应： `$d(date, 'short')` | 移除自定义格式化函数；依赖 `datetimeFormats`配置 |
| **语言切换** | 无 | 响应式切换： `locale.value = 'en-US'` (即时生效) | 需确保所有组件响应 `locale` 变化，无需刷新页面 |
| **资源管理** | 散落在代码中 | 集中管理： `locales/zh-CN.json`, `en-US.json` | 需建立文案审核与更新流程（Git 分支管理） |
| **语言包结构** | 无 | **Key 为中文的 JSON** `zh-CN`: `{ "你好": "你好" }` `en-US`: `{ "你好": "Hello" }` | `zh-CN` 包退化为“字典校验”，其他语言包以中文为键 |
| **代码可读性** |  | **极高**（代码即中文） | 发者无需查阅 Key 映射表，代码自解释性强 |
| **文案修改成本** | 低（直接改代码） | **高（需同步多语言）** | **风险点**：修改中文文案（Key 变更）会导致对应的外文翻译丢失，需重新补充翻译。相比较变量作为key，也可及时发现文案修改。 |
| **缺失处理** | 显示中文 | 显示 Key (中文) 或 Fallback | 若英文缺失，直接显示中文 Key，保证基本可用性 |
| **翻译词条抽取脚本** | 无 | 提供自动化抽取脚本，可配置目标语言，后可接入平台翻译工具，统一管理多语言翻译 | 基于node.js |
| **性能微损** |  | 长字符串作为 Key 进行哈希查找，理论上比短 Key 略慢（但在现代引擎中可忽略） | 无需特殊处理，`vue-i18n` 性能足以支撑 |

# 6. 使用场景

#### 6.1 场景

**场景 1：功能开发中的文本嵌入**

*   **完整流程**：
    
    1.  **编码**：开发人员直接在模板中使用 `$t('中文文案')`，例如 `<button>{{ t('保存成功') }}</button>`。无需预先去 JSON 文件定义 Key。
        
    2.  **本地运行**：
        
        *   当 `locale` 为 `zh-CN` 时，`vue-i18n` 查找 Key `'保存成功'`，直接返回 Value `'保存成功'`（Key=Value）。
            
        *   当 `locale` 为 `en-US` 时，查找 Key `'保存成功'`。若 `en_US.json` 中已存在该 Key，显示对应英文；若不存在，根据配置显示中文原文或 Key 本身（降级策略）。
            
    3.  **资源同步**：开发人员提交代码前，运行本地脚本（如 node extract-i18n.js），自动扫描代码中新增的 `$t('...')、trans('...')` 中文参数，并将其追加到 `locales/zh_CN.json` 和 `locales/en_US.json`（外文json标记空值）。
        
    4.  **翻译补全**：可通过脚本转换json为平台翻译工具可导入的excel文件，统一翻译导出，再转换成项目使用的json文件。
        
*   **前提条件 / 约束**：
    
    *   开发规范强制要求：禁止在 UI 层直接写中文字符串，必须包裹在 `$t()` 中。
        
    *   文案需保持简短稳定，避免在开发过程中频繁微调措辞。
        

**场景 2：用户动态切换语言环境**

*   终端用户在系统导航栏点击“语言切换”下拉框，选择“English”或“中文”。
    
*   **完整流程**：
    
    1.  **触发动作**：用户点击选项，调用 `i18n.global.locale.value = 'en-US'`。
        
    2.  **响应式更新**：
        
        *   `vue-i18n` 监听 `locale` 变化，触发全局重渲染。
            
        *   所有使用 `$t('中文 Key')` 的组件自动重新计算，从 `en_US.json` 中获取对应的英文 Value。
            
        *   所有使用 `$n()` (金额) 和 `$d()` (日期) 的地方，自动应用 `en-US` 对应的 `numberFormats` 和 `datetimeFormats` 配置（如 `$` 符号、`MM/DD/YYYY` 格式）。
            
    3.  **持久化**：系统将用户选择写入 `localStorage` 或 Cookie。
        
    4.  **刷新保持**：用户刷新页面后，初始化逻辑读取存储的语言配置，确保再次进入时仍为英文界面。
        
*   **前提条件 / 约束**：
    
    *   所有文本必须通过响应式 API 获取，严禁在 `created/mounted` 生命周期中将翻译结果赋值给普通变量（否则切换语言后不会更新）。
        
    *   非文本资源（如图标、图片）若包含文字，需具备随语言切换加载不同资源的能力
        

**场景 3：中文文案优化与迭代**

*   体验优化，将界面上的“确定”改为“确认提交”，或将“错误”改为“操作失败”。
    
*   **完整流程**：
    
    1.  **代码修改**：开发人员将代码中的 `$t('确定')` 修改为 `$t('确认提交')`。
        
    2.  **Key 失效检测**：
        
        *   此时，`en_US.json` 中原本存在的 `{ "确定": "Confirm" }` 映射关系失效。
            
        *   系统运行时，若切换到英文，`$t('确认提交')` 找不到对应 Key，触发“fallback”机制（显示中文“确认提交”或空）。
            
    3.  **差异扫描**：node extract-i18n.js
        
        *   识别出废弃 Key：自动删除冗余的key`"确定"` 。
            
        *   识别出新增 Key：`"确认提交"`（待翻译的文案为空）。
            
*   **前提条件 / 约束**：
    
    *   **强约束**：文案修改必须伴随翻译同步流程，严禁只改中文不改翻译包。
        

**场景 4：同词异义的处理（歧义场景）**

*   不同业务场景下出现相同的中文文案，但目标语言翻译不同。
    
    *   例 1：列表操作列的“打开”（Open）。
        
    *   例 2：设备控制列的“打开”（Turn on）。
        
*   **完整流程**：
    
    1.  **识别冲突**：开发人员发现直接写 `$t('打开')` 会导致英文环境下统一翻译成 "Open"，不符合设备控制语境。
        
    2.  **Key 差异化处理**：
        
        *   当前方案 ：在中文 Key 后增加隐性后缀。代码写为 `$t('打开||文件')` 和 `$t('打开||开关')`。自动化抽取词条脚本会自动截断 || 后的语境，生成zh-CN.json:{"`打开||文件":"打开","打开||开关":"打开"`}
            
    3.  **翻译映射**：
        
        *   `en_US.json`: `{ "打开||文件": "Open", "打开||开关": "Turn On" }`。
            
        *   `zh_CN.json`: `{ "打开||文件": "打开", "打开||开关": "打开" }` (显示时均为“打开”)。
            
*   **前提条件 / 约束**：
    
    *   需在开发规范中明确：遇到歧义必须加后缀，禁止强行复用 Key。
        

#### 6.2 异常场景

**异常 1：翻译文件缺失 Key（Key Not Found）**

*   **现象**：代码中使用了 `$t('新增功能文案')`，但 `en_US.json` 中尚未录入该条目（翻译滞后）。
    
*   **处理策略**：
    
    *   **降级显示**：配置 `vue-i18n` 的 `fallbackLocale` 或 `missingWarn` 策略。
        
        *   策略 A：直接返回 Key 本身（即显示中文“新增功能文案”），保证用户能看懂，不影响功能。
            
        *   策略 B：显示特定占位符（如 `[Missing Translation]`），便于测试阶段快速发现漏翻。
            
    *   **日志记录**：在开发/测试环境控制台输出 Warning，提示缺失的 Key，生产环境静默忽略。
        

**异常 2 ：长文案导致的 UI 布局崩坏**

*   **现象**：中文“保存”仅 2 个字，俄语、西文会更长。固定宽度的按钮或表格列导致文字换行、溢出或遮挡。
    
*   **处理策略**：
    
    *   **UI 自适应**：强制要求所有包含文本的容器（按钮、表头、弹窗标题）使用弹性布局（Flexbox）或最小宽度限制，禁止硬编码 `width: 60px`。
        
    *   **样式隔离**：针对不同语言设置 CSS 类名（如 `html[lang='de'] .btn`），允许特定语言下调整字体大小或行高。
        
    *   **测试覆盖**：自动化测试或人工验收时，必须切换至“最长语言包”（通常是德语或俄语）进行布局验证。
        

**异常 3：性能问题（大文件加载）**

*   **现象**：随着项目迭代，单个 JSON 文件达到数 MB，导致首屏加载变慢。
    
*   **处理策略**：
    
    *   **按需抽取**：语言包按模块抽取
        
    *   **按需加载**：利用 Webpack/Vite 的动态导入，仅在当前选择的语言包加载时请求对应 JSON 文件，而非打包进主 bundle。
        
    *   **缓存策略**：对静态 JSON 文件配置强缓存，仅在版本更新时重新拉取。
