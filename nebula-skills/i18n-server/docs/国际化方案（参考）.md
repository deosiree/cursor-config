# 国际化方案（参考）

# SaaS 国际化（i18n/l10n）需要做什么：范围、要翻译的内容、能力提供方式与可选方案

> 目标：用一套可扩展的机制，让同一套 SaaS 在不同语言/地区下可用、可维护、可运营。  术语：i18n=国际化（工程能力）；l10n=本地化（具体语言/地区的内容与格式）。

---

## 1. 需要考虑哪些内容（范围清单，不涉及真实的具体的）

### 1.1 语言类（Human-readable 文本）

*   控制台/前端 UI：菜单、按钮、表单、提示、空状态、引导、帮助说明
    
*   后端“面向用户”的输出：错误提示、告警标题/描述、建议动作
    
*   通知：站内信、邮件、短信、Webhook 消息体
    
*   导出/报表：CSV/Excel/PDF 中的标题、列名、汇总字段、页眉页脚
    
*   文档/帮助中心（如果产品包含）：FAQ、产品内帮助、引导文档
    

### 1.2 格式类（Locale formatting / l10n）

*   时间/日期：显示格式、时区（UTC vs 用户时区）、夏令时
    
*   数字/货币：千分位、小数点、币种符号、金额格式
    
*   单位与度量：MB/GB、℃/℉、km/mi（是否需要按地区切换）
    
*   排序与比较：不同语言的 collation（尤其是列表排序/搜索）
    

### 1.3 数据类（存储在 DB/配置中心的“名称/描述/模板”）

*   系统内置元数据：模块名、字段显示名、枚举项显示名、内置模板/策略名
    
*   运营/通知模板：邮件标题/正文、短信模板、告警描述模板
    
*   用户自定义内容：名称、描述、备注、工单内容、知识库文章（默认不强制翻译）
    

---

## 2. 需要翻译哪些部分（建议拆成 3 类）

### A 类：必须翻译（强 i18n）

**用户每次都会看到且由系统提供/控制的文本**

*   前端 UI 文案（全量）
    
*   系统错误/提示（用户可见部分）
    
*   告警标题/描述（系统内置的那部分）
    
*   通知模板（系统发送的内容）
    
*   导出/报表中的固定文本（列名/标题等）
    
*   内置枚举显示名（Running/Stopped 等）
    

### B 类：建议翻译（可分阶段）

**用户会看到，但可能先英文/中文兜底也能接受**

*   产品内帮助、引导说明
    
*   内置规则、内置报表模板、内置知识条目（如果有）
    
*   操作建议/Runbook 文案（若面向用户）
    

### C 类：默认不翻译（以原文为准，提供可选增强）

**用户输入内容，强制翻译会带来语义/审计/成本问题**

*   设备名称、描述、备注
    
*   工单内容、评论
    
*   用户上传文档
    

> 可选增强：提供“自动翻译生成副本/多语言版本”，保留原文 + 可编辑译文 + 标记生成来源与时间。

---

## 3. 后端返回内容要不要翻译（最简结论）

### 3.1 推荐原则

*   **API 返回必须稳定可编程**：用 `code` / `error_code` / `reason`（机器字段）作为主输出
    
*   **可选返回本地化文案**：`message` 仅用于展示，不能当逻辑判断依据
    

### 3.2 什么时候后端必须做翻译

*   后端直接生成给用户看的内容：邮件/短信/站内信、导出报表、定时通知
    
*   没有前端参与渲染的场景：纯 API 产品希望“开箱即显示本地化 message”
    

---

## 4. 如何提供国际化能力（产品侧能力/接口约定）

### 4.1 Locale 选择与传递（必须统一）

*   请求级：`Accept-Language`（或 `?locale=`）
    
*   用户级：个人语言设置
    
*   租户级：租户默认语言
    
*   系统级：平台默认语言
    
*   **兜底链**：用户语言 → 租户默认 → 系统默认（常用 en）
    

### 4.2 统一“文案渲染”机制（避免到处拼字符串）

建议统一为：

*   `message_key`：文案键（例如 `error.permission_denied`）
    
*   `params`：占位参数（例如 `{resource:"device/123"}`）
    
*   客户端/服务端按 locale 渲染 message（使用 ICU MessageFormat 或简单占位）
    

### 4.3 对外接口建议（错误/提示）

*   必选：`error_code`
    
*   建议：`message_key`、`params`
    
*   可选：`message`（按 locale 渲染好的文本，方便简易客户端展示）

## 5. 实现这些能力的可选方案（按层拆解）

## 5.1 前端 UI 文案方案

### 方案 F1：前端资源包（最常见）

*   UI 使用 i18n 框架（如 i18next / vue-i18n）
    
*   文案以 key 管理，构建时/运行时加载语言包
    

**优点**：实现简单、性能好、体验稳定   **缺点**：运营临时改文案需要发版（可通过远端语言包缓解）

### 方案 F2：远端语言包 + CDN（运营友好）

*   语言包放在对象存储/配置中心/CDN
    
*   前端启动时拉取（带版本号、缓存）
    

**优点**：可热更新   **缺点**：需要版本/缓存/灰度机制

---

## 5.2 后端“错误/提示/告警文案”方案

### 方案 B1：只返回 code + key + params（推荐）

*   后端不直接输出最终文案
    
*   前端根据 key 在本地/远端语言包渲染
    

**优点**：API 稳定、跨多端一致、便于自动化   **缺点**：前端/调用方必须具备渲染能力

### 方案 B2：后端按 locale 渲染 message（兼容第三方）

*   后端维护一套语言资源（或调用统一 i18n 服务）
    
*   请求带 locale，后端返回 message
    

**优点**：调用方简单   **缺点**：后端维护成本更高；多端一致性要治理

### 方案 B3：网关/聚合层渲染（折中）

*   微服务返回 key/params
    
*   API Gateway/BFF 统一渲染成 message
    

**优点**：治理集中、对下游服务侵入小   **缺点**：网关复杂度提高；需要保证性能与缓存

---

## 5.3 DB / 配置中心里的“名称/模板”国际化方案

### 方案 D1：翻译表（推荐，最可扩展）

**模型示例**

*   `i18n_text(resource_type, resource_id, field, locale, text)`
    
*   主表存“资源标识”，显示时 join 或批量拉取
    

**优点**：语言可无限扩展、审计与版本可控   **缺点**：查询与缓存要设计好（否则性能/复杂度上升）

### 方案 D2：JSON Map 存储（灵活）

**模型示例**

*   `display_name = {"zh-CN":"设备管理","en-US":"Device Management"}`
    

**优点**：读写简单、适配配置中心很自然   **缺点**：索引/检索/部分更新不如翻译表；语言增多会变大

### 方案 D3：多列存储（不推荐）

**模型示例**

*   `name_zh`, `name_en`, `name_ja` ...
    

**优点**：实现直观   **缺点**：语言扩展会频繁改表结构；长期维护成本高

---

## 5.4 通知模板（邮件/短信/站内信/Webhook）方案

### 方案 N1：模板按语言分版本（常见）

*   每个模板一组：`template_id + locale`
    
*   发送时按 locale 选择对应版本
    

**优点**：可控、好运营   **缺点**：模板数量随语言增长

### 方案 N2：模板内容用 key 引用（工程化）

*   模板中不写文案，写 key，渲染时再查语言资源
    

**优点**：复用语言资源、统一治理   **缺点**：模板引擎 + i18n 渲染链更复杂

---

## 5.5 格式本地化（时间/数字/货币）方案

### 方案 L1：前端统一格式化（推荐）

*   前端根据 locale 用标准库/Intl API 格式化
    
*   后端传“原始值”（timestamp、number、currency code）
    

**优点**：多端一致、后端简单   **缺点**：导出/PDF 若在后端生成仍要后端处理

### 方案 L2：后端统一格式化（用于导出/服务端渲染）

*   报表/PDF/邮件由后端格式化输出
    

**优点**：适合“后端直出”   **缺点**：后端要维护更多地区规则

---

## 6. 推荐的最小可行落地（MVP）与升级路线

### MVP（最快交付、风险低）

1.  前端 UI 全量 key 化 + 语言包（F1）
    
2.  后端错误/提示统一 `error_code + message_key + params`（B1）
    
3.  系统内置枚举/字段名等：用语言包管理（先不落 DB i18n）
    
4.  时间/数字格式：前端统一格式化（L1）
    
5.  通知：先做“按语言分模板版本”（N1）
    

### 扩展（规模化/运营化）

1.  语言包远端化 + 版本/灰度（F2）
    
2.  引入 DB i18n（翻译表 D1）管理系统元数据/运营文案
    
3.  网关/BFF 统一渲染（B3）提升一致性
    
4.  用户自定义内容提供“可选翻译副本”能力（C 类增强）
    

---

## 7. 你可以直接拿去做需求验收的 Checklist

*   [ ] 是否定义了 locale 决策链与兜底策略
    
*   [ ] UI 文案是否全部 key 化（无硬编码中文/英文）
    
*   [ ] API 是否提供稳定 
    
*   [ ] 通知/导出是否能按 locale 输出
    
*   [ ] 时间/数字/货币/单位是否符合地区习惯
    
*   [ ] DB/配置中的系统内置名称/模板是否有可扩展的多语言存储方案
    
*   [ ] 是否具备翻译资源的版本管理、缓存与灰度能力
    
*   [ ] 是否能监控“缺失翻译 key”的比例与告警
