# 3、搜索框查询

查询的内容是前端通过调用后端接口后查询得到，且查询内容会根据当前语言值返回目标语言，那么后端得到前端传入的搜索框内容后，后端应该使用哪种语言进行搜索？

![](https://alidocs.dingtalk.com/core/api/resources/img/5eecdaf48460cde5a0902744888301d00d07c15d573fa25a75b8339e1c4c2483036d8f39fb4ecebe65a117e969287064b61eb061b43d3b7107d7b330137b452e51043d6ec2687337cc090933aaba7db420fc8b3d85517d41a900dfd662445084?tmpCode=2ceae2f9-5571-4271-a75f-722a62e06b31)

**分析：**

*   多语言文本匹配：后端需根据请求头或参数中的 `locale`（当前语言），动态映射并查询数据库中对应的语言字段（如  { "deviceName": { "zh\_CN": "设备 1", "en\_US": "Device 1" } }），后端根据当前当前语言匹配查询字段对应的语言值。
    
*   枚举/字典值处理：对于“状态”、“类型”等基于后端 Code（代码值）存储的枚举字段，前端传递的可能是翻译后的文本（如“已完成”）。后端需先通过多语言字典映射表将输入文本反查为对应的 Code（如 `FINISHED`），再对 Code 字段进行精确匹配查询；若前端直接传递 Code，则直接匹配。

## 7.2 时区策略

### 7.2.1 时区设置

*   租户创建时需要管理员设置默认时区
    
    *   前端的所有时间基于租户时区转换、传递给后端为UTC时间
        
    *   后端统计服务等入库时间格式为UTC、
        
*   租户创建时需要管理员设置默认语言，该设置**不影响前端界面显示语言**。
    
    *   租户语言仅用于后端处理与该租户相关的告警、审计等入库信息的文本翻译，确保生成内容的语言一致性。
        
    *   系统审计
        
    *   租户审计
        
*   **边端设备时区与租户时区保持一致**
    
*   前端界面语言始终以浏览器设置为准，与租户语言无绑定关系
    

### 7.2.2 租户时区的必要性

*   所有服务端时间存储和计算均采用 **UTC 时间**，但租户必须配置其所在时区（如东八区）。
    
*   主要用于设备统计数据的“天”维度划分：例如中国租户设为 UTC+8，则统计服务将以 UTC+8 的 00:00 作为一天的起点，而非 UTC 的 00:00。
    
*   若不依赖租户时区，跨时区设备的数据统计会出现“日期错位”，影响业务准确性。
    

### 7.2.3 前端时间展示与转换规则

*   用户在界面上操作的时间（如下拉框选择“8:00”）均指**租户时区对应的时间**，而非浏览器本地时间或 UTC。
    
*   前端在调用后端接口前，需将用户选择的租户时区时间转换为对应的 UTC 时间传入；后端返回的 UTC 时间也由前端根据租户时区还原为可读时间展示。
    
*   服务端不参与时间格式化，仅处理 UTC 时间，避免多层转换导致混乱。
    

### 7.2.4 语言与时区解耦

*   语言与时区为两个独立配置项，不可通过语言自动推断时区。例如用户使用中文界面，但租户可能位于 UTC-5 美国区域。
    
*   界面可同时显示当前语言（如“中文”）和租户时区偏移（如“UTC+8”），两者分别管理，互不影响。
    

### 7.2.5 前后端时间交互模式

*   **统一采用前端转换策略**
    
    *   所有时间字段在前后端交互中均以 UTC 格式传输，**时间的加减转换由前端负责**。
        
    *   前端在请求时将租户时区下的时间转为 UTC，在响应后将 UTC 时间转回租户时区进行展示。
        
    *   后端无需解析时区上下文，简化逻辑并降低耦合。
        
*   **特殊场景：统计服务的时区处理**
    
    *   统计服务需基于租户时区确定每日数据切片的起止点（如 UTC+8 租户的“今日”从 UTC 时间 16:00 开始）。
        
    *   该逻辑由后端根据租户配置动态计算，**是唯一需要在服务端处理时区偏移的场景**
        

### 7.2.6 时区推荐方案：“存储统一基准（UTC），展示跟随租户”

*   **租户时区展示：用户登陆后，**++**页面上需要展示租户当前时区信息**++**，该时区不可更改**
    
*   **边端时区：可以更改，更改后需要通知租户，如果时区不一致会产生告警发送给边端（对时操作）。**
    
*   **云端后台服务和云端界面以租户时区为准。**
    
*   **尽量避免边端设备和租户时区不一致的情况，如果需要则创建新租户绑定该设备。**

# 8、组态工具图形画面翻译

**界面翻译范围：**顶部导航栏、左侧图元列表、右侧属性栏、右键菜单、画布内的文本

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/pLdn55X5XG0yWno8/img/df4b44ec-3691-4cfb-b988-828305b379a3.png)

**1、双重语境**：既包含“编辑态”（配置界面时的提示、属性名、图元信息等），也包含“浏览态”（最终用户看到的监控画面）。

**2、动态绑定**：大量文本不是写死的，而是绑定到实时数据库变量、告警代码或外部数据源。

**3、用户自定义**：画布上放置的文本框、图元、图表等，这些内容需要被提取并支持多语言。

**4、高性能要求**：浏览态翻译不能阻塞渲染循环，需避免频繁的 DOM 操作或重绘。

**5、图元内的文字：**若为编辑内容，应纳入翻译体系；建议**图片尽量无文字**，必要时通过叠加文本层实现可翻译性。

**6、词条的抽取和翻译**，可在组态工具画面json里添加多语言字段，由脚本统一抽取至语言包。或者支持单个画面文件内嵌多语言字段，避免维护多套画面文件带来的同步问题。渲染时动态替换 Json 文件中的文本节点，基于当前语言调用翻译方法完成展示，不修改原始文件内容。保持版本一致。

## 1、词条抽取（Key-Value）

后端定义的静态值或代码内写死的值。（代码、配置文件）

## 2、数据库Code关联翻译

通过业务字段中的 code（固定枚举文本，如状态、类型等）关联统一的多语言字典表（code + locale + value），实现结构化业务文本的国际化管理；

对于简单或低频场景，也可以使用 code-value 的 JSON 映射作为轻量级替代方案。（数据库）

## 3、JSON字段扩展法

为每行数据增加一个包含多语言版本的JSON字段，{ "deviceName": { "zh\_CN": "设备 1", "en\_US": "Device 1" } }，适用于用户自定义输入内容的翻译存储。（数据库）
