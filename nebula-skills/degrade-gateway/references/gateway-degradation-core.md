# Gateway 退化核心说明

## 这类任务的本质
这不是普通“删文件”，而是一次有前提的退场治理：
- 旧接口必须已经下线
- 现行网关链路必须已可独立运行
- 旧兼容层、旧 API、旧测试不再提供真实保护，只提供误导

所以重点不是“删得快”，而是“删得有证据”。

## 典型退化对象
1. 统一版本策略层
   - `gateway-version-policy.ts`
   - `gateway-executor.ts`
   - `executeWithVersionFallback`
2. 兼容壳方法
   - `loginV2 -> login`
   - `getPageV2 -> getPage`
3. 已下线旧 API 文件
   - `auth.api.ts`
   - `role.api.ts`
4. 临时兜底
   - `temp-v1-menu.ts`
   - 旧 mock 数据
5. 旧测试
   - fallback 顺序测试
   - 旧策略 mock
   - “失败后切到下一版本”的断言

## 决策原则
### 保留
- 仍有真实 import
- 仍承载现行协议转换
- 仍承担稳定类型映射

### 删除
- 只做内部转发
- 只为旧版本存在
- 只在测试里自我证明
- 仓内无任何真实消费方

## 推荐验证顺序
1. 先检索残留关键词
2. 再跑定向测试
3. 最后跑 `type-check`

不要反过来先删再猜。

## 为什么这是更新型 skill
这个 skill 不是从 0 增加一个新机制，而是基于“旧链路已经失效”的前提，把现有仓库里的历史兼容层退场。

因此最适合的示例组织方式不是“新增模板”，而是：
- `[[../template/before]]`
- `[[../template/after]]`

这样更容易让维护者看清：
- 退化前有哪些误导性残留
- 退化后哪些文件、入口、测试已经消失

## 为什么通常不拆成父 skill + 子 skill
这类退化动作的判断前提高度共享：
- 旧版本是否真的下线
- 哪些引用是真实引用
- 哪些测试已经失真

如果拆成多个子 skill，每个子 skill 都要重复建立同一套事实盘点，收益很低，维护成本更高。对 nebula 这类高耦合网关退化场景，更适合一个组合 skill。

## 为什么 before/after 优先于新增型模板
对这类任务来说，人类更关心的是：
1. 退化前有哪些典型坏味道
2. 退化后目标状态长什么样
3. 哪些删除动作可以联动进行

所以 `before/after` 比一个抽象新增模板更有解释力，也更适合复盘真实会话经验。
