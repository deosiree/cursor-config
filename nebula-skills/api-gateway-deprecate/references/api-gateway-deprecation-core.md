# API 网关旧兼容层退化说明

## 为什么退化也必须看契约
只按文件名删，会误伤两类内容：
1. 名字看起来旧，但其实还对应现行契约的接口或类型
2. 只是命名不一致，真正需要的是重命名与收口，不是删除

## 固定退化顺序
1. 盘点兼容层引用
2. 用契约判边
3. 删除旧版本细节与兼容壳
4. 收口业务调用
5. 删除旧 API、旧测试、旧 mock
6. 验证残留

## 典型退化对象
- `gateway-version-policy.ts`
- `gateway-executor.ts`
- `executeWithVersionFallback`
- `loginV2` 这类历史兼容壳
- 无引用旧 `*.api.ts`
- 临时兜底文件，如 `temp-v1-menu.ts`
- 只验证 fallback 的旧测试

## 删除 vs 重命名
### 适合删除
- 契约中已无对应项，且仓内无真实消费方
- 只服务已下线版本策略
- 只做内部转发，不承担现行映射职责

### 适合重命名收口
- 契约中仍有现行对应项
- 只是仓内命名仍带旧版本影子
- 仍承担现行 DTO -> stable 转换职责

## commit 粒度
skill 给完整路径，但不强制一次做完。
推荐按阶段提交：
- commit 1：删旧兼容壳并收口业务调用
- commit 2：删旧 API 与旧测试
- commit 3：清理命名、注释与残留
