## 文档目标

本文用于定义 `apex_dev` 与 `microfb` 后续权限体系的统一退化方案。

设计原则已经明确：

- 不考虑兼容旧链路
- 可以激进删除
- 允许先拷贝当前版本、必要时安全回滚，再按 UI 与 API 行为重建
- 最终整体迁移到“新链路”
- 废弃旧动作注册驱动方案与其配套解析链路

本文不是现状说明，而是目标方案与执行边界说明。

## 1. 结论先行

后续权限体系只保留两层真相源：

1. 前端声明真相源：`permission-meta`
2. 运行时消费真相源：`v-hasPerm` / `PermTabs` / `PermTabPane`

菜单管理中的功能项绑定，不再依赖 `perm -> gatewayAction -> api -> route` 的动作注册链路，而改为：

- 直接基于 `permissionMetaMap` 生成前端功能项候选
- 直接基于后端菜单树中的 FUNCTION 节点做 JOIN
- 继续展示 `linked / frontend_only / backend_only`

因此，`src/permissions/registry-route-action` 目录及其相关旧链路，原则上整体废弃。

## 2. 目标架构

### 2.1 保留的能力

以下能力继续保留，并视为未来标准方案：

- `permission-meta`
- `RegistrySource.permissionMetaMap`
- `v-hasPerm`
- `permission-guard`
- `PermTabs`
- `PermTabPane`
- 菜单管理中的功能项绑定 UI
- 菜单功能项配置中的三态显示：
  - `linked`
  - `frontend_only`
  - `backend_only`

### 2.2 明确废弃的能力

以下能力整体废弃，不再保留兼容层：

- `page-action-registry`
- `runtime-permission-resolver`
- `binding-registry-snapshot` 中基于 `functions` 的上送与消费
- 依赖 `gatewayActionBindings + apiMeta + actions` 才能生成功能项候选的旧模式
- `confirmPerm`
- “动作注册驱动”的租户旧方案

### 2.3 保留但降级定位的能力

以下能力可以保留，但定位需要收缩：

- `page-route-registry`

它不再属于“权限动作解析链路”的一部分，只作为“页面路由候选来源”服务菜单管理中的 PAGE 绑定。

换句话说：

- 页面路由注册可保留
- 页面动作注册整体删除

## 3. 新链路定义

### 3.1 前端声明层

每个具备权限控制的模块，都应有自己的 `permission-meta` 文件，至少声明：

- `perm`
- `label`
- `route`
- `component`
- `apis`

按需声明：

- `buttons`
- `tabClicks`
- `aliases`

`gatewayActions` 不再作为新链路的核心字段。

如果某些模块仍保留该字段，只视为迁移中间态，不再新增依赖。

### 3.2 组件消费层

前端页面统一只使用两种方式：

- 按钮、行操作、工具栏、局部控件：`v-hasPerm`
- Tab 容器单元：`PermTabPane`

不再新增任何基于 `routePath + perm` 的运行时指令。

因此：

- `confirmPerm` 直接删除
- 不再引入新的“二次权限解释器”

### 3.3 菜单管理绑定层

菜单管理中的功能项候选不再来自 `page-action-registry`，而改为直接由以下两部分构成：

1. 前端候选：当前页面对应的 `permissionMetaMap`
2. 后端候选：当前页面下的 FUNCTION 节点

JOIN 规则改为：

- 以 `perm` 为主键直接对齐
- 前端 API 直接读取 `permissionMeta.apis`
- 后端 API 直接读取 FUNCTION 节点上的 `apis`
- 不再经过 `gatewayAction -> apiKeys -> apiMeta` 中转

三态仍然保留：

- `linked`：前后端都存在同一 `perm`
- `frontend_only`：前端已声明，但后端 FUNCTION 节点不存在
- `backend_only`：后端 FUNCTION 节点存在，但前端未声明

## 4. `apex_dev` 迁移方案

### 4.1 目标

`apex_dev` 是主迁移对象，目标是彻底删除旧权限动作链路，把所有模块逐步收口到：

- `permission-meta`
- `permissionMetaMap`
- `v-hasPerm` / `PermTabPane`
- 菜单管理直接读取 `permission-meta`

### 4.2 需要整体删除的目录与文件范围

原则上以下目录整体删除：

- `apex_dev/src/permissions/registry-route-action`

包括但不限于：

- `page-action-registry.ts`
- `runtime-permission-resolver.ts`
- `binding-registry-snapshot.ts`
- 目录下相关模型、方法、变量、辅助函数
- 该目录对应单测

配套删除或重写的引用点包括但不限于：

- `apex_dev/src/plugins/qiankun/lifecycle.ts` 中对 `buildBindingRegistrySnapshot` 的依赖
- `apex_dev/src/views/system/menu/model/binding/menu-type-binding.registry.ts` 中对 `page-action-registry` 的依赖
- `apex_dev/src/directive/confirmPerm/index.ts`
- `apex_dev/src/views/tenant/__tests__/confirmPerm.test.ts`
- `apex_dev/src/views/tenant/__tests__/runtime-permission-resolver.test.ts`
- `apex_dev/src/gateways/tenant/__tests__/tenant.gateway.test.ts` 中对 runtime permission resolver 的 mock 依赖

### 4.3 需要退场的数据模型

以下模型或等价概念应整体退出：

- `RegisteredPageAction`
- `RegisteredPageActionEntry`
- `RegisteredPageActionBindingRow`
- `RuntimePermissionResult`
- 与 `resolveByperm / resolveByGatewayAction` 相关的 reason 枚举、映射函数、辅助函数
- 任何为 `functions snapshot` 上送服务的结构体

### 4.4 菜单功能项配置如何改造

`menu-type-binding.registry.ts` 需要改造为新模型：

#### PAGE 类型

- 仍可继续使用 `page-route-registry`
- 只负责“页面路由候选”
- 不参与功能项动作解析

#### FUNCTION 类型

直接由以下来源构建：

1. 当前页面 route 对应模块的 `permissionMetaMap`
2. 当前页面节点下的 FUNCTION 子节点

前端候选行字段由 `permission-meta` 直接给出：

- `perm`
- `label`
- `route`
- `component`
- `apis`

不再要求：

- `gatewayAction`
- `actions`
- `gatewayActionBindings`
- `apiMeta`

### 4.5 三态显示必须恢复

当前功能项配置虽然内部仍有：

- `linked`
- `frontend_only`
- `backend_only`

但 UI 没有稳定展示，这是不可接受的。

新方案要求把三态显式展示回功能项配置界面，用于快速判断：

- 前端声明是否缺失
- 后端菜单节点是否缺失
- 是否已完成对齐

建议最少提供：

- 状态列
- 状态筛选
- 明确中文文案

推荐文案：

- `已关联`
- `仅前端`
- `仅后端`

### 4.6 租户模块旧方案如何退出

租户模块当前是旧动作注册驱动的代表模块。

这里不做兼容迁移，而采用“回滚 + 重建”策略：

1. 允许先拷贝当前版本作为参考基线
2. 若历史旧版本更容易识别真实 UI 交互与 API，可安全回滚到旧版本
3. 基于回滚后识别出的真实交互与 API，重新建立 `tenant.permission-meta.ts`
4. 把页面里的权限消费改成：
   - `v-hasPerm`
   - 常量化权限码
5. 删除当前版本中为旧动作注册链路服务的租户权限中间层

最终目标不是“修补 tenant.actions”，而是彻底取消其作为权限主链路的存在意义。

## 5. `microfb` 迁移方案

### 5.1 定位

`microfb` 当前没有 `registry-route-action` 这一整套旧链路负担，主要只有：

- `v-hasPerm`
- `hasAuth`
- `permission bypass`

因此 `microfb` 不属于“删除旧动作注册链路”的主战场，但必须纳入统一方案，避免未来长出第二套模型。

### 5.2 对 `microfb` 的要求

`microfb` 不再强制直接复用 `apex_dev` 的 `permission-meta / permissionMetaMap` 固定模型。

后续若 `microfb` 需要接入前端声明、菜单绑定或跨应用上送能力，允许采用一个更轻量、更易扩展的注册中心模型，统一命名为：

- `micro-registry`

该模型用于承载原先 `micro-app-binding-registry` 一类能力，但不再强调重型、固定字段结构，而是允许使用可扩展对象形态，例如：

```ts
type MicroRegistryRecord = {
  [key: string]: unknown;
};
```

设计约束变更为：

- 名称统一收敛为 `micro-registry`
- 结构允许使用 `[key: string]: unknown`
- 可以按模块、页面、功能点逐步扩展字段
- 只要求能稳定支撑：
  - 前端权限声明
  - 菜单绑定候选生成
  - 跨应用上送或聚合

但仍然不允许把 `apex_dev` 当前准备删除的以下能力重新复制到 `microfb`：

- `page-action-registry`
- `runtime-permission-resolver`
- `confirmPerm`
- `functions snapshot`
- `actions + gatewayActionBindings + apiMeta` 驱动功能项候选

### 5.3 与 `apex_dev` 的统一边界

两边未来统一原则是：

- 页面显隐模型一致
- 权限声明语义一致
- `microfb` 可以通过 `micro-registry` 表达自身元数据
- 菜单功能项绑定若需要跨应用聚合，聚合的应是“权限声明语义”，而不是强制共享完全相同的字段模型

不再允许：

- `apex_dev` 走一套 registry-action 模型
- `microfb` 再走另一套与 `micro-registry` 脱节的临时散装模型

统一之后，`microfb` 只会比 `apex_dev` 少“菜单配置复杂度”，不会再多出一套额外心智。

## 6. Snapshot 与上送策略调整

### 6.1 旧策略废弃

旧策略中，`binding-registry-snapshot` 会上送：

- `routes`
- `functions`
- `permissionMeta`

其中 `functions` 是基于 `page-action-registry` 解析出来的中间产物。

这部分整体废弃。

### 6.2 新策略

如果仍需要主应用聚合前端声明，则只上送：

- `routes`
- `permissionMeta`

不再上送：

- `functions`
- 基于 `gatewayAction` 推导出来的 API 结果

主应用若要构建 FUNCTION 候选，应直接使用：

- 页面 route
- 权限元数据中的 `route`
- 权限元数据中的 `apis`

## 7. 对“用户页和租户页直接写字符串权限”的定性

以下现象不视为需要废弃：

- 用户页仍有很多 `v-hasPerm="'sys:xxx:yyy'"`
- 租户页仍有很多 `v-hasPerm="'sys:xxx:yyy'"`
- 这些权限点还没有统一 `permission-meta`

定性应改为：

- 这不是旧链路
- 这是“尚未完成元数据收口”的中间态

后续改造应做的是：

- 把这些权限点补齐到 `permission-meta`
- 把视图中的原始字符串逐步替换为常量

而不是把 `v-hasPerm` 本身视为待删除能力。

## 8. `confirmPerm` 的最终处理

`confirmPerm` 已明确进入删除名单。

删除理由已经充分：

- 未全局注册
- 无业务使用点
- 与 `v-hasPerm` 重叠
- 引入额外 routePath 心智
- 强依赖已决定删除的 runtime permission resolver

因此本次方案中：

- 删除指令实现
- 删除相关测试
- 删除所有注释、README、文档中的推荐描述

不保留兼容别名。

## 9. 风险与迁移顺序

### 9.1 风险

本方案最主要风险有三类：

1. 菜单功能项配置在删除旧解析链路后，候选数据暂时不完整
2. 租户模块回滚后，可能出现 UI 行为与当前版本短期偏差
3. 主应用若仍依赖 `functions snapshot`，会出现聚合数据缺口

### 9.2 处理方式

处理策略是“先重建新链路，再删旧链路调用点”，顺序如下：

1. 先在菜单绑定层实现“直接基于 `permission-meta` 的 FUNCTION 候选生成”
2. 恢复三态显示
3. 给角色、用户、租户补齐或重建 `permission-meta`
4. 调整 qiankun 上送，只保留 `routes + permissionMeta`
5. 删除 `registry-route-action`
6. 删除 `confirmPerm`
7. 删除旧单测并补新单测

### 9.3 回滚策略

允许按模块执行：

1. 保留当前分支或建立备份分支
2. 回滚到更容易识别真实交互和 API 的版本
3. 只提炼：
   - UI 交互
   - API 列表
   - 实际权限落点
4. 在当前主线以新方案重建

这不是为了恢复旧链路，而是为了给新链路提供干净的行为基线。

## 10. 测试策略

### 10.1 删除的测试

以下测试应随旧链路一起删除：

- `page-action-registry` 相关测试
- `runtime-permission-resolver` 相关测试
- `binding-registry-snapshot` 中依赖 `functions` 的测试
- `confirmPerm` 相关测试

### 10.2 保留或新增的测试

后续测试重点应转为：

- `hasPerm` 指令测试
- `permission-guard` 测试
- `PermTabs / PermTabPane` 测试
- `permission-meta-index` 测试
- 菜单功能项配置基于 `permission-meta` 的 JOIN 测试
- 三态显示测试

特别是功能项配置，应新增覆盖：

- 前端已声明、后端不存在
- 后端存在、前端未声明
- 前后端同 perm 已绑定

## 11. 最终目标态

最终目标态如下：

- `apex_dev` 不再存在 `registry-route-action`
- `microfb` 不会接入任何同类旧动作注册链路
- 菜单管理的功能项候选只依赖 `permission-meta`
- 页面显隐只依赖 `v-hasPerm / PermTabs`
- 功能项配置能稳定显示：
  - `已绑定`
  - `仅前端声明`
  - `仅后端存在`
- 所有模块逐步收口到统一权限声明模型

## 12. 一句话定案

本次退化方案的本质不是“修旧链路”，而是“彻底删除 `perm -> gatewayAction -> api -> route` 这套动作注册中间层，只保留 `permission-meta` 作为前端权限声明真相源，并让菜单管理直接消费它”。
