# 菜单树真相源边界纪律

## Overview
权限管理、菜单管理和 qiankun 聚合这条链里，最容易漂移的地方是“谁是真相源”。本 skill 用来先钉死边界：

1. 菜单树/后端 `menu` 表是业务真相源。
2. 注册中心是菜单树的扩展视图。
3. 基座总注册中心是增强索引，不是第二真相源。

## 适用场景
1. 想把基座聚合注册中心接进菜单管理。
2. 想从菜单树和前端注册中心同时生成候选项。
3. 排查“菜单绑定已改，但前端行为没变”这类问题。
4. 团队开始把注册中心当成独立配置源使用。

## 真相源定义
1. 菜单树负责：
- `id / parentId / type / name`
- `routePath / routeName / component`
- `perm`

2. 注册中心负责补充：
- `componentDisplayPath`
- `componentStoragePath`
- `gatewayAction`
- `apiPath`
- `fullRoutePath`
- 其它前端扩展字段

3. 基座总注册中心负责：
- 汇总各微服务 snapshot
- 与菜单树关联成增强索引
- 不直接写业务绑定结果

## 可空边界与强约束边界
1. 后端菜单树字段是业务真相源，但不代表每个字段在开发阶段都已补齐。
2. 来自后端 `menu` 表、且后续仍允许人工增删改查补齐的字段，可以为空后再编辑：
- `menu.name`
- `menu.routePath`
- `menu.routeName`
- `menu.component`
- `menu.perm`
3. 前端注册中心自己的持久化契约属于强约束，不应以“后端当前还没补齐”为理由放宽：
- `routes.ts` 中页面路由与组件路径映射
- 页面动作注册中心中的 `actionKey -> gatewayAction -> apiPath`
- snapshot 输出字段契约
4. 判断规则：
- 后端传来的业务字段：允许空值进入“可编辑态”
- 前端本地注册事实：缺失即暴露错误，不做静默兜底

## 链路业务逻辑（状态机）
### 1. 菜单树加载阶段
- 系统先读取菜单树，这是当前绑定真相。

### 2. 注册中心补充阶段
- 微服务本地注册中心补充前端实现信息。
- 基座汇总 snapshot，形成菜单树增强索引。

### 3. 菜单管理展示阶段
- 菜单管理展示的是“菜单树 + 前端扩展”的增强视图。
- 但用户确认保存时，最终仍只写菜单树字段。

### 4. 运行时消费阶段
- 页面、resolver、gateway 都读菜单树真相和注册中心扩展。
- 不得把运行时结果反向写成新的配置。

### 5. 变更生效阶段
- 菜单树一旦更新，刷新菜单缓存后成为新的唯一真相。
- 注册中心只重新参与解析，不单独生效。

## 判断标准
如果一份数据满足以下任一情况，它不是新真相源：
1. 不能单独决定最终持久化结果。
2. 必须依赖菜单树节点才能定位回写目标。
3. 只提供前端展示或解析补充信息。

## 常见错误
1. 把基座聚合 store 当作新的可编辑配置源。
2. 在注册中心里保存“当前绑定结果”。
3. 修改绑定后只更新前端快照，不更新菜单树。
4. 用 UI 本地状态长期缓存业务绑定结果。
