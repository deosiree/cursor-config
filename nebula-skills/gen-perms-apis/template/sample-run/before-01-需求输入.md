# before-01：需求输入（真实历史样本）

> 本文件沉淀自 2026-06-03 会话。供人类阅读和 agent few-shot 参考。
> 对应 write-skill 规范中的「真实历史样本型模板 — 基于 RED 写 before」。

## 原始需求

```text
下述模块中，所有消费了api的地方都需要配置功能项权限点，设计修改源码的方案，
以及如何配置菜单管理的权限点和apis（输出到docs/menu）

首页：只配置一个权限点，并且记录权限点对应的所有apis
租户管理：检查是否还有没配置权限点的，但使用了apis的
个人中心：检查是否还有没配置权限点的，但使用了apis的
用户管理：检查是否还有没配置权限点的，但使用了apis的
角色管理：检查是否还有没配置权限点的，但使用了apis的
安全配置：只配置2个权限点（安全配置、会话配置），并且记录权限点对应的所有apis
菜单管理：检查是否还有没配置权限点的，但使用了apis的
```

## 需求特征分析

| 特征 | 说明 |
|------|------|
| 范围 | 7 个模块，默认为 apex_dev |
| 类型 | 盘点 + 设计 + 改码 + 菜单配置（全流程） |
| 模糊点 | "检查是否还有"意味着不确认当前状态，需要先盘点 |
| 边界约束 | 仅输出到 docs/menu |

## 关键决策点（事后确认）

在 skill 设计中应标记为"必须人工确认"的节点：

1. **个人中心权限策略**：登录即可访问 vs 建 perm vs 按操作拆分
2. **租户管理跨模块 API**：并入现有 perm vs 新建独立 perm vs 复用其他模块 perm
3. **loginSetting 处理**：direct/no-auth 豁免 → hidden page 收敛
4. **个人中心 page 节点**：挂在可见目录 vs hidden page

## 补充约束

```text
1. loginSetting 走 direct 前缀 → 不建功能项 perm，收敛到隐藏页「状态管理」
2. 个人中心 page 节点存到隐藏页「个人中心」
3. 仅改 apex_dev，不动 opsdeck
4. 源码改动：最小化 + 集中式（父组件优先）
```

## 对 skill 设计的启示

- 用户输入通常不完整，需要多轮确认
- 权限粒度决策不能由 agent 自行裁量
- `targetRepo` 应作为可选入参，默认 apex_dev
- "检查是否还有" = 先盘点再设计
