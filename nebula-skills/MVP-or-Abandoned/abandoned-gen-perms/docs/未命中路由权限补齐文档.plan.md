## 文档结构（MVP）

- `## 说明`：声明覆盖范围为全部未命中路由，且行号同时提供“源码文件行号 + 业务行说明”。
- `## 路由清单`：逐路由分节（12 条）。
- 每条路由使用稳定层级键组织：
  - `## [路由]`：路由级主标题（如 `## /Apex/system/apiManage`）。
  - 该路由下固定输出：
    - **表1 路由组件表（总表）**：`| 路由 | 对应组件 | 组件路径 |`
    - **表2 组件权限点表**（每个组件下可有多个权限点）：`| 权限点(按现有风格设计) | 对应哪一行(源码行号+业务行) | 对应什么代码中 |`
  - 对路由下每个权限点继续下钻：
    - `### [权限点]`（如 `### sys:api:delete`）
    - **表3 权限点 API 表**（该权限点下可有多条 API）：`| apiMethod | apiUrl | description |`
- 关系约束：
  - 表2中的每个权限点必须在同一路由节下存在对应 `### [权限点]` 小节与表3。
  - 表3中的 API 不可跨路由复用到其他路由节，避免引用歧义。

## 权限命名与映射规则

- 命名风格对齐现有：`sys:<module>:<action>`（如 `sys:user:add`）。
- `apiUrl` 统一使用业务路径，不带 `/direct`、`/forward`、`{direct|forward}` 前缀。
- `description` 使用 Swagger 接口可读描述：优先 `description`，缺失回退 `summary`；仍缺失时标注“swagger 未提供接口描述”。
- 仅路由跳转、无 API 的操作位也要列入表2；其表3写“当前无后端 API 调用”。

## 自检

- 每条路由都必须有 `## [路由]` 主节，且至少包含表1与表2。
- 表2 每条权限点记录都必须有“源码行号 + 业务行说明 + 代码位置说明”。
- 每个权限点都必须有 `### [权限点]` 子节与对应表3；有 API 则列 `apiMethod/apiUrl/description`，无 API 则明确标注原因。
- 术语与命名风格统一，不与现有权限前缀冲突。
