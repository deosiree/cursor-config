# 单一写点与 fail-fast 约束

## Overview
本 skill 不是业务功能 skill，而是实现任何权限/菜单/注册中心改造前都应先对齐的工程纪律：

1. 单一写点
2. 只读派生
3. fail-fast
4. 不做 silent fallback

适合在真正改代码前先执行，用来判断现有实现是否已经漂移。

## 适用场景
1. 同一份数据在多个组件、store、resolver、gateway 中重复维护。
2. 缺字段时用了 `?.`、空串、默认值、`try-catch` 静默吞错。
3. UI、注册中心、提交层都在各自拼字段。
4. 旧 fallback 太多，准备先瘦身再重构。

## 核心原则
1. 一份业务含义只允许一个写点。
2. 其它层只能做只读派生，不能回写。
3. 缺少必要字段时直接报错。
4. 宁可早暴露问题，也不要把错误埋到运行时深处。

## 链路业务逻辑（状态机）
### 1. 写点确认阶段
- 先回答：这份数据最终应该由谁维护？
- 如果回答不唯一，先停下来收口写点。

### 2. 派生确认阶段
- 除写点外的其它层，只能从写点读取并派生展示/索引/运行时结果。

### 3. 校验阶段
- 派生时发现必要字段缺失，应立即失败并暴露。
- 不允许用空串、可选链、默认兜底掩盖缺口。

### 4. 提交阶段
- 真正保存时只写回原始写点，不写第二份业务结果。

## 建议检查项
1. 路由-组件、动作-gateway、gateway-API、菜单绑定是否各有且仅有一个写点。
2. 组件模板里是否还在手工拼展示字段。
3. store 和组件是否同时维护同一份业务状态。
4. 是否还存在“兼容旧逻辑所以两边都写”的情况。

## 常见反模式
1. UI 一份、registry 一份、submit 一份，各自维护同一个字段。
2. resolver 命不中时返回空对象继续往下跑。
3. gateway 遇到异常直接吞掉然后照常请求。
4. 菜单刷新前后同时维护本地影子状态。
