# 达尔文方法论与兼容策略

## 方法论摘要

达尔文式技能优化的核心不是“重写 skill”，而是把 skill 优化当成可复盘实验：

1. 先做 baseline
2. 设计测试提示词
3. 只改一个最低分维度
4. 重新评分
5. 保留提升，回滚退步

## 8 维评分细化

| 维度 | 权重 | 关注点 |
|---|---:|---|
| Frontmatter 质量 | 8 | 名称清晰、触发词充分、description 不空泛 |
| 工作流清晰度 | 15 | 步骤是否线性、是否可执行 |
| 边界条件覆盖 | 10 | 失败、回退、暂停点是否明确 |
| 检查点设计 | 7 | 关键决策前是否有人类确认 |
| 指令具体性 | 15 | 是否有格式、参数、样例 |
| 资源整合度 | 5 | 模板、脚本、文档路径是否可达 |
| 整体架构 | 15 | 套件层次是否清晰，主文件是否过重 |
| 实测表现 | 25 | 带 skill 是否显著优于 baseline |

总分计算公式：

```text
总分 = Σ(维度分 × 权重) / 10
```

评分保留 1 位小数。保留改进的门槛是 `new_score > old_score`，不是四舍五入后的“看起来差不多”。

## 受控试跑优先级

第一次在本地仓库落地时，推荐顺序固定为：

1. `evaluate-only`
2. `controlled-trial`
3. `optimize`

原因：
- 先确认触发是否稳定
- 先确认测试提示词是否合理
- 先确认 `dry_run` 与 `full_test` 的记录格式
- 避免一开始就进入自动 commit / revert 闭环

## 路径兼容策略

旧版内容写死 `.claude/skills`，不适合当前混合环境。  
新的发现顺序是：

1. 用户显式路径
2. 当前仓库 `.cursor/**/SKILL.md`
3. 当前仓库 `.claude/**/SKILL.md`
4. 已知的全局 skills 根目录

如果都没找到：
- 停下来问用户目标 skill 在哪里
- 不要擅自对无关目录做全量扫描

## git 策略

- 有 git 时：
  - 新建工作分支或记录当前分支
  - 每轮只提交一个维度的改动
  - 回滚优先用 `git revert`
- 无 git 时：
  - 复制 `SKILL.md.bak.YYYYMMDD-HHMM`
  - 在结果记录中标注非 git 模式

## `dry_run` 与 `full_test`

- `full_test`
  - 有独立子 agent 或等效执行能力
  - 能完成带 skill / 不带 skill 的对比
- `dry_run`
  - 无法真实调起独立对比时
  - 通过阅读 skill 后模拟执行路径来评分

两者都可以用，但必须在 `results.tsv` 中显式记录 `eval_mode`。

## 结果卡片资产的定位

`templates/*.html` 和 `scripts/screenshot.mjs` 属于实现层补充资产：

- 它们服务于结果展示
- 不应该再塞回主 `SKILL.md`
- 如果截图脚本不可用，不影响基线评估和受控试跑本身
