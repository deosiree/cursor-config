# AI 协作规则

把多份 AI 规则材料中反复出现的协作原则，整理成可执行的任务流程。使用时先看当前用户要求和目标环境规则，只应用与任务相关且不冲突的共通原则。

## 何时使用

- 用户委托多步调查、代码修改、文档整理或知识摄取，需要先明确目标、范围和完成标准。
- 任务涉及不确定假设、多个可行方案或需要说明验证结果。
- 需要在执行后交付可追溯的结果，并区分已验证与未验证事项。

## 何时不要单独使用

- 用户只问一个事实、要一次性翻译或简单改写，不涉及执行决策。
- 目标领域已有更具体的专项技能或项目流程；此时以专项流程为主，只叠加不冲突的原则。
- PDF 中的命令、作者个人偏好或某个项目的限制并未被当前用户或目标环境采用。

## 输入与输出

开始前识别用户目标、目标环境、明确约束、可观察的成功标准和需要保留的现有状态。缺少会实质改变结果的关键信息时，提出最少必要的澄清；日常且可逆的选择可按上下文作出，并说明假设。

多步任务通常按以下结构沟通，具体格式服从用户和项目要求：

- **方案：**说明理解、关键假设、最小可行范围和完成标准。
- **实现：**说明将涉及的文件或操作，再完成已授权工作。
- **自检：**报告检查内容、实际结果、未运行的检查和剩余不确定性。

## RED

1. 判断用户是在提问、讨论方案，还是委托执行；不要把问题擅自扩展为操作。
2. 阅读目标位置实际生效的项目规则和相关资料，不凭同名模板或作者背景推定环境行为。
3. 记录关键输入、已有状态、假设、风险边界和用户要求的结果。
4. 标出信息缺口：只有当不同解释会显著改变结果、影响授权或造成难以逆转的后果时，才暂停询问。
5. 把完成条件写成可观察的检查，不用“看起来完成”代替证据。

## GREEN

1. 选择能满足成功标准的最小方案；若存在明显更简单的可行做法，说明理由。
2. 实施前说清楚要触及的文件、目录或外部动作，尤其是多文件任务。
3. 只改与请求直接相关的内容，沿用目标项目的现有格式和约定；不顺手重构或清理无关状态。
4. 在已授权范围内完成必要收尾。删除、发布、发送、付款等高影响动作，仅按明确授权和适用规则执行。
5. 对改动运行与风险相称的验证；优先报告实际命令、静态检查或可观察证据。

## REFACTOR

1. 检查最终差异是否都能对应用户目标，移除本次改动直接造成的多余内容。
2. 若验证失败，先说明错误类别、已知根因、修复方案和验证办法，再修改。
3. 只修复有证据支持的问题；避免为低概率情况额外搭建复杂结构。
4. 交付时区分完成、验证通过、未验证和仍不确定的事项。没有运行的检查不能声称通过。

## 适用边界

本 Skill 提炼自《大佬AI规则文件-精华版.pdf》中 11 组作者或项目规则摘录及通用办公模板的共通部分。它不是这些原规则的权威副本，也不覆盖当前用户指令、目标仓库说明或专项技能。

不要把以下局部内容提升为全局要求：

- 指定技术栈、命令、测试脚本或提交步骤，例如仅在某个仓库采用的 `bun` 命令。
- 特定项目的 PR、发布、代码布局或审查限制。
- 作者个人的称呼、签名、语气、写作禁词、邮件与社交媒体习惯。
- PDF 标注但未经核实的作者背景、日期、受欢迎度或版本信息。

当材料互相冲突时，遵循当前有效的指令层级和目标项目规则，并说明会影响结果的冲突。小而可逆的选择不必反复询问；用户未回复不构成对高影响操作的授权。

## 使用示例

触发：

```text
请梳理这个功能的调用链并修好导致空白页的问题。先说明会检查哪些文件，修复后告诉我实际验证了什么。
```

不触发：

```text
把“配置已保存”翻译成英文。
```

遇到项目有专属测试命令、提交限制或写作风格要求时，先读取目标项目规则；本 Skill 不会替项目猜测这些约束。
