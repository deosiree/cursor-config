# 目标

在「已有语料但仍不够 / 要更严 / 不知道缺什么」时，用门禁报告与矩阵做缺口诊断，并给出可确认的阈值变更提案——**不自动改严**。

## 何时使用

- 用户说：不够深、再抬阈值、测集太少、只有单模块
- PASS 后仍要升档
- 父路由「缺口 / 升阈值」

## 何时不要使用

- 明确 FAIL 且已知修法 → 直接核验续跑
- 从 0 建场且接受默认阈值 → 走编排 intention

## 输入

- 最近一次门禁报告（stdout 或 `last-gate-report.txt`）
- 当前 `EVAL_GATES.md` 版本与阈值表
- `coverage-matrix.yaml` / `journeys-matrix.yaml`
- 用户期望（可选）：目标汉字、md 数、每旅程金标数

## 步骤

1. **读现状**  
   解析 PASS/FAIL 项：体积、md 数、旅程全绿、golden/split、截图。

2. **缺口分类**（写入短表）

   | 类型 | 信号 | 建议动作 |
   |------|------|----------|
   | 体积不足 | han &lt; MIN | 模块深挖 + 旅程加厚；禁垫字 |
   | 篇数不足 | md &lt; MIN | 补 FAQ/SOP/场景；禁复制粘贴改标题 |
   | 旅程缺口 | 矩阵非绿 / 缺模块切换 | 挖跨模块；补 handoff |
   | 金标不足 | test/runtime 低于阈 | 按 journey_id 补问答 |
   | 结构空洞 | 缺前置/失败/证据 | 按模板补节，不新开空文件 |
   | 阈值过松 | 用户主观要严 | 出提案，不直接改 |

3. **阈值提案表**（必须给人看）

   | 项 | 当前 | 提案 | 理由 | 风险 |
   |----|------|------|------|------|
   | MIN_VOLUME | … | … | … | 扩面成本 |
   | MIN_MD_FILES | … | … | … | … |
   | per-journey gold | … | … | … | … |

4. **人工门禁**  
   🔴 等人明确确认提案（或拒绝/改数字）。  
   - 确认 → 指导调用「落盘-门禁与看板」升 **版本号** 并改脚本常量 / EVAL_GATES  
   - 拒绝 → 保持旧阈值，仅输出内容侧扩面清单

5. **内容侧待办**（不升阈值时也要给）  
   按优先级列出：缺哪个模块 FAQ、缺哪条 journey、缺哪些金标 id。交给编排或对应 feature。

## 输出

- 缺口分类表
- 阈值提案表（含「不改」选项）
- 若已确认：版本 bump 说明（如 1.1.0 → 1.2.0）+ 待改文件列表
- 内容扩面待办（可勾选，但勾选 ≠ PASS）

## 失败分支

| 情况 | 动作 |
|------|------|
| 无门禁报告 | 先跑核验脚本再分析 |
| 用户要降阈值以「快速绿灯」 | 可提案，但须标明技术债；仍 🔴 |
| 提案与黑名单冲突（计入垫字） | 拒绝该项提案 |

## 反例

- 未确认就改 `MIN_VOLUME` 并声称「已对齐更严标准」
- 把「感觉少」写成 FAIL 项而不对照脚本
- 建议恢复 deprecated 垫字附录充量
