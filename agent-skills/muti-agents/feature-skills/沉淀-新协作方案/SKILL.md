# 沉淀新协作方案

## 任务

将真实且可复用的研发协作流程变成带明确输入、角色阶段和验收条件的注册方案。新增方案不只是一串模型名称，必须定义能力前提、传输、失败条件和人类控制点。

## 输入

- 用户提出的方案目标和需要解决的任务类型。
- 每阶段宿主、角色、模型、责任、交接输入/输出和退出条件。
- [Agent 注册表](../../assets/agents-registry.json)、[方案注册表](../../assets/schemes-registry.json)。
- [方案编写指南](../../references/scheme-authoring-guide.md)。
- 方案样本、脚本覆盖能力和客观回归检查。

## 流程

1. 询问目标问题、角色边界、串并行关系、隔离、执行模式和验收责任。
2. 逐一确认每个阶段的宿主已登记，模型和选项由用户提供或实测；未确认能力标为缺项。
3. 写出 ID、代码、名称、摘要、支持宿主、阶段、委派默认值、人工门禁和 forbidSilentDowngrade。
4. 用 🔴 CHECKPOINT 展示注册表差异、默认方案影响、脚本兼容情况和测试样例，等用户批准。
5. 获批后添加方案注册表项、快照样本和覆盖新方案的测试，运行相关回归。
6. 报告修改文件、测试输出和未验证限制；建议通过 Issue/PR 和 Darwin 复验完成治理。

## 输出

- 注册表候选对象及唯一 id、code。
- 阶段责任和每一阶段的可验证退出条件。
- 默认参数、用户覆盖范围、人工门禁及失败即停策略。
- 快照和带唯一 ID 的回归案例。
- 验证命令、真实结果与剩余风险。

## 边界

- 没有明确批准前不修改注册表，不改变 defaultSchemeId。
- 不为凑齐阶段而增加 Agent，不推测 provider 或 model 的当前能力。
- 不复制敏感任务内容进样本；用脱敏场景和客观检查。
- 新方案若针对批量 HTTP API 请求并发和模型路权，路由到 [多模型并发调度](../../../多模型并发调度/SKILL.md)，不放入本注册表。

## 示例

用户提议新增 S-02 作为 S-01 的备用模型路径。先收集备用宿主、触发切换条件、是否需用户确认、运行失败检测与回归用例。若备用模型的当前可用性未知，将其列为未验证并暂停在提案，不将其设为默认。
