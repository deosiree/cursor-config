# muti-agents

## 目标

把研发任务按研究、实现、审查等角色交给合适的 Agent，并保留人类对宿主、方案和外部委派的控制。先识别当前宿主，再读取登记能力和方案，不因工具缺失而静默换路。

## 何时使用

- 需要多个 Agent 在研发阶段按角色分工、交接上下文或独立复核。
- 需要复用已记录的分模型 Plan/Exec/Verify 方案。
- 需要跨机器发现支持状态，或为未登记宿主提出适配。
- 需要把已验证的 Agent 角色组合沉淀为可复用方案。

## 何时不要使用

- 用户要把大量独立请求分发到多个模型，以 HTTP API 并发和模型路权执行翻译、批量审查或测试时，使用兄弟 Skill [多模型并发调度](../多模型并发调度/SKILL.md)。它处理批处理 API 调度；本 Skill 处理研发过程中的 Agent 角色分工与委派。
- 任务只需当前 Agent 完成，且没有并行工作、独立审查或跨模型需求时，不创建无必要的委派。
- 仅询问模型价格、API 可用性或并发路权时，不触发本 Skill。

## 输入契约

开始前收集或从当前对话提取以下字段；缺少关键项时只询问缺少项：

| 字段 | 必需 | 说明 |
|---|---|---|
| task | 是 | 可独立验收的研发任务与完成定义 |
| currentAgent | 是 | 探测结果和用户确认的宿主名称 |
| targetAgent/model | 视方案 | 目标 Agent、模型及角色；不可推测能力 |
| plan | 视方案 | 已确认计划文件或明确范围 |
| constraints | 是 | 文件所有权、禁止操作、环境和凭据边界 |
| acceptance | 是 | 测试、静态检查和需要回报的证据 |
| approval | 是 | 是否授权本次外部委派及其具体范围 |

不要把密钥、令牌、个人路径或不相关对话放进委派简报。探测结果只能包含信号是否存在，不得输出环境变量原值。

## RED · 失败基线

| 失败信号 | 风险 | 安全处置 |
|---|---|---|
| 当前宿主未确认或探测结果为 unknown | 方案可能在错误宿主执行 | 停在宿主确认状态，不构造委派请求 |
| 注册表没有该宿主或适配能力未证实 | 子任务无法启动或选错传输 | 路由到 [新 Agent 适配 Loop](feature-skills/扩展-新Agent适配Loop/SKILL.md)，不登记猜测能力 |
| 缺少委派工具、CLI 或必要环境变量 | 任务会被错误地当作已派发 | 说明缺项并停止；不静默改成本地执行或其他通道 |
| 计划、所有权或验收条件缺失 | 子 Agent 可能改错范围或无法验收 | 补齐简报后重新过人工门禁 |
| 异步委派尚无完成通知 | 把启动误报成完成 | 等待宿主完成事件，不轮询 task_status；未完成时如实报告等待状态 |
| 子任务结果没有可核对证据 | 无法确认完成质量 | 主 Agent 对照差异、测试输出与验收项；未验证项单列 |
| 用户未授权本次委派 | 产生未批准的外部执行 | 停在 🔴 CHECKPOINT，等待明确确认 |

这里的安全处置是停止并说明下一步，不代表可自动尝试其他传输方式。

## 失败模式 fallback 表

“回退”指回到上一个有效决策状态或明确停止，不是自动换模型、换宿主或改为本地执行。

| 失败点 | 返回状态 | 可继续的条件 |
|---|---|---|
| 宿主探测不一致 | identify | 用户确认名称并有可核对的环境证据 |
| Agent 未登记 | capability → adapter | 完成适配提案并通过修改门禁 |
| 注册方案不存在或不支持当前宿主 | choose | 用户选择适配方案或当前 Agent 单独处理 |
| 当前会话没有所需委派工具 | capability | 恢复工具，或完成适配与烟雾验证 |
| ACP 进程报错或返回非零码 | dispatch → failed | 根因解决且用户重新确认同一范围 |
| 异步任务没有完成通知 | dispatch → waiting | 宿主发出完成或失败事件 |
| 改动超过文件所有权 | review → blocked | 用户审阅偏差并重新授权范围 |
| 验收命令失败 | review → failed | 根据失败证据修复并重新运行同一验收 |

每次回流都保留之前已确认的字段，只询问或重做失效部分。重新授权前不重复发送外部任务。

## 任务拆分与交接

只把能独立完成并检查的工作单元交给一个执行 Agent。拆分前先画清楚依赖与文件所有权：

- 前置调研、接口定义和测试夹具等有依赖关系的步骤按顺序交接。
- 文件集合互不重叠且结果可单独验收时才考虑并行；共享文件的写入任务串行。
- 需要独立复核时，审查者只读被测差异，不兼任实现者。
- 每个简报都写唯一责任人、写入路径、禁止动作、阻塞时如何回报。
- 不把整个对话转发给子 Agent；仅附完成任务所需的上下文和必要证据。

最小交接内容示例：

~~~text
任务：实现计划中的菜单状态映射
所有权：只允许写 src/menu/
禁止：提交、推送、改配置或修改其他目录
验收：npm test -- src/menu；回报完整文件清单与退出码
阻塞：缺少接口或环境时停止并报告，不扩大范围
~~~

## 验收判定

验证证据按来源分开记录，不将推测、旧运行结果或委派者摘要写成当前执行结果。

| 证据 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| 静态检查 | 文档、格式、链接或类型约束满足 | 运行逻辑正确或外部工具可用 |
| 自动化测试 | 被覆盖的行为通过本次测试 | 未覆盖路径、真实宿主通知可用 |
| DryRun/mock | 请求结构与测试桩的传输行为符合预期 | 真实委派已发送或已完成 |
| 完成通知与差异复核 | 子任务返回且改动可检查 | 验收命令全部通过，除非有结果证据 |

报告要注明执行环境、命令、退出状态和时间；跳过的检查写明原因。若测试本身修改了工作树，先检查产生的文件再判断是否属于任务范围。

## GREEN · 四步交互引导状态机

每步只在当前状态所需输入齐备后前进；记录状态和未满足项，避免跳过确认。

### 1. 识别并确认宿主

运行 scripts/detect-agent-env.mjs，读取 assets/agents-registry.json。报告探测到的宿主、平台、建议传输和信号布尔值；请用户确认“当前 Agent 是什么”。探测不到时让用户说明名称，不猜测。

### 2. 判定支持与能力

在注册表中精确匹配 id 和 status: supported。再检查该宿主当前会话实际可用的委派工具、CLI/MCP 通道、参数选项和异步完成机制。只有登记状态与实时能力都满足本任务时才继续；否则转到 [新 Agent 适配 Loop](feature-skills/扩展-新Agent适配Loop/SKILL.md)。

T3 Code 是 assets/agents-registry.json 中已登记的一个宿主适配器，当前注册传输为原生 MCP 与 ACP MCP 调用。能力检查须依据当前会话提供的 orchestrator_capabilities 及实际工具；适配器存在不等于本次调用一定可用。

### 3. 展示并选择方案

读取 assets/schemes-registry.json，按代码、角色阶段、目标模型、隔离和异步策略展示全部有效方案。首版 S-01 为 Plan（Gemini 4 Neon）→ Exec（GPT-6 Luna）→ 验收（Gemini 4 Neon）。询问用户选择一个方案、只执行单个 Agent，或进入 [新协作方案沉淀](feature-skills/沉淀-新协作方案/SKILL.md)；不得替用户选模型。

### 4. 确认、委派与验收

展示最终简报：任务、目标角色与模型、计划、写入范围、禁止事项、传输、隔离、执行模式、验收命令和风险。🔴 CHECKPOINT 等待对本次委派的明确授权。获得授权后按方案调用已验证通道；收到完成通知后由主 Agent 检查文件清单、差异、测试和静态检查，报告证据、失败项与未验证项。执行功能见 [T3 Code 分模型委派](feature-skills/执行-T3Code分模型委派/SKILL.md)。

### 状态转移摘要

| 状态 | 成功条件 | 下一状态 | 停止或回流 |
|---|---|---|---|
| identify | 探测结果已展示且人类确认宿主 | capability | 信息未知时留在本状态 |
| capability | 注册与当前会话工具均支持 | choose | 不支持时转适配 Loop |
| choose | 用户选择已登记方案 | checkpoint | 新方案需求转方案沉淀 |
| checkpoint | 授权范围覆盖当前委派 | dispatch-and-review | 无授权则停止，不发送请求 |

## 🔴 CHECKPOINT · 人工门禁

在下列动作之前先给出具体变更或执行预览，并等待用户明确同意：

- 调用另一个 Agent，或向外部宿主发送任务内容。
- 新建或修改适配器、注册表、委派脚本和方案资产。
- 执行可能改动仓库、创建分支、提交、推送、开 Issue/PR 或合并的操作。
- 发送包含用户数据、私有代码或敏感上下文的简报。

确认只覆盖被展示的宿主、任务、范围和动作。沉默、模糊回应或对另一项工作的授权不算本次确认。

## 反例黑名单

- 不把“注册表里有宿主”当成当前会话已具备执行工具。
- 不把子任务已创建、进入等待或收到文本回复当成代码已验收。
- 不用同模型、低能力模型或本地执行冒充目标 Agent。
- 不在不支持的宿主上静默降级，也不泄漏环境变量值。
- 不把批量 HTTP API 的并发调度误路由到本 Skill。
- 不要求用户粘贴凭据，不把凭据写入计划、任务简报或测试输出。

## REFACTOR · 复盘

每次方案运行后，按证据检查输入是否足够、路由是否准确、交接是否完整、验收是否可重复。发现问题时先确定属于描述、能力登记、方案、脚本还是测试资产，再只修改所属层并补一个可客观核对的回归案例。任何新增能力先走人工门禁；不可用“增加更多兜底”掩盖未验证通道。

新增宿主遵循 [适配器规范](references/agent-adapter-spec.md) 与 [新 Agent 适配 Loop](feature-skills/扩展-新Agent适配Loop/SKILL.md)；新增方案遵循 [方案编写指南](references/scheme-authoring-guide.md) 与 [新方案沉淀](feature-skills/沉淀-新协作方案/SKILL.md)。

## 输出契约

一次完整协作至少回报：

~~~text
host: 已确认宿主 / 平台 / 已验证传输
scheme: 方案 ID / 角色与模型
approval: 已确认的动作和范围
handoff: 委派请求 ID 或明确的未派发原因
changes: 文件清单与摘要
verification: 命令、通过/失败结果、未验证项
status: complete | waiting | blocked | failed
~~~

只有在收到完成结果并完成主 Agent 验收后才能标记 complete。证据缺失时使用 waiting 或 blocked 并说明阻塞条件。

## 使用示例

用户说：“请按 S-01 将当前修复拆给实现 Agent，计划文件已确认，允许只改 src/menu/ 并运行指定单测。”

正确响应先运行探测并展示宿主；核实宿主和本会话有可用委派通道后，展示 S-01 的 Plan/Exec/Verify 角色、模型、src/menu/ 所有权和单测命令。得到本次授权后发送简报。完成后报告真实文件差异及单测输出；如果异步通知尚未到达，则报告 waiting，不声称完成。
