# 阶段编排与回流

## 核心任务

以已确认 Spec 为单一验收依据，推进一个阶段并维护可追溯交接；阶段失败时按根因返回责任节点，不以增加补丁掩盖规格问题。

## 输入与输出

输入：流程密度、当前阶段、最新 Spec/Plan/Tasks、失败或审查证据、未关闭风险。

输出：currentStage、requiredInputs、selectedFeature、gateResult、returnStage、handoffSummary、humanGateReason。

## 编排顺序

1. 需求未形成可测 Spec：转「需求采访与规格澄清」。
2. Spec 已确认但任务/依赖不清：转「计划拆分与依赖排程」并做文档一致性 Analyze。
3. 计划与前置依赖满足：转「TDD 实现与独立审查」。
4. 实现和审查完成：转「Analyze 与 Converge」。
5. Converge 出现偏差：按偏差性质回流到 Spec、Plan/Tasks 或对应实现任务。
6. 门禁通过：汇总证据与剩余风险，交给人类验收。

每次只路由当前需要的阶段节点；任务依赖允许时才并行准备审查或独立分析，代码修改仍按依赖串行。

## 失败回流表

| 根因 | 回到 | 禁止动作 |
|---|---|---|
| 歧义、矛盾或非目标缺失 | 需求采访与规格澄清 | 擅自选解释后继续编码 |
| 无 Spec 来源的任务、依赖环或 Plan 违规 | 计划拆分与依赖排程 | 让实现者现场决定架构 |
| 行为或测试失败 | TDD 实现与独立审查 | 删除断言或标记任务完成 |
| 实现超出范围/漏掉验收 | 对应实现任务；若需求本身错则回规格 | 把偏差写成“合理增强” |
| 多轮无进展或触及产品取舍 | 🛑 STOP 并提交证据 | 无上限重复调用子技能 |

## RED / GREEN / REFACTOR

- RED：每阶段开始先确认输入版本、依赖和未决事项，避免沿用过期文档。
- GREEN：阶段交接只传 Spec、相关 Plan/Task、上游契约、测试证据和未决风险；原始日志仅保留必要片段。
- REFACTOR：同一问题在实现中第二次出现时，检查并修正 Spec、任务拆分或项目规则，避免同类局部修补。

## 使用示例

用户：“Analyze 发现任务 T04 没有对应 Spec。”

回到计划节点核对需求映射；若确属无来源工作则删除/改写任务并重跑 Analyze，不派实现代理继续执行 T04。
