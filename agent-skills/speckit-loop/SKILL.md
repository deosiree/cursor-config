# speckit-loop

## 任务

编排一个有退出条件的规格驱动开发循环。先让需求、约束和验收可验证，再安排实现；实现后独立检查规格符合性与代码质量，修复差距并由人类完成产品验收。

## 何时使用

- 需求尚未结构化，需要从访谈形成 Constitution、Spec、Plan 和 Tasks。
- 用户要求使用 Spec Kit、规格驱动开发、Analyze、Converge 或完整开发闭环。
- 实现已开始，但规格、任务、测试与代码之间存在未核实的差距。

## 何时不要使用

- 用户只问一个事实、要求纯文本改写，或要修复范围清晰且可直接验证的单点问题。
- 用户只要求执行一个已明确的任务；此时按最小必要阶段执行，不补造整套规格文档。
- 任务涉及发布、生产数据删除、权限变更或其他高影响动作；本技能可准备和验证变更，但最终动作须由用户明确决定。

## 输入契约

收集目标用户与问题、相关仓库/文件、硬性约束、成功证据、非目标、风险承受度和验证方式。缺少某项时先判断能否从仓库和现有规则可靠读取；会改变产品行为、数据、安全或验收结果的未知项必须提问，不得猜测。

## RED：失败基线

常见失败是直接编码而未验证需求；“友好、快速、安全”等词没有可观测定义；任务过大导致执行代理二次规划；测试在实现后才补；实现者自己宣告规格审查通过；修复偏差时顺手扩展范围；会话变长后丢失初始约束；验证没有命令与输出证据；循环没有退出条件。

## GREEN：执行流程

1. 运行「流程密度与需求门禁」，确定轻量、标准或高风险流程，并标出缺失事实。
2. 运行「需求采访与规格澄清」。先检查项目 Constitution；将用户故事、异常流程、验收条件和非目标写入 Spec；再逐项消除歧义与冲突。
3. 运行「计划拆分与依赖排程」。Plan 描述技术边界、文件范围、接口、风险和验证；Tasks 拆成可独立验收的工作，并做规格到任务的 Analyze。
4. 运行「TDD 实现与独立审查」。按依赖顺序执行任务；先 Red，再最小 Green，再 Refactor。未参与实现的审查者先核对规格符合性，再做代码质量审查；放行前逐项使用 assets/review-checklist.md 核验证据。
5. 运行「Analyze 与 Converge」。检查 Spec/Plan/Tasks 一致性，再检查代码、测试与文档是否收敛到已确认规格。发现缺口时回到责任阶段，只改必要范围并重跑相关验证。
6. 提供可复核验证证据、剩余风险与待用户决定项；高风险及产品体验判断交给人类验收。

执行时只调用当前阶段需要的子技能；每次阶段交接携带已确认的规格、边界和证据，不复制无关日志。

若运行时已安装 Spec Kit 阶段技能，按阶段映射调用现有能力；映射与原生流程见 references/Spec Kit阶段映射.md。先探测当前运行时可用技能/命令，不可用时使用本套件内嵌步骤，不因插件缺失中断普通流程。已调用的技能/命令失败时，不自动切换节点或重试；先汇报失败证据并询问用户是否改走内嵌等价流程。

## 阶段门禁与失败回退

| 发现 | 回退位置 | 继续条件 |
|---|---|---|
| 目标、规则或验收仍有多种解释 | 需求采访与规格澄清 | 影响行为的歧义已由用户裁定，或明确记录为阻塞 |
| Spec、Plan、Tasks 彼此矛盾或任务无需求来源 | 计划拆分与依赖排程 | 差异已修正，Analyze 无未处理阻塞项 |
| 测试失败、执行受阻或依赖未就绪 | TDD 实现与独立审查 | 根因、失败证据和下一步明确；不可伪报通过 |
| 规格审查不通过 | 实现任务或规格阶段 | 每个阻塞问题已归属到一个任务且复验通过 |
| 代码审查发现风险 | 对应实现任务 | Critical 已修复；Major 在进入下一任务前修复 |
| Converge 发现文档/代码漂移 | 责任阶段；必要时同步 Spec | 差异已修复并重跑关联测试、审查 |
| 同一阻塞项两轮未收敛或需要产品取舍 | 🛑 STOP，提交证据并询问用户 | 用户补充决策或明确接受风险后再继续 |

🔴 STOP：不得用推测补齐高影响需求，不得把未运行的测试写成通过，不得在高风险决策上代替用户确认。

## REFACTOR：循环退出

循环仅在以下条件都满足时完成：范围内验收条件逐项有证据；相关测试、类型检查、Lint、构建按项目约定实际运行并报告结果；最终 diff 与 Spec 一致；Critical/Major 问题关闭；剩余风险和未验证项公开；需要产品判断的项目由用户验收。

同一缺口连续两轮没有实质进展时停止自动修改并请求决策。不得为“清零”而扩大范围、降低测试标准、删除验收条件或连续重写文档。小任务没有规格缺口时可结束在轻量验证，不强求形式化 Converge 文档。

## 输出契约

small 任务用简洁摘要，不填充无关阶段字段；medium/large 或用户要求完整报告时使用下方完整结构。无对应阶段标记 not-applicable 并说明原因；没有证据时写 missing，不推测通过。

~~~yaml
taskSize: small
outcome: ""
verification: ""
nextAction: ""
~~~

完整结构：

~~~yaml
currentUnderstanding:
taskSize: "small | medium | large"
selectedSubskills: []
specStatus: missing | draft | clarified | approved
planAndTaskStatus: not-started | blocked | analyzed | ready
verificationEvidence:
  - command: ""
    result: pass | fail | not-run
reviewFindings:
  - severity: Critical | Major | Minor
    evidence: ""
    ownerStage: ""
convergenceDecision: pass | blocked | conditional
openRisks: []
humanGateReason: none | ""
nextAction: ""
~~~

## 反例与黑名单

- 不要把实现方案塞进 What/Why 规格，除非技术约束本身已确认。
- 不要并行修改同一核心文件或依赖未冻结的数据模型。
- 不要让实现者作为唯一规格审查者。
- 不要把 “tests pass” 当作证据；报告命令、实际结果和未跑项目。
- 不要自行发布、删除生产数据、改变权限或接受未确认的产品取舍。
- 不要为小变更制造多份文档或为了循环而循环。

## 使用示例

用户：“给后台列表加批量停用，状态变更要可追溯；先把范围问清，再按规格实现。”

本技能先访谈权限、部分失败、审计字段和完成证据；整理非目标后形成 Spec，澄清歧义，拆解为依赖任务；按 TDD 实现并独立审查；Analyze/Converge 无阻塞后报告验证证据，批量停用的产品策略由用户最终验收。
