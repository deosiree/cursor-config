# TDD 实现与独立审查

## 任务与输入

实现一个已排程 Task。输入包括 Constitution 约束、相关 Spec、已确认 Plan、单个 Task、上游接口、测试命令及允许修改范围。没有明确 Task 或前置依赖未满足时不开始代码修改。

## TDD 执行

1. 任务交给新鲜执行上下文；提供必要文档和接口，不塞无关会话日志。没有子代理能力时使用当前上下文，并显式记录。
2. Red：编写对应行为测试并运行，确认因目标行为缺失而失败。初始通过时先核对测试是否命中目标、断言是否有效、测试是否实际执行。
3. Green：写通过当前测试的最小实现，不增加非目标能力。
4. Refactor：整理重复、命名、职责、错误处理和临时代码，随后重跑相关测试。
5. 记录实际命令、输出/退出状态、修改文件、偏差和未验证风险。

## 独立审查

由未参与实现的审查者先做规格符合性审查：逐条验收映射、遗漏/误解、非目标、范围外文件和测试充分性，输出“通过/不通过”及阻塞/非阻塞项。通过后再做代码质量审查，覆盖架构、重复、安全、资源/异常、并发、测试脆弱性、性能和过度设计。

Critical 立即修复；Major 在进入下一任务前修复；Minor 可记录为建议。审查者无独立上下文时标记为非独立审查，不伪装成独立结论。

## RED / GREEN / REFACTOR

- RED：测试无法运行、前置契约不一致、改动超出 Task 范围或审查者与实现者相同却声称独立时阻断。
- GREEN：仅在验收和代码审查门禁满足后标记任务完成。
- REFACTOR：审查发现重复错误时检查 Plan/Task/项目指令是否遗漏约束；修正后重跑受影响测试与审查。

## 使用示例

用户：“执行 T03 增加的权限检查。”

仅在上游权限接口已冻结后，对无权限/有权限场景先写 Red 测试；最小实现通过后，再交由不同审查上下文按 Spec 核对授权边界与代码风险。
