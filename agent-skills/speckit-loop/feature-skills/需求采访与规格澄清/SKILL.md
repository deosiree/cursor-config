# 需求采访与规格澄清

## 任务与输入

将需求中的 What/Why 转成可验证行为。输入包括用户目标、典型场景、当前流程、约束、影响范围和已知未知项；先查看项目 Constitution 与相关既有 Spec，不重复覆盖稳定规则。

## 执行

1. 缺影响决策的事实时，一次集中提问最多 3 个相互关联的问题，说明每项会影响的行为；回答缺失则标记阻塞，不猜。
2. 明确用户故事、前置条件、主流程、失败/边界流程、可观察验收条件和非目标。
3. Spec 只写功能目的和行为。具体接口、模块、数据结构移至后续 Plan。
4. Clarify 检查模糊词、冲突、未定义边界、无来源功能和不可验证验收。每项记录问题、影响、决策来源及状态。
5. 新 Constitution 规则只收录跨功能长期有效、能验证的原则；规则已有时仅指出对应条目，不复制一份。

## 批量导出专项

批量读出或导出数据时，在最多 3 个关联问题内覆盖：数据字段与敏感级别；角色/租户授权和审计；筛选字段、时区、选中项还是全部匹配项、数量上限/速率、格式及部分失败处理。涉及个人/敏感数据时先走 large 门禁；未确认授权和字段范围不得形成可执行实现计划。

## 输出

输出确认后的 Spec 摘要、验收条件清单、非目标、待决问题及来源。每条验收条件使用 Given/When/Then 或等价的可观察表达，并覆盖主路径与关键异常路径。

## RED / GREEN / REFACTOR

- RED：没有受影响用户/结果定义，或成功条件只有“好用、快速、安全”时不放行。
- GREEN：结合仓库现状补上下文；每个假设标来源，未知影响产品行为的事项升级给用户。
- REFACTOR：Review 发现 Spec 才暴露原有矛盾时，更新 Spec 并通知依赖它的 Plan/Tasks 重新 Analyze。

## 边界与使用示例

本节点不决定技术方案、不写实现代码，也不把模型猜测当成用户决策。

用户：“登录失败要提示用户。”

先确认哪些失败原因可对用户公开、是否区分账号不存在、重试/锁定策略和审计要求，再写验收条件；如果安全策略未定，标为阻塞并 STOP。
