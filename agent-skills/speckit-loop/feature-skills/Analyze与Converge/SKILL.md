# Analyze与Converge

## 任务与输入

区分两类检查：Analyze 查 Spec/Plan/Tasks 文档一致性；Converge 查代码、测试、文档与已确认 Spec 的实现差距。输入为最新文档版本、实现 diff、测试证据和独立审查结论。

## 执行

1. Analyze：确认每条 Spec 验收项有任务来源；无任务绕过 Spec；Plan 遵守 Constitution；边界、验收与依赖无冲突。
2. Converge：对照每个验收条件检查代码、测试、用户可见结果和文档；列出漏实现、漏测、过度实现、规格漂移、部分完成和集成问题。
3. 每个发现记录严重度、证据、责任阶段、最小修复和复验范围。不得以整体“看起来一致”代替逐项映射。
4. 回流到责任节点修复，运行相关验证并重查受影响项。完成后再运行项目约定的全量验证和 diff 检查。
5. 输出停止决定、未解决风险和人类验收项。

## 判定

通过：无 Critical/Major 差距，验收项均有实现与测试证据，非目标未实现，文档已同步。条件通过：只有 Minor 且不影响安全、契约或验收，须明确风险归属及接受人。失败：任一 Critical/Major、无证据声明或高影响产品取舍未决。

## RED / GREEN / REFACTOR

- RED：文档版本不匹配、没有最终 diff、测试证据缺失时暂停结论。
- GREEN：差异归类后回流；同一阻塞项最多自动重试两轮。
- REFACTOR：若根因是 Spec 不完整，先修 Spec 并重新 Analyze；若是执行遗漏，只修实现/测试，不无理由重写全部计划。

## 🛑 STOP

相同阻塞项连续两轮没有实质进展、修复将改变用户可见行为或风险接受方式时停止并提交证据与选择题，等待用户决定。

## 使用示例

用户：“Converge 发现异常重试没有对应验收测试。”

核实重试是否在 Spec 中；若有则回流实现任务，补失败路径测试并复验；若行为定义缺失则先回需求澄清，不自行选重试次数。
