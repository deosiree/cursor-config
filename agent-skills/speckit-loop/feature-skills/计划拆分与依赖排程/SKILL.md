# 计划拆分与依赖排程

## 任务与输入

依据已确认 Spec、项目约定和仓库结构形成实施计划。输入必须包含 Spec 版本、验收项、Constitution 约束和可读取的目标仓库；缺少 Spec 时退回需求澄清。

## 执行

1. 调查既有架构和相关实现，记录事实来源与未确认假设。
2. Plan 说明组件/数据流/接口变化、文件范围、兼容性、异常处理、安全/性能风险、测试策略、回滚路径和交付门禁。
3. 将每个验收条件映射到至少一个 Task；每个 Task 写目标、修改范围、依赖、接口/行为、验证命令或方法、通过标准。
4. 任务粒度以单个代理可执行且可独立审查为准。过大则拆成可验收模块；过小的编辑步骤合并。
5. 先画依赖有向关系。只有文件/契约互不冲突、上游接口已冻结时并行；同一核心文件或数据模型相关工作串行。
6. 执行规格文档 Analyze：Spec 有对应任务、Task 有需求来源、Plan 符合 Constitution、验收可测、依赖无环。

## 输出

输出 Plan 摘要、任务清单、依赖序列/并行组、验收映射、风险与回滚、未决项和 Analyze 结论。不用完整代码代替计划。

## RED / GREEN / REFACTOR

- RED：任务无来源、无法独立验证、依赖未定义或文件范围为空泛时不放行。
- GREEN：按依赖顺序执行；新接口先由上游任务确认再派生下游任务。
- REFACTOR：Analyze 发现映射/依赖问题时修改文档后重跑，不在实现阶段口头补约定。

## 使用示例

用户：“Spec 已确认，请规划新增导出 API 和下载按钮。”

将 API、权限/错误映射、前端调用和端到端验收拆为依赖任务；明确接口契约完成后才允许前后端并行，不将两个改动都交给代理自由规划。
