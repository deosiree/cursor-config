### 典型流程示例

#### 示例 1：开启 TUN 后无法访问本地 localhost:8080

```
1. 调用: intention-skills/编排-完整修复流程
2. 自动诊断:
   - 诊断-TUN状态: FlClash TUN metric 0
   - 诊断-DNS配置: fake-ip 劫持 127.0.0.1
3. 分析: DNS劫持 + 路由劫持
4. 决策: TUN 路由排除（方案 A）
5. 修复:
   配置 inet4-route-exclude-address:
     - 127.0.0.0/8
6. 验证: ✅ ping 127.0.0.1 成功
```

#### 示例 2：修复后 Kiro 报 429 错误 🆕

```
1. 症状: Too many requests (Request ID: 023da2fa...)
2. 调用: feature-skills/修复-配置还原
3. 诊断: 排除 10.0.0.0/8 导致 Claude API 走物理网卡
4. 优化配置:
   # 从
   inet4-route-exclude-address:
     - 10.0.0.0/8  # ❌ 过大
   
   # 改为
   inet4-route-exclude-address:
     - 10.17.196.0/24  # ✓ 精确
```

## 🔧 技术参考

### 核心原理

1. **TUN 工作机制**（`references/clash-tun-原理.md`）：
   - TUN 在 OSI Layer 3 劫持流量
   - Metric 0 成为默认路由
   - fake-ip 劫持 DNS 解析

2. **为什么 Rules 无效**（`references/网络层次与优先级.md`）：
   - Rules 在 Layer 7（应用层）
   - TUN 在 Layer 3（网络层）
   - Layer 3 决策先于 Layer 7 → Rules 无法撤销路由选择

3. **路由优先级**：
   - 最长前缀匹配（10.17.196.0/24 > 0.0.0.0/0）
   - Metric 值越小优先级越高
   - TUN metric 0，物理网卡 metric 256
