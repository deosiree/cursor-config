# Feature Specification: 公理设计需求分析

**Feature Branch**: `feat/issue-pr-loop-axiomatic-analysis`

**Created**: 2026-11-28

**Status**: Draft

**Input**: User description: "在 git-skills/issue-pr-loop 中，于 HITL-1 方案确认包之前增加基于 MIT 公理设计的需求分析能力。支持新需求设计、既有项目优化、项目源码学习三种模式。分析时从用户目标识别可验证 FR，从候选方案或代码证据识别同一抽象层级的 DP；源码模式引用文件、符号或调用链，并区分事实与推断。设计矩阵按 DP 为行、FR 为列，X 表示调整该 DP 会影响该 FR，未知关系显式标记；非方阵报告覆盖缺口或冗余参数，不伪造方阵。对角阵是独立设计；三角阵只有在存在明确 DP 调整顺序时才判为解耦；其他结构如实判为耦合。发现耦合时优先在不改变 FR 的前提下重设计 DP，无法解耦则说明约束和残余耦合。仅对满足独立性公理的候选比较信息量；没有成功概率或设计范围数据时标记无法量化。分析回流至适用的 Issue 或 Goal 草稿和 HITL-1 确认包；单独源码学习保持只读，不创建 Issue、推送或开 PR。简单单点 bug 和只发布 Issue 的路径保持现有流程。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 评估新设计与既有项目优化 (Priority: P1)

需求负责人需要在确认方案前看清用户目标、可验证需求、候选设计参数及其相互影响，从而选择满足目标且耦合更少的方案。

**Why this priority**: 这项分析决定方案是否满足独立性公理，是 HITL-1 确认范围和后续 Issue/Goal 拆解的依据。

**Independent Test**: 分别给出一项新需求和一项既有项目优化请求，检查两者在确认包前均得到可验证 FR、同层级候选 DP、设计矩阵、结构判定及问题回流草稿。

**Acceptance Scenarios**:

1. **Given** 用户提出新的设计目标，**When** 形成方案确认包，**Then** 分析先将目标写成可验证 FR，再从候选方案识别同一抽象层级的 DP，并按矩阵结构说明独立性或耦合。
2. **Given** 用户要求优化既有项目，**When** 形成方案确认包，**Then** 候选 DP 有对应的现状或方案依据，耦合时先尝试在 FR 不变的条件下重设计 DP，并将分析映射到适用的 Issue 或 Goal 草稿。
3. **Given** 矩阵含未知关系或不是方阵，**When** 分析结果交付，**Then** 未知关系被显式标出，且覆盖缺口或冗余参数被报告，不以补造参数或关系伪装为方阵。

---

### User Story 2 - 学习项目源码中的设计关系 (Priority: P1)

维护者需要通过源码理解项目当前提供的功能，同时能区分代码直接证明的现有行为、用户确认的需求与分析者推断，避免把实现细节误当成用户意图。

**Why this priority**: 源码学习为既有项目优化提供可靠证据，也可独立用于理解项目而不触发任何变更。

**Independent Test**: 提供一个具有可追踪调用路径的项目问题，检查源码学习输出是否引用文件、符号或调用链，分别标注事实和推断，并且未创建 Issue、推送、开 PR 或修改源码。

**Acceptance Scenarios**:

1. **Given** 用户单独要求学习项目源码，**When** 分析完成，**Then** 输出从可观察行为提取的 FR、DP 关系及设计矩阵，为源码依据引用文件、符号或调用链，并区分现有行为事实、用户确认需求与推断出的意图。
2. **Given** 某项 DP 或关系无法从源码证据确认，**When** 输出设计矩阵，**Then** 该关系保持未知并说明缺少的证据，不把未检索到的代码当作不存在。
3. **Given** 用户只进行源码学习，**When** 分析完成，**Then** 工作保持只读，不创建或更新 Issue，不推送，不开 PR。

---

### User Story 3 - 保持现有精简路径 (Priority: P2)

维护者需要让简单单点 bug 和只发布 Issue 的请求继续按现有规则处理，避免额外分析延长本可直接处理的流程。

**Why this priority**: 新分析只应出现在需要设计选择或源码学习的场景，不能改变现有请求终点和授权边界。

**Independent Test**: 分别触发简单单点 bug 和仅发布 Issue 请求，核对流程、确认门禁和输出与改造前一致，且没有被强制插入公理设计分析。

**Acceptance Scenarios**:

1. **Given** 用户提交范围清楚的简单单点 bug，**When** 进入现有处理流程，**Then** 保持原有精简 Issue 路径，不要求完成公理设计矩阵。
2. **Given** 用户只要求发布已经评审的 Issue，**When** 准备发布，**Then** 保持仅发布路径，不增加设计分析、实现或 PR 步骤。

---

### Edge Cases

- 当 FR 与 DP 数量不相等时，报告未被 DP 覆盖的 FR 或没有对应 FR 的冗余 DP；不增删条目以制造方阵，也不把非方阵判为对角阵或三角阵。
- 当矩阵关系未知时，使用明确的未知标记；空白只表示已确认不存在影响关系，不能将未知当作无影响。
- 当方阵为三角结构但没有明确的 DP 调整顺序时，不能判为解耦，应如实标为耦合；DP 行、FR 列的下三角矩阵按从下到上的 DP 顺序调整，上三角矩阵按从上到下的顺序调整。
- 当通过重排行列可得到三角结构时，只能采用有明确设计含义的 FR/DP 顺序；不得任意重排以掩盖耦合。
- 当耦合无法在不改变 FR 的条件下消除时，说明限制、未能调整的 DP 和残余耦合。
- 当候选方案不满足独立性公理时，不将其与独立候选进行信息量比较。
- 当缺少成功概率或设计范围数据时，说明信息量无法量化，不估造概率、范围或排名。
- 当源码证据不足、符号不存在或调用链不完整时，标注证据缺口并保留未知关系，不将推断伪装为事实。
- 当用户请求意图无法区分三种模式且会影响只读边界或交付物时，先澄清模式，再继续分析。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 分析流程必须区分新需求设计、既有项目优化和项目源码学习三种模式，并在分析结果中标明所用模式。
- **FR-002**: 新需求设计与既有项目优化必须在 HITL-1 方案确认包形成前完成适用的公理设计分析；简单单点 bug 和只发布 Issue 的请求必须保持现有流程。
- **FR-003**: 新需求设计和既有项目优化必须从用户目标提取可验证的功能需求（FR），每项 FR 都有可检查的结果或验收条件，并保留其与原始目标的对应关系；源码学习可从代码可证明的现有行为提取观察项，但不得将其标为用户确认的需求。
- **FR-004**: 分析必须从候选方案或项目源码证据识别设计参数（DP）；FR 与 DP 必须处于同一抽象层级，无法确认的 DP 或关系不得伪装为已知。
- **FR-005**: 源码模式必须为源码依据引用文件、符号或调用链，并分别标注代码直接证明的现有行为、用户确认的需求和由证据推导的判断；推断不得表述为用户已确认需求。
- **FR-006**: 设计矩阵必须以 DP 为行、FR 为列；`X` 表示调整该 DP 会影响该 FR，未知关系必须显式标记，空白仅表示已确认无影响关系。
- **FR-007**: 非方阵必须如实报告 FR 覆盖缺口或冗余 DP，不得补造行、列或关系来形成方阵。
- **FR-008**: 对完整已知的方阵，只有每个对角单元格均有 `X` 且所有非对角单元格均确认无影响时才可判为结构完整的无耦合设计；还须有验收依据证明每个 DP 可满足对应 FR。`X` 只表示依赖关系，不等于验收通过；缺少对角 `X` 表示 FR 未满足或 DP 未形成对应关系。三角结构只有在对角单元格均有 `X`、每个 DP 可满足对应 FR 且存在明确 DP 调整顺序时才可判为完整解耦设计；DP 为行、FR 为列时，下三角按 DP 从下到上调整，上三角按 DP 从上到下调整。其他结构必须判为耦合。含未知关系的结构不得被报告为已证实无耦合或解耦。
- **FR-009**: 发现耦合时，分析必须优先尝试在不改变 FR 的前提下重设计 DP；若无法解耦，必须说明约束及残余耦合。
- **FR-010**: 只有满足独立性公理的候选方案可以参与信息量比较；缺少成功概率或设计范围数据时，必须标注无法量化，不得编造数值或排序。
- **FR-011**: 新设计与既有项目优化的分析结果必须回流到适用的 Issue 或 Goal 草稿及 HITL-1 确认包，且保持需求、候选 DP、矩阵结论与验收目标之间的可追溯关系。
- **FR-012**: 单独的项目源码学习必须保持只读，不得创建或更新 Issue、推送或开 PR；其发现只有在后续明确转为优化请求时才进入对应草稿与确认流程。

### Key Entities *(include if feature involves data)*

- **功能需求（FR）**：从用户目标提取的可验证结果，包含验收条件及其目标来源。
- **设计参数（DP）**：用于实现一个或多个 FR 的候选设计选择，包含抽象层级和方案或源码依据。
- **设计矩阵**：以 DP 为行、FR 为列的影响关系表，记录影响、已确认无影响及未知关系。
- **分析模式**：新需求设计、既有项目优化或项目源码学习，决定分析依据、交付物与动作边界。
- **耦合说明**：矩阵结构判定、调整顺序、重设计尝试、约束与残余耦合的可追溯记录。
- **源码证据**：代码事实所引用的文件、符号或调用链，以及基于事实形成的独立推断。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的新设计和既有项目优化确认包在 HITL-1 前包含模式、可验证 FR、同层级 DP、设计矩阵、结构判定及适用的 Issue 或 Goal 草稿回流。
- **SC-002**: 100% 的源码学习输出为源码事实提供文件、符号或调用链引用，并将现有行为事实、用户确认需求与推断出的意图分开标注。
- **SC-003**: 所有非方阵都报告 FR 覆盖缺口或冗余 DP；所有包含未知关系的矩阵都显式标记未知，且不会被宣称为已证实独立。
- **SC-004**: 所有被判为无耦合或解耦的方阵均有完整对角 `X` 映射、对应 FR 的验收依据且所有其他关系已知；解耦三角矩阵另有明确 DP 调整顺序作为依据；其他方阵结构如实报告为耦合或功能未覆盖。
- **SC-005**: 100% 的源码学习请求不产生 Issue 创建或更新、推送、PR 创建及源码修改。
- **SC-006**: 简单单点 bug 与仅发布 Issue 的既有流程不因本能力增加额外公理设计步骤。

## Assumptions

- 新设计和既有项目优化的公理设计分析属于 HITL-1 方案准备的一部分，不代表用户已授权实现或任何远端写入。
- 独立源码学习可以识别并记录候选优化方向，但不会自动将其转换为 Issue、Goal 或变更授权。
- 源码直接证明的行为不自动等同于用户或产品已确认的功能需求。
- 已确认无影响的矩阵单元可留空；未知单元必须使用可见标记。
- 信息量只有在候选满足独立性公理且具备必要的成功概率与设计范围数据时才可量化比较。
- 用户未指定优先级、概率、范围、工程容量或排期时，分析不自行捏造这些数据。

## Out of Scope

- 自动修改项目源码、创建或更新 GitHub Issue、推送分支、创建 PR 或合并代码。
- 将公理设计分析强制应用于简单单点 bug 或仅发布 Issue 的路径。
- 在源码证据不足时通过猜测补全 DP、设计关系、成功概率或设计范围。
