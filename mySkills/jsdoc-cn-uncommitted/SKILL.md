# jsdoc-cn-uncommitted

## 目标

在**提交前**对当前仓库（repo）内的**未提交变更**补齐：

- **函数级 JSDoc（中文）**：职责、参数、返回值、异常/错误码、边界条件。
- **关键变量/业务分支行注释（中文）**：只解释“意图/约束/边界”，不写“显而易见”的废话注释。

## 输入约定（关键）

### 仓库选择（单仓 vs 多仓）

- **单仓工作区**：默认使用当前工作目录对应的那个 `.git`。
- **多 Git 工作区（像本项目）**：必须明确仓库根目录 `repo_root`，例如：
  - `F:/Documents/Repertory/Sieyuan/nebula/microfb`
  - `F:/Documents/Repertory/Sieyuan/nebula/apex_dev`

若用户未指定且检测到多仓：不要猜；使用结构化提问让用户选择 `repo_root`。

### 快速开始：选择 `apex_dev`（本项目示例）

当用户希望处理 `apex_dev` 的未提交变更时：

- 将 `repo_root` 固定为 `F:/Documents/Repertory/Sieyuan/nebula/apex_dev`
- 后续所有 `git`/`lint`/`test`/文件读写操作都在该目录下执行（不要混用 `microfb` 的 `.git`）

## 执行流程（按顺序，不跳步）

### Step 0：确定 `repo_root`

1. 在候选目录分别执行 `git rev-parse --show-toplevel` 来确认是否为有效仓库根。
2. 若只发现 1 个仓库：选它作为 `repo_root`。
3. 若发现多个仓库：让用户在候选项中选择，并在后续所有命令/读写操作中使用该 `repo_root` 作为工作目录。

### Step 1：盘点未提交变更（范围锁定）

在 `repo_root` 内收集：

- `git status -sb`（确认分支与改动概览）
- `git diff --name-only`（获取“需要补注释”的文件清单）
- 若存在已暂存改动：同时查看 `git diff --cached --name-only`

输出一个“文件清单（新增/修改/删除）”，只处理本仓库的这些文件，不要扩散到全仓重写注释。

### Step 2：逐文件补注释（核心）

对每个变更文件执行：

1. 先读文件内容与 diff，定位**本次改动涉及的函数/模块**。
2. 对**新增或被修改的函数**补齐 JSDoc（中文），至少包含：
   - 一句话职责说明（说明“为什么这么做/约束是什么”）
   - `@param`：每个参数的业务含义（对象参数用点语法拆解关键字段）
   - `@returns`：返回值语义（`async` 函数用 `Promise<...>` 语义描述）
   - 可选但推荐：错误码/异常策略（例如“返回 code 供 UI 提示”）
3. 在以下位置补**行注释**（中文）：
   - 重要开关/策略分支（例如“服务端要求传输加密”）
   - 关键变量的来源与约束（例如“公钥来自 loginSetting”）
   - 兜底策略（例如“捕获加密异常并收敛错误码，避免底层异常泄露到 UI”）
4. 约束：
   - 不要给 `auto-imports.d.ts` 这类**生成文件**补冗余注释（除非本次改动确实需要解释原因，如 `eslint-disable` 的目的）。
   - 不要引入 `any`；需要时用 `unknown` + 类型守卫/断言函数。
   - 避免把“实现细节复述”写进注释；注释只解释代码无法表达的“意图/风险/边界”。

### Step 3：一致性与回归检查（前端项目必做）

在 `repo_root` 内执行（按项目实际脚本选择其一或多项）：

- ESLint：`pnpm lint` / `npm run lint` / `yarn lint`
- 类型检查：`pnpm typecheck` / `npm run typecheck`
- 单测（如存在）：`pnpm test` / `npm run test`

若发现报错：

- 先给出“错误分类 + 根因 + 修复方案 + 验证方案”，再改代码。

### Step 4：交付输出（必须）

用清单形式输出：

- **修改了哪些文件**
- **每个文件新增/修改了哪些函数的 JSDoc（列出函数名）**
- **哪些关键业务分支补了行注释（描述意图）**
- **ESLint/类型检查/测试结果摘要**

## MVP 与增强（按需）

- **MVP**：只覆盖本次未提交变更中“新增/修改”的函数与关键分支。
- **可选增强**：
  - 对同模块被调用链路的上游/下游补齐最小必要注释（仍限制在改动范围附近）
  - 为关键错误码补一份“错误码含义表”（放在同文件或 `reference.md`）
