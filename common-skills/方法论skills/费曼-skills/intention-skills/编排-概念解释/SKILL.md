# 编排：费曼 · 概念解释

> **定位：** 给定一个术语，用通俗类比加具体例子解释它。适用于"什么是 X？"场景。

## 输入

| 参数 | 来源 | 说明 |
|------|------|------|
| `术语` | 上层传入 | 需要解释的技术概念（单个） |
| `标准定义` | 上层传入 | 术语的官方/技术定义（1-2 句） |
| `上下文` | 上层传入 | 读者背景、章节主题、写作风格 |

## RED（失败基线）

| 触发条件 | 一线修复 | 兜底 |
|---------|---------|------|
| 用了多个并列类比 | 收敛为一个核心类比贯穿全文 | 仅保留最贴切的类比 |
| 类比领域与读者背景不匹配 | 选读者熟悉的领域（程序员→编程，非程序员→生活） | 去掉类比，直接定义+示例 |
| 只有类比没有标准定义 | 先给定义再给类比 | 标注⚠️ 省略定义可能造成误解 |
| 类比覆盖度不足 80%（引起误解） | 加边界说明段 | 降级为定义+示例 |
| 术语本身就是生活化概念（如"文件"） | 不需要类比，直接定义+示例即可 | 不嵌入 |
| 类比过长超过概念本身 | 缩短类比到核心映射关系 | 用 2-3 句类比 + 映射表 |

## GREEN（执行主线）

### Step 1：选择核心类比

```
从读者已知领域找一个熟悉事物：
- 读者是程序员：进程池→餐馆厨房的厨师团队、缓存→便利店的货架
- 读者是非技术人员：API→餐厅服务员、数据库→文件柜
- 读者是学生：函数→果汁机（输入水果→输出果汁）

类比要求：
- 覆盖术语 80%+ 核心特征
- 不引起误解（领域匹配度要高）
- 可在一句话内说完
```

🔴 CHECKPOINT：类比是否覆盖 80%+ 核心特征且与读者背景匹配？→ 是则继续，否则换类比

### Step 2：构建解释结构

```
[标准定义]：{1 句话技术定义}
[类比引入]："就像..." {一句话类比}
[映射表]：术语要素 ↔ 类比要素（表格格式）
[具体例子]：{一个真实的例子}
[边界说明]：这个类比在哪里不适用
```

### Step 3：输出交付

3-5 段可直接注入文档的正文：
```
段 1：标准定义（开门见山）
段 2：类比引入（"这就好比..."）
段 3：映射表（要素↔要素）
段 4：具体例子（带着数据/代码）
段 5：边界说明（类比的局限）
```

## REFACTOR

- 类比库超过 20 个 → 独立为 `references/概念解释-类比库.md`
- 映射表格式标准化 → 拆出 `feature-skills/执行-映射表生成/SKILL.md`

## 使用示例

```
术语 = "上下文窗口"
标准定义 = "LLM 一次能处理的最大 Token 数量"
读者 = "程序员"

输出：
段 1："上下文窗口是 LLM 一次能处理的最大 Token 数量。"
段 2："就像你的工作台面——台面越大，一次能摊开的文件越多。"
段 3：映射表（Token↔文件、窗口大小↔台面面积、超限↔文件掉到地上）
段 4："GPT-4 有 128K 上下文，约等于一篇 200 页的 PDF。"
段 5："但上下文窗口≠记忆——超过窗口的内容会完全丢失，不是暂时放到抽屉里。"
```

## 约束

- 只解释单个术语，不介绍相关概念（那些属于统合叙事）
- 类比与读者背景匹配（程序员用编程类比，非程序员用生活类比）
- 必须包含边界说明（防止误解蔓延）
- 写后必须过理解校验 `[[../编排-理解校验/SKILL.md]]`
