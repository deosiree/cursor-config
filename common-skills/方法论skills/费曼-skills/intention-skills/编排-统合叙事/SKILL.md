# 编排：费曼 · 统合叙事

> **定位：** 给定多个术语 + 它们的层级/派生关系，生成一个统一场景串联全部术语。

## 输入

| 参数 | 来源 | 说明 |
|------|------|------|
| `术语列表` | 上层传入 | 需要串联的 2-5 个术语 |
| `关系描述` | 上层传入 | 术语之间的层级/派生/调用关系 |
| `上下文` | 上层传入 | 章节主题、读者水平、写作风格偏好 |

## RED（失败基线）

| 触发条件 | 一线修复 | 兜底 |
|---------|---------|------|
| 术语列表为空 | 🛑 STOP，请求上层补充 | 无 |
| 场景与术语领域不匹配 | 换一个与术语领域一致的场景 | 改用独立类比逐个解释 |
| 并列多个「XX 就像 YY」 | 整合为一个场景贯穿全局 | 仅保留第一个类比，其余融入场景 |
| 只有定义没有场景动作 | 加一个带时序动线的实例 | 降级为对比表 |
| 术语超过 5 个 | 先建分组再选代表术语 | 标注⚠️ 未覆盖的术语列表 |
| 读者反馈场景太抽象 | 加具体数字/界面截图描述 | 换成更生活化的场景 |

## GREEN（执行主线）

### Step 1：寻找串联场景

```
条件：一个场景覆盖所有术语
候选方向：
- 面试现场对话（面试官问→候选人答）
- 一次 API 请求的完整链路（从发起到返回）
- 一个业务场景的完整处理流程
- 一个故障从发生到恢复的经过

选择标准：
- 可画成一张简图或一条时序
- 场景中的每一步自然引入一个术语
- 读者不需要额外背景知识
```

🔴 CHECKPOINT：找到的场景是否覆盖所有术语？→ 是则继续，否则换场景

### Step 2：在场景中嵌入术语

```
场景推进线 → 术语 A 出现（自然引入原因）→ 调用术语 B → 术语 B 的机制派生术语 C → ...

格式：
[场景段落 1：引入第一个术语]
  场景推进到某一步 → "这时需要 {术语A}，因为..." → 一句话解释术语A的角色

[场景段落 2：自然过渡到第二个术语]
  基于场景推进 → "而 {术语A} 的结果会传给 {术语B}" → 解释术语B

[场景段落 3+：继续覆盖剩余术语]
```

**规则**：
- 每个术语不配独立类比（独立类比=举例，不是费曼统合）
- 术语之间的关系通过场景动作自然呈现
- 场景须可画成一张简图或一条时序

### Step 3：输出交付

```
正文（3-5 段），可直接注入文档：
- 第 1 段：场景铺垫 + 第一个术语出现
- 第 2-3 段：场景推进 + 后续术语依次出现
- 最后一段：场景收尾 + 术语关系总结
+ 可选 Mermaid 时序图
```

## REFACTOR

- 场景库膨胀到 10+ → 独立为 `references/统合叙事-场景库.md`
- Step 2 术语嵌入规则复杂化 → 拆出 `feature-skills/执行-场景嵌入/SKILL.md`

## 使用示例

```
术语列表 = ["API Gateway", "Service Mesh", "Load Balancer"]
关系 = "请求→Gateway→Service Mesh→Load Balancer→实例"

场景："一次移动端下单请求"
段落 1：用户点击"提交订单"→ 请求到达 API Gateway（Gateway 做鉴权/限流）
段落 2：Gateway 通过后转发到 Service Mesh（Mesh 做服务发现/路由）
段落 3：Mesh 内 Load Balancer 从 10 个实例中选一个处理
段落 4：总结一条请求经过三者的完整链路 + 各自分工
```

## 约束

- 场景必须可画成简图
- 不超过 5 个术语，超出的先分组
- 每个术语用 1-2 句话解释即可（不是全量文档）
- 写后必须过理解校验 `[[../编排-理解校验/SKILL.md]]`
