# Cursor Config 仓库章程

## Core Principles

### I. 规则唯一来源与中文维护
本仓库自行维护的规则、规格、项目文档和提交信息必须使用简体中文；技术标识、命令和代码可保留原文。B 端编码与改码细则唯一维护于 `system-skills/my-skills/SKILL.md`。相关入口只说明适用范围、链接或路由，不复制该文件中的细则。第三方工具托管的生成文件按其官方格式管理，不作为本仓库自行维护的规则正文。

**提交规范**：
- 必须遵循 Conventional Commits 规范，格式为 `<type>(<scope>): <中文摘要>`（`<scope>` 可选）。
- 允许的类型包括 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。
- 支持自动化的提交信息生成；无论自动生成还是人工编写，提交信息主体必须使用简体中文，类型前缀、技术标识、命令和代码可保留原文。

### II. 范围最小与简洁优先
改动必须限于用户目标所需范围，不得夹带无关重构。代码决策优先级为简洁、稳定、可维护、性能；新增抽象必须承载明确业务语义或稳定边界，避免无实际收益的复杂度。

### III. 职责边界清晰
规则、技能、配置和文档必须按职责组织。通用章程不得承载领域操作手册；面向 B 端项目的具体分层、框架和类型约束以唯一规则源及目标仓库约定为准，本章程不复制其实现细节或覆盖目标项目已有边界。

### IV. 质量要求可验证
交付结论必须能由实际证据复核。报告验证结果时应区分已通过、失败和未执行的项目，不得将计划中的验证写成已通过；具体测试和文档要求由适用的规则源定义。

### V. 高影响决策由用户授权
涉及产品取舍、生产数据、权限、发布或其他高影响动作时，用户必须明确授权最终动作。调查、方案准备和可逆验证不得被视为对最终动作的授权。

### VI. 轻量渐进披露式跨 Skill 协作
跨 Skill 协作必须遵循轻量、渐进披露协议：在执行前（如 `HITL-1`）埋点声明拟调用的协作 Skill 计划，阶段调用前透明披露原因、阶段、交接产物与门禁，避免 AI 漏判或隐式跳步；普通无需协作的任务不得罗列未用 Skill。除非用户显式要求 AI 自行判断 Skill 调用（例如明确提出“头脑风暴”），否则不得跳过执行前协作埋点与阶段披露。

## 规则来源与适用范围
本章程约束本仓库维护的规则配置、技能、文档及其 Spec Kit 产物。B 端编码和改码的详细要求以 `system-skills/my-skills/SKILL.md` 为唯一来源；`.cursorrules`、`.cursor/.cursorrules`、`.codexrules` 和 `CLAUDE.md` 等入口应保持来源引用一致，不另建重复副本。领域细则由对应规则源维护，避免在本章程中重复定义。

## Governance
本章程是本仓库 Spec Kit 规格、计划和任务的项目级治理依据；领域实现细则仍由其唯一规则源治理。修订章程时必须说明变更理由、更新版本与最后修订日期，并检查受影响的规则入口仍指向正确来源。版本按语义化规则递增：不兼容地删除或重定义原则时升主版本，新增原则或实质扩展要求时升次版本，澄清和文字修订时升补丁版本。提交前移除顶部临时 Sync Impact Report，并确认无未解释的模板占位符。
