# 为何用 revert 而非强推

## 问题

共享分支（如 `develop`）上的草稿一旦 push，同事可能已经 fetch/基于 tip 工作。用 `push --force` / `--force-with-lease` **改写 tip** 会：

- 被托管平台或分支保护直接拒绝
- 让他人本地历史分叉、难以对齐
- 抹掉「曾经给后端看过哪一版」的审计线索

## 本套件做法

1. 草稿 commit `B` 保留在历史上  
2. 之后（中间可有同事提交）增加 `revert(B)`，树回到草稿前效果（叠加同事改动）  
3. 再 `cherry-pick` / 提交最终版 `F`

远端呈现：`B → … → revert(B) → F`。本地审查分支可丢弃。

## 何时才考虑强推

仅当：**私有特性分支**、无人依赖该 tip、且团队允许 force-with-lease。那不是本套件职责。
