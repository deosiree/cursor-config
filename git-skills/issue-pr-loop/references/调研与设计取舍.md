# 调研与设计取舍

本文件记录公开流程参考、已保留的上游快照和本套件自己的取舍。引用与复制均标注来源和许可；上游快照不替代本套件入口。

## 公开资料

- [dceoy/speckit-agent-skills](https://github.com/dceoy/speckit-agent-skills)：截至 2026-11-24 页面显示约 174 stars。其价值在于清晰的 Specify → Plan → Tasks → Analyze → Implement 阶段边界和多运行时 Agent Skill 产物布局。本套件只取需求澄清、计划、任务拆解和一致性分析，不要求目标仓库必须安装 `.specify/`。
- [magnus919/agent-skills](https://github.com/magnus919/agent-skills)：截至 2026-11-24 页面显示约 184 stars。其 `neckbeard` 工作流强调可验证验收先于实现、独立验证者、证据台账和人工停止门。本套件借鉴其“证据决定 done”原则。
- [lmorchard/agent-sessions](https://github.com/lmorchard/agent-sessions)：截至调研时页面显示 0 stars，因此不作为高星依据；它细化了冻结验收条件、按阶段处理 Issue 到 PR、独立评分和 merge gate 的做法，可作为小型专题参考。
- [vmitsaras/Agent-Skills 的 plan-to-issues-converter](https://github.com/vmitsaras/Agent-Skills/blob/4d97fd8af592be08ae16d072bcdb119fc89d8c9f/skills/project-planning/plan-to-issues-converter/SKILL.md)：MIT 许可，适合把已有计划转成自包含、带范围、验收、依赖和 readiness 的 Issue 草稿；原文和许可证副本见 `upstream/plan-to-issues-converter/`。本套件额外加入需求候选池、旧项目维护、批次授权和角色分离。
- [mattpocock/skills 的 triage](https://github.com/mattpocock/skills/blob/d65391149dbb5fe76478e76fa8d5122b2aa5a70e/skills/engineering/triage/SKILL.md)：MIT 许可，聚焦已有 Issue/PR 的 bug/enhancement 分类、needs-info 与 ready-for-agent 状态、复核反馈事实和 agent brief；原文、配套 brief、拒绝记录说明与许可证见 `upstream/mattpocock-triage/`。本套件借鉴其状态与验证方法，不采用自动贴标签、评论或关闭 Issue 的外部写入流程。
- [FurkanEdizkan/My-Skills 的 create-github-issue](https://github.com/FurkanEdizkan/My-Skills/blob/main/skills/create-github-issue/SKILL.md)：覆盖 plan 到 issue/branch/work log/PR 的连贯流程，适合 Issue 创建后马上交付的场景。本套件不照搬该默认联动，因为当前需求要允许 Issue、实现和 PR 分开。
- [GitHub REST API：Issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies)：当前文档提供 blocked-by 和 blocking 依赖查询、创建、删除端点。能力和权限受 GitHub API/仓库条件约束，因此本地表是离线事实源；远端支持时再同步并读回。
- [GitHub：Issue 与 PR 模板](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests)：仓库模板可标准化创建 Issue/PR 时要收集的信息；本套件将模板作为必需结构依据，并用 few-shot 演示可读正文。
- [GitLab：Description templates](https://docs.gitlab.com/user/project/description_templates/)：Issue 与 Merge Request 可使用项目级 Markdown 描述模板；跨平台时先识别仓库平台和现有模板。
- [GitLab Flavored Markdown](https://docs.gitlab.com/user/markdown/) 与 [GitLab 文档文本格式指南](https://docs.gitlab.com/development/documentation/styleguide/text_and_formatting/)：单个换行仍属于同一段，空行开始新段落；GitLab 文档规范也建议在不同 markup 区块间留空行。
- [GitHub：PR 标准化](https://docs.github.com/en/pull-requests/reference/managing-and-standardizing-pull-requests)：PR 模板可提示变更目的、关联 Issue、测试记录和 checklist。本套件采用这些信息类别，但不强制所有仓库使用相同标题或章节名。
- [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)：它规范 commit message 的结构，不是通用 PR 标题规范。本套件仅在目标仓库明确采用时，将其用于 PR 标题。

## 设计决定

| 决定 | 理由 | 替代方案 |
| --- | --- | --- |
| 当前会话完成需求讨论和调研 | 用户明确不要求固定在 ChatGPT 网页端；文件和决策统一由当前协作上下文承载 | 强制切网页工具会增加交接和上下文漂移 |
| 一个 Goal 锚点 + Issue DAG + 单 Issue develop.md | 对齐项目目标、依赖编排和可执行单项计划，同时避免复制多份规格 | 一个总计划会让每个 Issue 仍需自行拆解；无图会丢依赖和并行边界 |
| 请求先进入本地候选池，按批次评审后再发布 | 避免每条临时反馈立即打断实现节奏，也保留来源、去重和取舍记录 | 直接把每条口头建议马上转成远端 Issue 会膨胀 backlog |
| 区分候选、待澄清、可交实现和已拒绝状态 | triage 状态机适合管理已存在的 Issue；本地 inbox 负责 Issue 创建前的收敛，状态不替代发布或实现授权 | 只用 open/closed 会混淆需求不完整与已批准实现 |
| 新项目和旧项目使用不同 Goal 策略 | 新项目需要冻结初始目标；旧项目应复用长期维护目标，单个小 Issue 不强制新建全套图谱 | 每次维护都重做总规划会增加文档负担并造成目标漂移 |
| 先排并行候选，满足隔离和授权后再执行 | 用户需要 AI 并发能力；文件边界、冻结接口、独立工作区和团队名额决定能否安全并发 | 默认并行会增加协调和合并成本；默认串行则无法显式暴露可并行批次 |
| Issue、实现、PR 和合并分阶段授权 | Issue 创建者、实现者和 PR 作者可不同，reviewer 和 merger 仍有独立责任 | 自动把 Issue 创建绑定代码实现会打乱团队排期并混淆授权 |
| 依赖表为事实源，Mermaid 只展示 | 图形易读但不便表达 ID、状态、路径所有权和同步证据 | 只靠 Markdown 文本描述难于检查遗漏和环 |
| `goal.md` 修订显式确认并级联同步 | 防止会话延长或失败修复后悄然改变初始验收 | 允许实现者直接改 Goal 会破坏目标锚定 |
| 性能/安全采用明确授权与阈值门禁 | 没有负载目标或授权范围，无法可靠判定通过，也不能安全测试 | 用默认阈值或生产环境快速试跑不适当 |
| PR 人审和合并是停止点 | 用户要求人工审查验收后再合并 | 自动合并会绕过明确的人类门禁 |
| Issue 与 PR 使用独立格式样例 | 两类工件的读者问题不同；模板先定义必需字段，few-shot 示范清楚的正文和空行 | 一份通用模板会让 Issue 混入实现报告，或让 PR 缺少验证事实 |
| 用户自有仓库默认中文，外部仓库按项目语言 | 这是用户偏好，不是跨项目的通用强制标准；明确贡献规则优先，外部项目缺少语言声明时才观察近期同类工件 | 所有仓库固定中文会违背外部项目约定；固定英文会忽略作者对自有仓库的偏好 |
| 仓库模板优先定义结构，语言另行判定 | 保留必需字段，不将英文占位标题误判为强制英文 | 从 README 语言直接推断模板正文规则，可能忽略明确偏好 |
| Markdown 块之间使用空行 | GitLab GLFM 单换行不开始新段落；清晰分段改善网页渲染与源码审阅 | 把多项内容连成单段会降低扫描和维护性 |
| 行业信息要素映射到仓库格式 | GitHub 官方指南说明模板可收集变更目的、关联 Issue 和测试信息；仓库自己的章节名、顺序与语言仍是本地约束 | 固定套用一种“行业 PR 模板”会覆盖仓库要求，或误把 commit 规范当作 PR 规范 |
| Issue 分别记录依据分支和 PR 目标分支 | 依据分支与 commit SHA 说明问题在哪版代码上观察并提出；实现/PR 目标分支说明代码准备合入哪里，两者是不同事实 | 用 GitHub 默认分支代替项目实际开发分支，或把证据基线误当成 PR 目标，会让 Issue 无法复现或让 PR 指向错误分支 |
| 目标分支与合并结果分开记录 | PR base 在创建前按用户确认或项目约定选择，创建后读回核对；实际合入分支、日期和 merge SHA 在合并后读取 | 把目标分支误当成合并后才可知，或把预期合并状态写成事实，都会造成错误记录 |

## Issue 与 PR 写作规范

- GitHub 与 GitLab 都提供仓库级 Issue/PR 或 Merge Request 模板，适合固定必填信息；few-shot 负责示范具体写法，不替代仓库模板。
- 行业规范与仓库本地规范分层处理：通用规范提供变更目的、关联 Issue、改动、验证和风险等审阅信息；本地规则决定语言、标题格式、必需章节、名称和顺序。把前者映射进后者；字段缺失时在不冲突处补充，直接冲突则先问。
- “行业规范”不是一套普遍适用的 PR 标题/正文模板。GitHub 官方指南支持用 PR 模板收集上下文、关联 Issue 和测试记录；Conventional Commits 规范 commit message，不能未经仓库确认就当成 PR 标题规则。
- 基于代码现状起草 Issue 时，注明 `owner/repo`、Issue 观察问题时的诊断分支和 commit SHA，并单独注明预期实现/PR 目标分支。项目开发分支可能不同于 GitHub 默认分支；目标分支按用户确认或仓库约定核实，不从默认分支猜测。无法核实时用 `unknown`，并在创建 PR 前解决。
- PR 目标分支在创建时作为 base 设置并在远端读回核对；只有真实合并后才填写实际合入分支、日期和 merge SHA。
- 若 PR 本地格式有“合并版本/合入分支”，PR 未合并前保留待填写状态；读到远端合并事实后再补实际日期、分支和 SHA。
- 语言规则与结构规则分开判定：用户拥有的个人仓库默认中文；外部仓库遵循明确的贡献语言规则，未明示时参考近期同类 Issue/PR 与项目文档。强制规则与用户偏好冲突或证据不足时先询问。
- GitLab GLFM 明确说明单个换行仍在同一段，空行才开始新段落。Issue/PR 正文应按平台规则分开标题、段落、列表和代码块；不要把 GitLab 的换行行为泛化成所有平台的差异。
- 本套件将历史 Issue 结构脱敏归纳为格式样例，不复制内网正文或把样例事实当作当前项目事实。具体样例见 [[../assets/few-shot-example/README.md]]。

## 与 Spec Kit / speckit-loop 的关系

- Spec Kit 的 Specify/Clarify 体现在当前会话 Goal 澄清；Plan/Tasks 体现在每个 Issue 的 develop.md；Analyze/Converge 体现在节点核对和项目终验。
- 若仓库已经安装 `$speckit-loop` 或 Spec Kit 阶段技能，按用户或仓库约定调用它们的相关阶段；每个 Issue 单独使用必要部分，不把项目图谱替换为完整 `.specify/` 生成物。
- 目标仓库有 Constitution 或开发规范时，将其作为硬约束读入 develop.md。没有规范时不额外制造全套 Constitution 文档。
