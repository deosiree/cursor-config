# 调研与设计取舍

本文件记录本套件借鉴的公开流程和基于当前目标作出的取舍。调研用于改进工作流，不代表复制第三方 skill。

## 公开资料

- [dceoy/speckit-agent-skills](https://github.com/dceoy/speckit-agent-skills)：截至 2026-11-24 页面显示约 174 stars。其价值在于清晰的 Specify → Plan → Tasks → Analyze → Implement 阶段边界和多运行时 Agent Skill 产物布局。本套件只取需求澄清、计划、任务拆解和一致性分析，不要求目标仓库必须安装 `.specify/`。
- [magnus919/agent-skills](https://github.com/magnus919/agent-skills)：截至 2026-11-24 页面显示约 184 stars。其 `neckbeard` 工作流强调可验证验收先于实现、独立验证者、证据台账和人工停止门。本套件借鉴其“证据决定 done”原则。
- [lmorchard/agent-sessions](https://github.com/lmorchard/agent-sessions)：截至调研时页面显示 0 stars，因此不作为高星依据；它细化了冻结验收条件、按阶段处理 Issue 到 PR、独立评分和 merge gate 的做法，可作为小型专题参考。
- [GitHub REST API：Issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies)：当前文档提供 blocked-by 和 blocking 依赖查询、创建、删除端点。能力和权限受 GitHub API/仓库条件约束，因此本地表是离线事实源；远端支持时再同步并读回。

## 设计决定

| 决定 | 理由 | 替代方案 |
| --- | --- | --- |
| 当前会话完成需求讨论和调研 | 用户明确不要求固定在 ChatGPT 网页端；文件和决策统一由当前协作上下文承载 | 强制切网页工具会增加交接和上下文漂移 |
| 一个 Goal 锚点 + Issue DAG + 单 Issue develop.md | 对齐项目目标、依赖编排和可执行单项计划，同时避免复制多份规格 | 一个总计划会让每个 Issue 仍需自行拆解；无图会丢依赖和并行边界 |
| 默认串行，有条件再并行 | 多 agent/多 worktree 有路径冲突、共享契约和集成风险；并行应由证据解锁 | 默认并行会增加协调和合并成本 |
| 依赖表为事实源，Mermaid 只展示 | 图形易读但不便表达 ID、状态、路径所有权和同步证据 | 只靠 Markdown 文本描述难于检查遗漏和环 |
| `goal.md` 修订显式确认并级联同步 | 防止会话延长或失败修复后悄然改变初始验收 | 允许实现者直接改 Goal 会破坏目标锚定 |
| 性能/安全采用明确授权与阈值门禁 | 没有负载目标或授权范围，无法可靠判定通过，也不能安全测试 | 用默认阈值或生产环境快速试跑不适当 |
| PR 人审和合并是停止点 | 用户要求人工审查验收后再合并 | 自动合并会绕过明确的人类门禁 |

## 与 Spec Kit / speckit-loop 的关系

- Spec Kit 的 Specify/Clarify 体现在当前会话 Goal 澄清；Plan/Tasks 体现在每个 Issue 的 develop.md；Analyze/Converge 体现在节点核对和项目终验。
- 若仓库已经安装 `$speckit-loop` 或 Spec Kit 阶段技能，按用户或仓库约定调用它们的相关阶段；每个 Issue 单独使用必要部分，不把项目图谱替换为完整 `.specify/` 生成物。
- 目标仓库有 Constitution 或开发规范时，将其作为硬约束读入 develop.md。没有规范时不额外制造全套 Constitution 文档。
