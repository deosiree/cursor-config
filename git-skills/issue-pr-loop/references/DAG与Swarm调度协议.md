# DAG 拆解与 Swarm 调度协议

本协议为 `$issue-pr-loop` 的同构任务拆解、菱形 Fan-in 剥离、动态并发治理及跨 Skill Swarm 边界的唯一执行规范。所有规则均须以可核验事实为准，禁止无隔离抢写共享状态或虚构并发。

## 1. 统一同构节点 Schema

无论项目级多 Issue 拆解（`issue-graph.md`），还是单 Issue 内部 Stage / Task 拆解（`develop.md`），统一采用以下 7 列同构节点 Schema：

| id | 职责与验收 | deps | writes（写集 glob） | mode（ro/rw） | 关键路径权重 | 隔离模式（inherit/share/worktree） |
| --- | --- | --- | --- | --- | --- | --- |
| `<I-01 / T-01>` | `<单一可验证交付与对应检查命令/断言>` | `<前置阻塞 ID 列表或 —>` | `<写入路径 glob；ro 节点填 ->` | `ro` / `rw` | `<以本节点为起点的最长下游权重/依赖深度>` | `inherit`（仅 `ro`）/ `share` / `worktree` |

字段硬规则：

1. **职责与验收**：每节点只承载一个可独立验证的结果，必须写明至少一条可核对的检查标准。
2. **deps**：仅记录强阻塞前置依赖（`blocked_by`）；非阻塞的信息关联不得写入 `deps`。
3. **writes（写集 glob）**：显式列出本节点会新建、修改或删除的路径模式；`mode=ro` 的只读节点禁止写仓库源码，填 `—` 并指定独立产物输出路径。
4. **mode**：`ro` 表示只读分析、评审、盲评或审计；`rw` 表示会修改仓库文件或生成构建产物。
5. **关键路径权重**：按关键路径长度（下游被阻塞节点总数或最长下游链长度）赋权，用于就绪队列的**关键路径优先（CP-First）**排序。
6. **隔离模式**：`ro` 节点统一使用 `inherit`（共享只读仓库视图，隔离各自上下文与输出目录）；`rw` 节点强制使用 `share` 或 `worktree` 独立工作区，严禁多个 `rw` Worker 共享同一工作区并发写文件。

与项目图谱映射：在 [[../template/mvp/issue-graph.md]] 与 [[../intention-skills/项目规划与Issue图谱/SKILL.md]] 中，`Local ID`、`Blocked by`、`文件所有权` 与本 Schema 的 `id`、`deps`、`writes` 保持一一对应，并补充 `mode`、关键路径权重与隔离模式。

## 2. 三条串并发硬判据

判定两个就绪节点能否放入同一并行波次时，按顺序执行以下三条硬判据（任一不满足即取消同波次并发资格）：

1. **因果/契约依赖（RAW，Read-After-Write）→ 强制串行**
   - 下游节点需要读取、调用或依赖上游节点产出的类型定义、接口契约、Schema、数据结构或评测夹具时，必须通过 `deps` 建立强依赖边，上游未交付并验明契约前严禁启动下游。
2. **写集重叠（WAW，Write-After-Write）→ 剥离 Fan-in 或强制串行**
   - 比较同波次所有 `rw` 节点的 `writes` glob 集合。若存在交集：
     - **先判是否仅共享入口重叠**：若重叠只集中在导出索引、注册表、路由清单或汇总文档，按第 3 节默认剥离为后置单写者 Fan-in 节点，解锁中段并发；
     - **核心逻辑紧耦合不可剥离**：若多个任务修改同一文件的核心实现逻辑、状态数据结构或相互耦合的类型定义，强制排为串行波次。
3. **共享环境/外部状态互斥 → 强制串行或外环单写者收口**
   - 涉及监听同一本地端口、写入同一数据库/测试夹具、同一 Git 分支提交、修订项目宪法（`.specify/memory/constitution.md`），或写入 GitHub 远端（建/改 Issue、推分支、开 PR、合并）时，禁止子 Worker 并发抢写，必须强制串行或收敛至外环 Coordinator 单写者统一执行。

## 3. 默认菱形 Fan-in 拆解

当多个独立实现任务仅在少数共享入口、索引、注册表或汇总文件存在写集重叠时，**默认自动剥离共享文件为后置单写者汇聚节点（Fan-in）**，将串行链路重构为菱形拓扑以解锁中段宽并发。

- **典型共享入口文件**：`index.ts` / `index.js`、`SKILL.md`、`AGENTS.md`、`results.tsv`、`registry.json`、`README.md` 汇总表、路由/菜单注册文件。
- **剥离执行步骤**：
  1. 中段各并发 `rw` 节点只修改各自的专属实现文件（如 `src/modules/a.ts`、`plugins/b.ts`），`writes` 列表中**完全剔除**共享入口文件；各节点同时在其本地交付摘要中输出拟注册的导出/条目片段。
  2. 新增后置 Fan-in 节点（如 `T-fanin`），`deps` 覆盖所有中段并发节点，`writes` 独占该共享入口/汇总文件（如 `src/index.ts`、`plugins/registry.json`、`README.md`），`mode=rw`。
  3. 外环 Coordinator 逐一合入中段各隔离工作区的产物并确认无误后，再启动单写者 Fan-in 节点统一更新共享入口与汇总文档，并运行全量集成检查。
- **退回条件**：仅当共享文件内部存在核心业务逻辑、共享状态机数据结构或相互依赖的类型耦合，无法剥离为独立的声明式登记/导出动作时，才放弃 Fan-in 剥离并退回串行。

## 4. 黄金粒度标尺

每个进入调度队列的独立节点必须同时满足以下 4 条硬标尺：

1. **独立可验收**：至少绑定一条客观、可重复核对的检查命令、单测、Schema 校验或评审清单。
2. **零写集交集**：同波次任意两个 `rw` 节点的 `writes` glob 集合交集为空。
3. **单上下文周期可控**：任务边界清晰、输入自包含，单个 Worker 在一次独立上下文周期内即可完整交付，无需在 Worker 内部再做二次大拆解。
4. **可独立重跑或回滚**：节点执行失败时，只需重跑该节点或丢弃其独立工作区/输出目录，不会破坏同波次其他已完成节点的产物。

## 5. 动态并发治理（不设静态硬上限）

### 5.1 HITL-1 并发 Schema 强制披露

只要任务涉及多 Issue 编排或多阶段并发拆解，`HITL-1` 确认包必须显式输出以下 4 项并发 Schema：

1. **独立任务总数（逻辑隔离数）**：满足第 4 节黄金粒度的全部逻辑独立节点数（含 `rw` 与 `ro` 计数）。
2. **预期最大并发数（写入并发 / 只读并发）**：明确拆分列出写入并发上限与只读并发上限（格式如 `写入并发 ≤ N / 只读并发 ≤ M`），不得混写。
3. **关键路径与并行波次摘要**：标明关键路径节点链条、权重最高节点、各并行波次划分及阻塞关系。
4. **共享入口 Fan-in 收口清单**：列出已剥离的共享入口文件、对应 Fan-in 汇聚节点 ID 及其前置依赖；无 Fan-in 时写 `无`。

### 5.2 动态有效并发度计算与临时上限 `K`

本协议**不硬编码静态并发上限**（不规定“固定最多 2 或 3 路”）。任意调度窗口的有效并发度按以下公式实时计算：

`K_eff = max(1, min(K_dag, K_user, K_slots))`

- `K_dag`：当前已解锁（`deps` 全满足）且满足三条硬判据的同波次可并发节点数。
- `K_user`：用户本轮显式指定的临时并发上限（例如“本次写入并发上限设为 2”）；用户未指定时 `K_user = +∞`，仅受 `K_dag` 与 `K_slots` 约束。
- `K_slots`：当前运行时客户端可用 Worker 槽位数与后端多账号/API 真实可用并发槽位数的较小值。

**关键路径优先调度（CP-First）**：当 `K_eff < K_dag` 时（无论受 `K_user` 还是 `K_slots` 限制），严格按**关键路径权重从高到低**从就绪队列滑动取任务派发。必须优先派发能够解锁下游关键节点（如唯一阻塞后续汇聚节点）的高权重任务，严禁让无下游依赖的边缘任务挤占槽位。

### 5.3 三条防卡死铁律

1. **主动扇出，吃满槽位（Work-Conserving）**
   - 面对多账号后端（单号并发受限但多账号可并行消费）或运行时并发子代理能力，同一调度轮次必须立刻按 `K_eff` 扇出独立 Worker 或独立 LLM 调用，吃满全部可用槽位。
   - **绝不空等**：严禁因“可用槽位 `K_slots` 小于待跑任务总数”（例如 8 个任务但只有 2 个空闲槽位）而停在准备阶段空等槽位凑齐。
2. **即用即收（Slot Hygiene）**
   - 每个 Worker 交付产物并经外环核验其对应输出文件/工作区完整后，**立即关闭并销毁该 Worker 实例以回收槽位**，同时从动态就绪队列按 CP-First 原则立即补位下一个任务。
   - 严禁让已完成任务的 Worker 长期挂起僵尸占槽，阻塞后续任务或引发死锁。
3. **真实限流/撞槽弹性分批**
   - 运行中遭遇真实 `429` 限流、后端配额枯竭或客户端活跃槽位满载时，**临时弹性收缩并发窗口（最低保底 `K_eff = 1`）**并做退避分批推进，待限流恢复或槽位释放后重新将并发窗口拉满。
   - **严禁串台合跑**：绝不允许为了省槽位而将多个独立任务的输入揉进同一个 Worker 上下文合并执行（防止上下文污染与输出混淆），也不因单次 429 中止整个 Goal。

## 6. `/goal` 内嵌主动触发 Swarm 与跨 Skill 透传

### 6.1 `/goal` 指令内嵌授权与运行规范

长程多 Issue Goal 经 `HITL-1` 确认后交付的可复制 `/goal` 启动指令，必须直接内嵌以下并发执行指引，确保执行器在推进中**无需用户中途手敲 `/swarm`** 即可自动利用并发能力：

- **主动触发**：推进中遇到满足第 2~4 节隔离条件的并发波次或节点时，主动调用运行时内置的 Swarm 或带独立工作区的并行子代理工具扇出执行。
- **工作区硬隔离**：所有 `rw` 写节点强制运行在 `share` 或 `worktree` 独立工作区；`ro` 只读节点运行在 `inherit`，并分配互不重叠的输出目录/报告文件。
- **外环单写者收口**：所有并行节点产物均交由外环 Coordinator 单写者串行合入本地主工作区、执行 Fan-in 收口、跑通全量验收测试，并按 `HITL-1` 授权逐项创建 PR 后停在 `HITL-2`（不自动合并）。

### 6.2 无并发工具的诚实降级

若运行时客户端未向当前模型暴露任何原生 Swarm 或并发子代理工具（仅支持单线顺序调用）：

1. 执行器必须在遇到并发波次时**诚实降级为按关键路径优先（CP-First）逐个串行执行**；
2. 保持每个逻辑节点各自的输入边界、独立交付物记录与独立验收检查；
3. 在最终汇报和运行记录中如实注明“当前运行时未暴露并发工具，已按关键路径优先串行降级完成”；**严禁伪造并发执行过程、假装启动 Swarm 或虚构子 Worker 记录**。

### 6.3 跨 Skill 透传与边界红线

按 [[跨Skill协作协议.md]] 约定，纵向 `Single Dispatch`（同一阶段仅激活一个协作 Skill）与横向并发完全正交：

1. **保留阶段内并发**：外环调用 `$speckit-implement` 处理含 `[P]` 标记的并行任务，或调用 `$darwin-skill` 执行多题/多评委并发盲评时，不得阉割协作 Skill 内部的并发/Swarm 能力，并按第 5 节执行 `K_eff` 与 Slot Hygiene 治理。
2. **遵守 5 要素披露**：进入每个协作阶段并激活对应 Skill 前，仍先向用户披露 5 要素（拟调用 Skill、触发原因、当前阶段、预期交接产物、对应 HITL 门禁）。
3. **透传隔离与 GitHub 独占红线**：
   - 写操作子 Worker 必须使用独立工作区且禁止同时写入同一文件；只读评测/审计各自保持独立上下文与独立输出目录。
   - **子 Worker 严禁越权写 GitHub**：任何协作 Skill 及其派生的子 Worker 均不得创建/更新 GitHub Issue、推送分支、创建 PR 或合并；所有并行产物必须汇聚至外环 Coordinator 统一验证后，再由 `$issue-pr-loop` 外环单写者执行已授权的 GitHub 动作。

## 7. 正例与反例

### 正例

1. **共享入口自动剥离 Fan-in（菱形拓扑解锁并发）**
   - **场景**：模块 A/B/C 分别改 `src/modules/{a,b,c}.ts`，且均需在 `src/index.ts` 导出并更新 `README.md`。
   - **正确做法**：识别 `src/index.ts` 与 `README.md` 为共享入口/汇总重叠而非逻辑紧耦合，自动剥离为后置单写者节点 `T-fanin`（依赖 A/B/C）；中段 A/B/C 在 `share`/`worktree` 隔离工作区 3 路并发，完成后由外环合入并运行 `T-fanin` 统一更新导出与文档。
2. **核心逻辑紧耦合退回串行**
   - **场景**：任务 T1（状态枚举改造）与 T2（状态流转校验重写）均深度修改 `src/core/state-machine.ts` 核心数据结构，且 T2 依赖 T1 导出类型。
   - **正确做法**：判定同时命中 RAW 因果契约依赖与核心代码 WAW 紧耦合重叠，不可剥离 Fan-in；在 `HITL-1` 并发 Schema 中如实标注 `写入并发 ≤ 1（串行）`，按 `T1 → T2` 顺序执行，确认前不改文件。
3. **用户临时上限 `K` 与关键路径优先（CP-First）**
   - **场景**：4 个写任务隔离（`T1` 唯一阻塞 `T5`，`T2/T3/T4` 无后续阻塞）与 3 个只读核验任务；用户要求写入临时上限 `K_user=2`。
   - **正确做法**：`HITL-1` Schema 明确独立任务总数 7，拆分披露 `写入并发 ≤ 2 / 只读并发 ≤ 3`；写入槽位优先派发关键路径权重最高的 `T1` 搭配 `T2`，`T1` 完结并回收槽位后立刻解锁 `T5` 与 `T3` 接力，不让边缘任务阻塞 `T5`。
4. **槽位紧张 + 429 限流下的弹性推进与 Slot Hygiene**
   - **场景**：8 个隔离评测任务待跑（多账号池后端），客户端仅剩 2 个活跃子代理槽位，且第 1 批出现 1 次 429 限流。
   - **正确做法**：不空等 8 槽位凑齐，立即按 `K_eff=2` 扇出消费多账号池；每个任务交付并验明独立输出文件后立刻销毁 Worker 回收槽位补位；遇 429 时临时缩窗至 `1` 做退避推进，绝不将多个任务揉进同一上下文，恢复后再拉满至 `2`。
5. **`/goal` 内嵌主动 Swarm 与无并发工具诚实降级**
   - **场景**：长程重构已过 HITL-1 准备跑 `/goal`；客户端 A 支持内置 Swarm，客户端 B 仅支持单线调用。
   - **正确做法**：`/goal` 指令本身写明“遇隔离并发波次主动调用内置 Swarm/独立工作区并发子代理（写隔离 `share`/`worktree`，外环单写者合入开 PR），无并发工具时按关键路径串行降级，停在 HITL-2 不合并”。客户端 A 自动并发推进；客户端 B 如实按 CP-First 串行推进并标注降级事实，绝不伪造并发。
6. **跨 Skill 透传并发与 GitHub 单写者收口**
   - **场景**：获批阶段先调 `$speckit-implement` 跑 4 个 `[P]` 并行任务，再调 `$darwin-skill` 跑 6 题多评委盲评。
   - **正确做法**：阶段切换经外环交接并披露 5 要素（纵向 `Single Dispatch`）；阶段内分别允许 4 路独立工作区并发实现与多题/多评委 `inherit` 并发盲评；所有子 Worker 禁止新建 Issue、推送或开 PR，成果统一回流 `$issue-pr-loop` 外环验明后单写者开 PR。

### 反例

1. **误把共享入口重叠判死为全串行或让并发 Worker 抢写同一索引**
   - **错误做法**：看到 A/B/C 都要在 `plugins/registry.json` 加一项，要么直接把 A/B/C 全部退回串行浪费并发，要么让 3 个并发 Worker 直接改同一个 `registry.json` 造成合并冲突或覆盖丢失。
2. **忽视紧耦合硬上并发导致语义破坏**
   - **错误做法**：对同时改造同一状态机核心类型与流转逻辑的 `state-machine.ts` 两个任务强行开 `worktree` 并发修改，造成类型契约不匹配与大面积逻辑冲突。
3. **设死静态上限或只按任务编号顺序排程（违反 CP-First）**
   - **错误做法**：在协议里硬编码“并发永远 ≤ 2”；或在 `K_user=2` 限流时机械按 `T2, T3` 先跑边缘任务，把关键路径瓶颈 `T1` 压到最后，导致 `T5` 长时间饥饿阻塞。
4. **空等凑齐槽位、僵尸占槽或 429 串台揉包**
   - **错误做法**：有 8 个任务但只有 2 个槽位时停着不动等 8 个槽位；或 Worker 完成后不销毁回收占死槽位；或遇 429 时把 3 份独立代码审计/评测塞进同一个子代理上下文一起跑，导致相互污染与裁决失真。
5. **未暴露并发工具却伪造 Swarm 并行**
   - **错误做法**：在只支持单线执行的客户端中，不按关键路径诚实串行降级，而是在输出中伪造“已并发拉起 4 个 Worker 并行完成”。
6. **越权让协作子 Worker 写 GitHub 或混写外环主权**
   - **错误做法**：在 `$speckit-implement` 并行执行 `[P]` 任务后，让子 Worker 顺手直接 `git push` 并创建 PR 或合并；或跳过 5 要素披露在阶段内部自动嵌套拉起 `$darwin-skill`。
