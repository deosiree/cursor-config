# Issue 与 PR few-shot

本目录演示如何把仓库规则转成清楚、可读、可核对的 Issue 与 PR 正文。样例中的业务事实、编号和测试结果均为格式演示，不可复制为真实项目事实。

## 使用规则

1. 先读取仓库的 `CONTRIBUTING`、Issue/PR 模板、仓库规则和近期同类工件。模板决定必需字段；保留仓库的标题前缀、章节名和顺序。
2. 用户拥有的个人仓库默认用中文。外部仓库遵循明示的贡献语言规则；没有明示规则时，参考近期 Issue/PR 与项目文档的主要语言。所有权或语言不清时先询问。
3. 仓库有明确的强制语言规则且与用户偏好冲突时，先说明冲突并确认，再发布。
4. 示例只帮助模仿结构、语气与信息密度。每次重新核实项目事实、标签、依赖、验证结果和权限；不要复用示例的编号、事实或结论。
5. 删除样例中的注释后再生成最终正文。标题与正文分开；标题、段落、列表和代码块按平台规则留出空行。
6. 仓库要求“行业规范 + 本仓库规范”时，不套用臆造的通用 PR 模板：先抽取平台指南要求表达的信息，再逐项映射到本地章节；本地章节保留原名和顺序，冲突时先询问。
7. Issue 的代码现状依据写明仓库、诊断分支和 commit SHA，并另列预期 PR 目标分支。PR 目标分支在创建前确认并在远端读回核对；只有合并日期、实际合入分支和 merge SHA 要等真实合并后填写。

## Issue 样例

- [[issue/01-缺陷反馈.md]]：标题与正文分开；问题描述、复现、实际结果、预期结果和可观察验收。
- [[issue/02-能力改进.md]]：标题与正文分开；现状、期望行为、验收和待确认项。
- [[issue/03-缺空行反例与修正.md]]：展示单行挤压的问题，并给出只调整 Markdown 结构的修正版。
- [[issue/04-通用问题单与分支基线.md]]：将通用问题单信息与本地要求的代码诊断分支、commit 基线组合。

这些样例是根据用户认可的历史结构脱敏整理，不是历史 Issue 的逐字副本。反例只用于识别格式错误，不要复制到新 Issue。

## PR 样例

- [[pr/自有仓库-中文.md]]：自有仓库的中文标题与正文，验证部分只放实际结果。
- [[pr/外部仓库-英文.md]]：外部仓库明确要求英文时，保留其模板结构并使用英文。
- [[pr/通用信息与TranslationTool-DCM结合.md]]：将 GitHub PR 的通用审阅信息映射进用户提供的 DCM 本地章节；展示合并前不填写未来的合并事实。

PR 的目的、关联 Issue、改动内容、验证、未运行检查和风险按需组织。未运行的检查写 `not-run`，不得把假设或样例结果写成通过。
