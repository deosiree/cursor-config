# 项目验收与文档收敛

## 核心任务

用实际代码和运行证据检查整个项目是否达到最初 Goal，不把 Issue 已关闭或单测通过等同于产品完成。

## 何时使用

- Issue 图中的实现任务均已完成，准备宣布项目交付。
- 用户要求项目级功能回归、压测、渗透测试或文档一致性检查。
- Goal、实现、测试、PR 和维护文档可能已经漂移。

## 输入 / 前置条件

- 已确认版本的 `goal.md`、`issue-graph.md`、全部对应 `develop.md`。
- 当前默认分支或指定集成版本、合并 PR/commit 清单、项目运行方式。
- Goal 中批准的端到端验收、负载模型、性能阈值、安全范围、测试环境与授权。

关键指标或安全授权不完整时，不运行高影响测试，不判通过；列为 `blocked` 并请求所需事实。

## 流程

1. **核对完成范围**：读取 GitHub 实时 Issue/PR 状态和合并 commit；检查图中所有前置、延期、取消和新增节点。未完成项明确列出。
2. **建立追踪矩阵**：逐条映射 `G-*` → Issue → 合并 PR/commit → 测试/运行证据 → 用户文档。任何目标遗漏、无来源代码或无文档责任项都列为差异。
3. **功能集成验证**：在项目规定环境运行端到端关键场景、回归测试和适用构建检查；记录命令、环境、版本、结果和缺陷。自动化缺失的场景标注人工验收，不编造结果。
4. **性能验证**：严格使用 Goal 中确认的负载、持续时间、成功率、延迟和资源阈值；在授权的隔离环境运行，记录工具、配置、原始结果和 commit。未有阈值或基准时只提出需决策项，不自行选择阈值宣布通过。
5. **安全验证**：按批准的威胁模型、测试范围和授权，在非生产环境执行安全测试；保存工具版本、范围、发现等级和复测结果。没有明确授权/环境就记 `not-run`，不得扫描未授权目标。
6. **检查文档漂移**：对照 Goal、Issue、代码/API 行为、测试名称和用户文档；修正文档或提出 Goal 变更。用具体路径和证据定位差异。
7. **收敛结论**：所有适用门禁通过、Critical/Major 风险关闭、文档对齐后才标 `converged`。否则输出阻塞项、负责人、修复 Issue 和下一次验证条件。

## 输出

- Goal 到实现和验证证据的追踪矩阵。
- 功能、性能、安全和文档检查结果，分别标记 `pass`、`fail`、`not-run` 或 `blocked`。
- 缺陷/漂移清单、责任 Issue、修复和复验状态。
- 结论：`converged`、`conditional` 或 `blocked`；不得将缺证据的项目标为 `pass`。

## 边界

- 不在未批准的生产系统上运行负载或渗透测试。
- 不改变 Goal 指标以匹配失败结果；Goal 变更必须由用户确认并同步追踪矩阵。
- 不自行关闭未修复的风险、豁免验收或宣布人工体验验收通过。

## 使用示例

```text
Issue 都显示已合并。请按 goal.md 的验收条件做项目终验，功能、性能、安全、文档四部分分别给出证据；尚未执行的压测或渗透测试必须明确标 not-run。
```
