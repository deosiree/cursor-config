## 2026-11-26 显式调用 Issue 优先 MVP

### 失败基线

- 原 `no-trigger-single-bug` 与 holdout-4 只覆盖未显式调用 skill 的普通小修；没有测试用户明确选择 `$issue-pr-loop` 后仍应留问题记录并等待方案确认。
- 主入口允许直接实现单点小修，候选登记又是默认而非必需；因此“显式选择 Issue 流程”与“直接进入代码修复”之间缺少明确优先级和停止状态。

### 本轮 MVP

- 显式调用 `$issue-pr-loop` 后，即使是单点问题，也先复用远端 Issue 或建立本地候选记录，形成 Issue 草稿与精简方案，默认停在 `plan-pending-confirmation`。
- 只有用户明确要求现在直接开始修复时才跳过方案等待；问题记录、范围、验收与验证证据仍保留。GitHub Issue、推送和 PR 的授权仍单独判断。
- 未显式调用 skill 的普通单点修复仍不自动触发 Issue 流程；已确认计划的继续任务可以在原范围内执行。

### 定向手工 dry-run

- `dev-5` 显式调用并等待确认：5/5 检查项符合流程。
- `dev-6` 明确要求立即开始修复：4/4 检查项符合流程。
- `holdout-4` 未显式调用的普通小修：4/4 检查项保持不触发且不强加留痕。
- 合计 13/13 条文档规则推演检查通过。该结果由本轮主执行者按文档手工推演，不是独立 agent 执行、盲评、E2 对照或业务仓库实测。
- Darwin E0：0 错误、0 警告、0 提示；三个 JSON 文件可解析且评估用例 ID 无重复；`git diff --check` 通过。

### 结论边界

- 本轮仅证明新增规则与三类目标路径没有明显自相矛盾。没有运行独立 A/B E2；历史 97/100 基线来自两条规划任务，不作为本次行为的对照分数。
- 新版保留为功能分支候选，待后续使用相同输入、仓库快照和授权约束做独立受控评估后再决定 `keep` 或 `revert`。
