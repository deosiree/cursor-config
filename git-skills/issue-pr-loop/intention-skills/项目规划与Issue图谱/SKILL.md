# 项目规划与 Issue 图谱

## 核心任务

在开始实现前，把用户意图收敛为一个 Goal、一个 Issue DAG 和一组本地 Issue 计划。先让人确认范围和可观测验收，再进行 GitHub 写入。

## 何时使用

- 用户给出跨模块或多阶段项目需求，尚无可直接执行的 Issue 序列。
- 用户已从候选池选定一批需求，需要形成可发布的 Issue 草稿和依赖图。
- 需要从现有 Issue、产品需求或代码库基线重新建立项目依赖图。
- 新项目需要建立初始开发计划，或旧项目需要整理维护 backlog。
- 需要给已确认的项目补 Goal ID、验收追踪或文件所有权。

## 输入 / 前置条件

- 当前会话中的需求、示例、限制和已有决策。
- 已评审的候选及其来源、分类、代码/需求证据和未决问题；未评审建议先路由到 [[../需求收敛与Backlog排程/SKILL.md]]。
- 仓库路径、现有文档惯例、目标 GitHub 仓库；缺失时先查可确认的本地上下文。
- 用户需要的输出位置；未指定时使用仓库已存在的设计文档目录，不存在则建议 `docs/development/<project>/`。
- GitHub Issue 的创建/更新授权。没有明确授权时只生成本地草稿。

影响用户行为、数据、安全、预算或最终验收的歧义必须提问。其它实现选择先查看源码和仓库规范；没有证据时标为待确认或假设，不写成事实。

## 流程

1. **建立现状**：检查仓库规则、现有需求文档、请求实际入口及调用链、关键测试、Issue/PR 状态、验证命令和工作树改动。对错误/通知类行为同时查请求拦截器、公共 helper 和业务调用点；只读单个 helper 不足以证明全局行为。需求讨论和调研在当前会话进行；只有需要核实外部事实时才搜索资料。
2. **选定项目模式**：新项目建立新的 Goal；旧项目复用长期维护 Goal 和现有 Issue 图，不为每条建议重建。若是一个边界清楚的维护 Issue 且没有跨 Issue 依赖，可只写该 Issue 草稿和必要的 `develop.md`，不强制生成全局 Goal 与图谱。
3. **写 Goal 草稿**：需要项目级规划时，按 [[../../template/mvp/goal.md]] 记录目标、用户场景、非目标、约束、风险、假设、待澄清项、全局验收条件和退出条件。用 `G-01` 等稳定 ID 标识验收条件；每项依据须直接引用规格中的用户故事、功能需求或成功标准 ID。计划、任务清单和 quickstart 可补充实现线索，但不能替代需求事实源；无直接依据时标为待确认，不伪造追溯。旧项目 Goal 记录本批次范围，不覆盖历史维护目标。
4. **澄清并冻结**：对影响范围和验收的 `NEEDS CLARIFICATION` 一次汇总提问。Goal 确认后记 `baselineVersion`、确认时间和决策者；后续目标变化走显式变更记录。旧项目单 Issue 不需要为形式而冻结新 Goal。
5. **垂直拆分 Issue**：每个 Issue 只交付一个可独立验证的结果；写清标题、背景、范围、非目标、依赖、验收条件和交付物。将已确认事实、建议和待澄清项分开；验收条件可观察，不把参考实现参数伪装成用户决定。检查仓库规则要求的行业规范和本地格式，将通用信息要素映射到本地章节，不覆盖仓库明确格式；冲突时先询问。若 Issue 基于代码现状，分别记录仓库、观察问题时的诊断分支与 commit SHA、预期实现/PR 目标分支。目标分支按用户确认或项目约定核实，不从 GitHub 默认分支推断；未核实时标 `unknown` 并在创建 PR 前解决。标题与正文分开；用户自有个人仓库默认中文，外部仓库遵循贡献语言规则或项目主要语言。参照 [[../../assets/few-shot-example/README.md]] 保持格式一致。
6. **建立依赖图**：多 Issue 批次按 [[../../template/mvp/issue-graph.md]] 填依赖表和 Mermaid 图。表格是事实源，图只作展示。节点记录稳定本地 ID、可核实的 Goal ID、`blocked_by`、排程波次、并行组、文件所有权和验证入口。
7. **检查范围与排程**：确认 ID 唯一、依赖无环、Goal 覆盖完整。依赖无边只代表可评估并行；还要确认共享接口冻结、文件和测试数据隔离、独立工作区及可用团队名额。只要求“排期建议”时输出波次，不自动创建代理或指派。排程建议必须逐一列出 Issue 作者、实现者、PR 作者、reviewer 和合并决策者；未知角色写 `unknown`，不得互相推断，审查通过也不等同于合并。
8. **写本地交付材料**：多 Issue 批次为每个节点生成 `issues/<issue-id>/develop.md`；单 Issue 仅在实现者需要文件边界或详细验证计划时生成。GitHub Issue 保持可审阅，详细执行计划留在本地。
9. **发布并同步**：用户明确要求发布当前这批 Issue 即构成写入授权；否则先给完整草稿与批次清单，等用户选定。保留本地 ID 与实际 GitHub 编号/URL 映射；只有 API 和权限支持时同步原生依赖，发布后读回核对正文、标签和依赖。创建 Issue 本身不启动实现或 PR。

## 图谱校验规则

- 每个 Issue 至少映射一个 Goal ID；每个 Goal 验收 ID 必须回链到原始需求/用户故事事实源并映射一个或多个 Issue、验证证据和相关文档，不得只引用实现计划；项目级终验须明确标注。
- 新项目以用户确认的 Goal 为锚点；旧项目维护 Issue 引用稳定的维护目标或明确说明不需要全局 Goal。
- `blocked_by` 表示前置任务未完成时禁止开始实现；不以“相关”替代阻塞关系。
- Mermaid 图只呈现依赖表中的边。若二者不一致，依赖表优先，修复图后再交付。
- 路径冲突、共享接口未定、测试数据竞争都取消并行资格，即使图上没有依赖边。
- 本地草稿节点使用 `I-01` 等稳定 ID；发布后同时记录 GitHub issue URL 和 `#number`，不得通过标题匹配猜编号。

## 输出

- `goal.md`：已确认的目标锚点或含阻塞项的草稿。
- `issue-graph.md`：依赖事实表、Mermaid 展示、路径边界、波次和 Issue 映射。
- `issues/<issue-id>/develop.md`：逐 Issue 计划。
- 授权范围内发布时，报告实际创建/更新的 Issue URL 和依赖读回结果。
- `status`：`draft`、`awaiting_clarification`、`ready_for_issue_creation`、`ready_for_development` 或 `blocked`。
- 批量候选的合并、拆分、延期和拒绝均记录来源 ID 与理由；没有被用户选中的候选不发布。

## 边界

- 不替用户决定影响需求范围、产品指标、安全范围或预算的歧义。
- 不创建 GitHub Issue，除非请求明确要求创建或更新。
- 不把发布 Issue 与开始实现、创建 PR 或合并绑定为同一步；这些动作分别检查本次授权。
- 不把 Spec Kit 的完整 `.specify` 结构作为前置条件；仅复用需求澄清、Plan、Analyze 的必要部分。
- 不将所有实现细节提前写成大计划；只为 Issue 图中可执行节点准备 `develop.md`。

## 使用示例

```text
把这个多模块需求整理成 goal.md 和 GitHub Issue 依赖图。Issue 草稿先落在本地，先检查每个 Goal ID 是否都有 Issue 和验收证据，再等我确认后发布。
```
