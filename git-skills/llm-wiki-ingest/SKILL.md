# LLM Wiki Ingest

按目标 Wiki 的 `SCHEMA.md` 摄取用户明确指定的来源。此技能兼顾人的理解与 Agent 检索，不以生成文件数量作为目标。

## 使用时机

- 用户明确要求将指定文章、链接、对话、文件或笔记摄取到 LLM Wiki。
- 用户要求整理复杂技术资料，并希望保留图示、来源追溯、索引和操作日志。

## 执行流程

1. 确认目标 Wiki 根目录，先读取其中的 `AGENTS.md`（若存在）、`SCHEMA.md`、索引、日志及必要的相邻 canonical 页面；不得假定当前工作目录就是 Wiki。
2. 完整阅读用户指定的来源。不得因主题相似而扫描或迁移其他旧资料。
3. 记录来源类型和出处。可访问原文时按 Wiki 规范保存快照；来源是用户消息且没有独立 URL 时，如实记录“用户提供的对话文本”，不要编造 URL。来源快照不翻译、不删节、不润色；外链只按其原用途记录，不能自动视作论据。
4. 在 `raw/` 保存原始快照，在 `entities/`、`concepts/`、`comparisons/` 或 `queries/` 等 canonical 目录创建或更新知识页。必须区分来源事实、跨段综合解释和本地推断，并标注置信度与适用边界。
5. 复杂技术资料先识别概念层级、实体关系、系统分层、调用顺序和决策分支，再在相关正文附近嵌入互补的 Mermaid 图：概念层级用 `mindmap`，实体关系用 `erDiagram`，架构/决策用 `flowchart`，调用顺序用 `sequenceDiagram`。图后紧跟阅读提示；推断关系和基数须明确标注。只有 Mermaid 无法清晰表达时才创建独立 HTML 图及所需资源。
6. 用 Obsidian 双链连接相关页面，更新索引、页面总数和操作日志。保留原始来源文件不变，除非用户明确授权修改。
7. 内容、索引、日志和来源快照写入后立即执行本次范围的 lint。发现可安全修复的问题时先修复并重跑；仍有失败项时如实报告，不得称为完成。

## 必查项目

- Frontmatter 字段、页面类型、已登记标签、来源路径和双链均有效。
- 原文快照保留状态及正文哈希一致；索引覆盖页面且总数准确；日志记录本次文件和结果。
- Mermaid 围栏配对、图类型、实体/关系/方向的来源依据、图与正文的位置及紧随其后的阅读提示。
- HTML 和资源路径存在；未使用 HTML 时确认没有遗留引用。
- 只检查用户本次授权范围及必要引用目标，不扫描或修复无关的历史资料。

## 交付报告

列出新建或更新的文件、生成的图和每项 lint 结果；说明来源限制、推断点和未解决问题。所有结论都应可由来源或明确标记的推理追溯。
