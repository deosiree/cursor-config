# 编排-版本前问题核对

## 核心任务

解析本次约束、筛选记录、收集代码证据，并协调功能节点生成完整报告。

## 何时触发

- 父级收到人工发版前扫描请求并已通过基本输入检查。
- 用户指定新的文档、仓库、人员或列集合，需要按本次值覆盖默认配置。

## 输入 / 前置条件

- 已解析 `recordDocument`、`referenceRepos`、`developerName`、`targetColumns`、`targetVersion`。
- `repoRefs` 可按仓库路径提供 refs；解析优先级为仓库级字段、全局显式字段、每仓库默认值。未提供全局基线时，各仓库独立选择最近可达发布 tag；目标 ref 默认各自的 `HEAD`。
- 可选 `recordIds` 用于按业务 ID 缩小行集合；可选 `sourceRows` 用工作表名和物理行号精确定位已由用户确认的行；可选 `reportPath` 覆盖默认输出路径。

## GREEN 编排

1. 对照输入契约，先解决缺项、空列、无效路径和目标版本不清；逐仓库解析 refs 并固定为 commit SHA。记录 dirty source 状态，但 commit refs 扫描只读 refs 内容，不把工作区改动混入证据。
2. 调用 `[[../../feature-skills/读取问题记录文档/SKILL.md]]`，按人员、版本、业务 ID 或可选物理行定位提取原始行；核对提取数量和来源定位。
3. 调用 `[[../../feature-skills/扫描参考仓库/SKILL.md]]`，逐仓库使用解析后的 refs，逐行定位当前实现和版本差异；多仓库分别给出证据。
4. 调用 `[[../../feature-skills/生成指定列报告/SKILL.md]]`，仅输出目标列及审核辅助信息。
5. 对照报告模板核验行数、列名、顺序、证据状态和未执行测试标记。

## 输出

- `resolvedInputs`：实际使用的文档、人员、列、版本，以及每个仓库各自的路径、refs、SHA 和工作区状态。
- `selectedRecords`：纳入报告的记录及来源 ID 或工作表/物理行定位；不得把工作表行号伪装为业务 ID。
- `evidenceMap`：逐记录、逐仓库的证据状态和定位信息。
- `reportPath`：唯一生成的 Markdown 文件路径。
- `unresolvedItems`：无法继续的全局问题，或报告内需要人工复核的单行问题。

## 边界与失败处理

- 单行缺代码证据时保留该行并标注状态；不得整行猜写。
- 来源无法读取、目标人员/版本/行范围无法核实、任一仓库 refs 歧义时暂停并询问。若工作区 dirty 但本次已明确按 commit ref 扫描，记录并排除工作区改动；用户要求纳入未提交内容时先固定可复查快照。
- 不把功能节点建议的测试步骤写成已执行结果；不自行修复、提交、切换 refs 或修改线上表格。
- 若用户只要求改现成报告格式，直接转交生成报告功能，不重新扫描仓库。

## 使用示例

```text
编排一次版本前核对：记录来源为问题台账.xlsx，仓库为前端和服务端，
负责人为惠岩，仅输出“改动方案说明”和“开发自测结果”，目标版本 2.4.0。
```
