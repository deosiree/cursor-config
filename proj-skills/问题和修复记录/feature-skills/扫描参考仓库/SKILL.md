# 扫描参考仓库

## 核心任务

以本次解析的版本 refs 为范围，核对需求对应的代码实现、调用链、权限/数据边界和仓库外依赖，并提供可复查证据。

## 何时触发

- 记录读取功能已返回筛选后的问题行。
- 用户提供一个或多个参考仓库，需要判断实现状态或变更范围。

## 输入 / 前置条件

- `referenceRepos`：一个或多个存在的 Git 仓库路径。
- `repoRefs`：可选的仓库路径到 `baseRef` / `targetRef` 映射；仅覆盖映射中明确提供的字段。
- `baseRef` / `targetRef`：可选全局显式 ref，作为没有仓库级覆盖时的回退值。
- `selectedRows`：每行含原记录 ID（若有）、来源工作表/物理行（若适用）、需求描述和关联上下文。

## 每仓库 ref 解析

每个仓库独立解析 refs：仓库级 `repoRefs` 字段优先于全局显式字段；基线仍未指定时，选择该仓库目标 ref 可达的最近唯一发布 tag；目标仍未指定时使用该仓库的 `HEAD`。因此不同仓库可以使用不同 tag、分支或提交。`repoRefs` 中的路径必须能唯一对应 `referenceRepos` 的一个路径；重复或无法匹配的路径先询问。没有列入 `repoRefs` 的仓库，以及映射中未提供的字段，继续使用全局显式值或该仓库默认值。

## 版本口径

`targetVersion` 是问题记录的业务版本，`targetRef` 是代码证据快照，两者不能互相推断。若目标 ref 未被确认对应 `targetVersion` 的发布快照，结论只描述该 ref 上的当前代码；报告需标记历史版本状态未确认。用户若要求判断某功能在指定发布版本中是否存在，必须使用可验证对应关系的 tag/commit，否则暂停询问，不用较新的 `HEAD` 代替历史版本。

## 执行与输出

1. 对每个仓库分别记录实际路径、分支、`git status --short`、解析后的 refs 和目标 SHA；不切换分支或改工作区。将 ref 解析到的 SHA 作为唯一代码快照，使用限定 ref 的 Git 读取命令取证。
2. 在每个仓库内筛选名称包含 `x.y.z` 版本号且可从该仓库目标 ref 到达的发布 tag，按提交图距离选择最近者。没有候选或最近距离并列时，暂停并询问该仓库的基线。
3. 分别读取每个仓库的 `baseRef..targetRef` 差异并搜索目标版本代码；再追踪必要的类型、调用方和接口契约，避免仅凭命中字符串下结论。引用前用目标 SHA 的 tree 确认每个文件路径存在，并用该 SHA 的文件内容核对符号/行号；路径不存在时重新定位，不复制工作区路径到报告。普通文件读取不得取代 ref 快照读取。
4. 区分可执行路径与注释代码、关闭的 feature flag、不可达分支或被隐藏的 UI；这些代码只能证明痕迹存在，不能证明当前版本功能可用。使用 `[[../../references/证据分级与只读边界.md]]` 给每条记录分类，输出仓库、ref、文件路径、符号/行号、观察事实和限制，并注明代码快照是否能代表记录的目标版本。
5. 多仓库分别报告证据；不可访问的仓库明确列为待提供，不从其他项目推断。

## 边界

- 仅运行只读 Git 和静态检索/阅读命令；不得运行测试、构建、安装依赖或会写缓存的工具。
- 不以搜索未命中证明功能不存在；写成“在已检查范围内未定位到”。
- 工作区 dirty 时记录状态并排除未提交差异；只要目标 refs 已解析为明确 commit，就继续读取这些 refs，不因无关或已明确排除的脏文件而停止。用户要求纳入未提交内容、目标快照无法固定或 ref 无法解析时暂停确认。
- 不修改、暂存、签出、重置或提交任何文件。

## 使用示例

```text
只读检查前端和服务端仓库，各自从最近可达发布 tag 比较到 HEAD；服务端覆盖为 v2.3.0 到 release/2.4。核对所给的 2.4.0 问题记录并返回逐条代码依据。
```
